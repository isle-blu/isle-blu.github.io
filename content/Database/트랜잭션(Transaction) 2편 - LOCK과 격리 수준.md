## LOCK

>[!NOTE] Lock?
한 트랜잭션이 데이터에 접근할 때, 해당 데이터에 ==동시에 다른 트랜잭션이 접근하지 못하도록 제어하는 방법==을 말한다. 

- 공유 자원에 대한 ==동시성(Concurrency) 문제를 방지하고 데이터의 일관성(Consistency)을 보장==하기 위해 사용된다.
- 종류로 **공유(Shared) lock**과 **배타(Exclusive) Lock**이 있다. 각각 Read Lock, Write Lock이라고 부르기도 한다.

<br/><br/>



추가 : 낙관락, 비관락

### LOCK의 종류

#### 공유(Shared) Lock
> 여러 트랜젝션이 **읽을 수 있게 허용**하지만 <u>쓰기는 허용하지 않는다.</u>

<br/>

#### 배타(Exclusive) Lock
>한 트랜젝션만 읽고 쓸 수 있으며, 락을 해제 하기 전까지 **다른 모든 트랜젝션의 읽기, 쓰기를 차단**한다.


<br/><br/>

### LOCK으로 발생할 수 있는 문제
#### Blocking(블로킹, 잠금 대기)
>한 트랜잭션이 **락을 걸어둔 채**로 작업이 진행 중 일 때, <u>다른 트랜잭션이 해당 데이터에 접근</u>하려고 하면 ==대기 상태==가 되는 문제이다.

- 공유 락 사이에서는 발생하지 않는다.
- 이 경우 이전 트랜젝션이 커밋, 롤백이 진행돼야 블로킹이 해소된다.
- <u>블로킹이 너무 많이 걸려있는 경우</u> **서비스 지연이 발생**할 수 있다.

<br/>


>[!check] 방지 및 해소법
>- 한 트랜젝션의 길이를 길게하지 않게해, 동시에 접근할 확률을 줄인다.
>- 설계 시 데이터를 갱신(쓰기)하는 트랜젝션이 동시에 수행되지 않게 한다.
>- 트랜잭션 격리 수준을 너무 높게 설정하지 않는다.


<br/>

#### Deadlock(교착 상태)
> ==둘 이상의 트랜젝션이 각각 락을 설정하고 서로의 락에 접근하여 데이터를 얻어오려 하는 상황==으로,
> 서로 영원히 기다리기만 하고 진행이 멈추게 된다. 

- 일반적으로 시스템이 하나의 트랜젝션을 강제 중지(rollback) 시켜 원래 상태로 돌린다.
- 자주 발생할 경우 시스템 성능이 저하되고, 데이터 손실 가능성이 증가한다.

<br/>

>[!check] 방지 및 해소법
>- 일관된 Lock 획득 순서를 유지한다. 여러 자원을 사용할 경우, 항상 동일한 순서로 자원에 접근하도록 설정한다.
>- 타임아웃을 설정해, 일정 시간 이상 락을 기다리면 자동으로 실패하게 설정한다.
>- 블로킹 방지법과 마찬가지로 트랜잭션을 길이를 짧게한다.


<br/><br/><br/>

## 트랜잭션 격리 수준
>[!Note] 트랜잭션 격리 수준?
>트랜잭션 간 격리 정도를 설정해, 한 트랜잭션이 ==다른 트랜잭션에 의해 변경된 데이터를 볼 수 있는지 여부를 결정==하는 것을 말한다.

- SQL표준에서는 **4가지 종류의 격리 수준**을 정의해놓았다. <u>격리 수준이 낮을 수록 성능이 높지만 이상 현상이 발생할 확률도 높다</u>.
- 반대로, 격리수준이 높을수록 이상 현상이 발생가능성이 낮지만, 성능이 그만큼 떨어진다.
- 격리 수준을 통해 **동시성과 데이터 무결성을 조절**할 수 있다.
- 격리 수준의 종류는 다음과 같다.

> - Read Uncommitted
> - Read Committed
> - Repeatable Read
> - Serializable

<br/><br/>

### 격리 수준의 종류

#### Read Uncommitted
> 다른 트랜잭션이 **커밋되지 않은 변경사항 모두 읽을 수 있다**.
- 가장 낮은 격리 수준
- 성능은 가장 뛰어나지만, <u>데이터 무결성 보장이 어렵다</u>.
 
![[transaction2.png]]

- <u>커밋되지 않은 다른 트랜잭션의 데이터를 읽어오는 문제</u>가 있다. -> **Dirty Read**
- Dirty Read뿐 아니라 **Non-Repeatable Read, Phantom Read**가 모두 발생할 수 있다. (각 문제에 대한 자세한 내용은 아래에서 확인할 수 있다.)


<br/>

>[!warning] Dirty Read
>- <u>커밋되지 않은 다른 트랜잭션의 데이터를 읽어오는 현상</u>
>- Read Committed 수준에서 발생한다.
>- 위 이미지에서도 Dirty Read가 발생한 것을 볼 수 있다.

<br/>

#### Read Committed
> 다른 트랜잭션이 **커밋한 데이터만 읽을 수 있다.**
- 만약 다른 트랜잭션이 먼저 데이터를 참조하고 있는 경우, 실제 테이블이 아닌 ==Undo 영역에 백업된 데이터를 가져온다.==
- 가장 널리 사용되는 격리 수준이다. (ex. Oracle, PostgreSQL의 기본값)


![[transaction3.png]]


- 참조하고 있는 데이터가 다른 트랜잭션으로 인해 변경되고 커밋 된 경우, <u>이전 조회와 다른 결과</u>가 나올 수 있다. -> **Non-Repeatable Read**, 이로 인해 <u>일관성(Consistency)에 문제</u>가 생긴다.
- **Phantom Read** 문제도 발생 가능하다.

<br/>

>[!warning] Non-Repeatable Read
> - <u>같은 데이터를 2번 읽었는데, 그 결과가 다른 현상</u>
> - 다른 트랜잭션의 커밋으로 인해 위와 같은 문제가 발생할 수 있다.
> - Read Committed, Read Uncommitted에서 발생 가능하다.
> 
> ![[transaction4.png]]



<br/>

#### Repeatable Read
> 한 트랙잭션에서 같은 데이터를 **여러 번 조회해도 항상 같은 결과** 나와야한다.
- Non-Repeatable Read 문제를 방지한 격리 수준이다.
- <u>대부분의 일관성 문제를 방지</u>할 수 있다.
- MySQL InnoDB의 기본 격리 수준이다.
- **MVCC**와 Next-Key Lock와 같은 방식으로 구현한다.

<br/>

>[!info] MVCC(Multi-Version Concurrency Control)
>- <u>**하나의 데이터에 여러 버전을 유지**하여 읽기와 쓰기를 충돌없이 처리하는 동시성 제어 기법</u>
>- ==Lock을 필요로 하지 않아== 매우 빠르게 작동한다.
>- 자세한 내용은 추후에 작성해보고자 한다.

<br/>


- 트랜잭션마다 **고유한 트랜잭션 ID를 부여**하고, 자신의 ID보다 ==작은 ID 값의 트랜잭션에서 변경하고 커밋한 데이터만 읽는다==.

![[transaction5.png]]

- MySQL은 **Undo log**를 통해 MVCC를 구현한다. Undo log는 데이터의 이전 버전을 log로 저장한 것이다. 변경된 데이터가 있는 경우 ==트랜잭션은 Undo log에서 변경 이전 데이터를 조회==한다.
- 하지만 Undo log가 너무 많이 쌓인 경우, 데이터베이스 처리 성능에 문제가 생길 수 있다. 따라서 일정 주기마다 삭제가 필요하다.
- 일정 범위의 데이터를 2번 읽을 때 첫번째 쿼리에는 <u>없었던 유령 데이터(Phantom)가 생기거나 사라지는 문제</u>가 발생할 수 있다. -> **Phantom Read**

<br/>

>[!warning] Phantom Read 
> - <u>일정 범위의 데이터를 2번 읽을 때 첫번째 쿼리에는 없었던 유령 데이터(Phantom)가 생기거나 사라지는 현상</u>
> - 다른 트랜잭션의 커밋으로 인해 위와 같은 문제가 발생할 수 있다.
> - Repeatable Read 이하 격리 수준에서 발생 가능하다.
> 
> ![[transaction6.png]]


<br/>

#### Serializable
> 트랜잭션이 **하나씩 순차적으로 실행**되는 완전한 고립 상태를 만든다.
- 위에서 설명한 모든 문제점들을 방지한다.
- 높은 일관성, 데이터 무결성을 보장하지만, 가장 낮은 동시성을 가진다.
- 성능 부담이 크기때문에 실무에서는 특별한 경우에만 사용한다.
