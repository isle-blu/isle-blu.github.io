# 오늘의 상황

> 채팅방 이름 변경·삭제, 읽음 처리, SSE 알림과 채팅 시작 기능을 차례로 작업했다.

읽음 처리·실시간 알림·채팅 시작 기능은 구현 전에 계획 문서를 만들었다. 계획에 남아 있는 질문에 답하면서 동작을 정하고, 구현은 Codex에 맡겼다. 이후 계획대로 구현됐는지 코드와 리뷰 결과를 확인했다.

가장 오래 고민한 것은 **테스트가 끝난 방에서 메시지 전송을 막을지, 무엇을 기준으로 끝났다고 볼지**였다.

# 오늘의 과정

## 테스트가 끝나면 채팅도 막아야 할까?

기존 기획은 테스트가 끝나면 채팅방을 읽기 전용으로 만드는 것이었다. 그런데 피드백을 받은 뒤 채팅으로 다시 물어보는 경우도 생각해야 했다. 이슈 109의 내용까지 고려하면, 테스트가 끝났다고 전송을 막는 것이 실제 사용 흐름과 맞지 않을 수 있었다.

AI는 처음에 마감 뒤에도 보낼 수 있다고 답했다. 기존 README의 11월 4일 결정을 근거로 바로잡고, 현재 테스트의 상태를 어떻게 구분하는지부터 다시 확인했다.

우선 기존 기획대로 테스트가 끝나면 전송을 막고, 종료 여부는 이미 있는 `phaseAt`을 기준으로 판단하기로 했다. 구독 조건은 개발자의 현재 구독 상태를 기준으로 확인하기로 했다.

나중에 종료 후에도 보낼 수 있도록 바꾼다면 수정 범위가 얼마나 클지도 따졌다. 그래서 읽기 전용 여부를 판단하는 코드는 `ChatReadOnlyPolicy` 한곳에 모았다. 채팅 시작과 메시지 전송에 같은 기준을 적용하고, 나중에 정책을 바꿀 때도 한곳에서 수정할 수 있도록 했다.

## 대화방 이름 변경과 삭제

대화방 이름 변경·삭제 기능을 구현하고 [PR 173](https://github.com/likelion-backendschool-9th/test-moa/pull/173)을 병합했다.

- 방 이름은 내 화면에서만 바뀌도록 했다.
- 삭제는 실제 데이터 삭제 대신 내 채팅함에서 숨기는 방식으로 구현했다.
- 상대가 새 메시지를 보내면 이름과 읽은 순번은 유지한 채 다시 나타나도록 했다.
- 이름의 앞뒤 공백과 NBSP를 제거하고, 빈 이름과 30자 초과를 검증했다.

이름 변경·삭제·읽음 처리가 동시에 실행돼도 다른 요청이 바꾼 값을 덮어쓰지 않도록 필요한 컬럼만 직접 갱신했다. HQL update에서 수정 일시가 자동으로 갱신되지 않는 부분도 보완했다. PostgreSQL에서 채팅 테스트 55개 통과를 확인했다.

## 읽음 처리와 상대 읽음 표시

읽음 처리와 안 읽은 수, 상대 읽음 표시를 구현하고 [PR 174](https://github.com/likelion-backendschool-9th/test-moa/pull/174)를 병합했다.

화면에 표시된 마지막 메시지의 순번을 받는 읽음 처리 API를 추가했다. 요청이 도착하는 순서가 바뀌더라도 읽은 순번이 내려가지 않도록, 기존 값보다 클 때만 갱신했다.

- 채팅함의 방별 안 읽은 수와 헤더용 전체 안 읽은 수를 제공했다.
- 내가 보낸 메시지와 숨긴 방은 안 읽은 수에서 제외했다.
- 상대가 읽은 마지막 순번을 방 정보에 추가했다.
- 방 숨김과 읽음 처리는 별개로 두고, 방을 숨겨도 읽은 순번은 바꾸지 않도록 했다.

상대 읽음 표시는 **내 메시지의 `seq`가 상대의 `last_read_seq` 이하인지**로 판단한다. 계획 문서뿐 아니라 이슈에도 이 시나리오를 추가했다.

PostgreSQL에서 채팅 테스트 68개 통과를 확인했다.

### 리뷰 대응

통합 리뷰의 세 항목을 코드와 대조했다. 읽음 처리가 성공한 뒤 DB를 다시 조회하지 않도록 수정하고, README에서 같은 규칙을 반복하던 두 줄도 정리했다.

엔티티의 `markRead`에 대한 리뷰 의견도 있었다. 실시간 알림 작업에서는 해당 메소드를 사용하지 않는다는 것을 확인했다. 수정 후 CI 통과를 확인하고, 이 내용과 함께 리뷰어에게 답글을 남겼다.

## SSE로 변경을 알리고 REST로 내용 가져오기

[PR 181](https://github.com/likelion-backendschool-9th/test-moa/pull/181)을 올렸다. 기록 시점에는 병합 전이다.

SSE로는 메시지 내용 대신 순번을 알리고, 실제 메시지는 REST API로 조회하도록 역할을 나눴다. 재연결 후 누락된 메시지를 가져올 수 있도록 `after` 조회도 추가했다. 알림은 DB 커밋 이후에 보내도록 했다.

### 다른 탭에는 어디까지 알려야 할까?

이름 변경·삭제는 다른 탭에 알리지 않기로 했는데, 계획의 시나리오에는 알림을 보내는 내용이 남아 있었다. 계획 안에서도 서로 어긋나는 부분이 있어서 범위를 다시 정리했다.

- **메시지·읽음 변경**: 내 다른 탭과 기기에도 알린다.
- **이름 변경·삭제**: 다른 탭에 알리는 작업은 범위에 넣지 않는다.

Next Route Handler 중계와 nginx 설정도 이번 실시간 알림 작업에 포함했다. 하트비트, 연결 만료, 회원당 연결 수 제한을 구현했고, 전송 오류 뒤 `complete()`를 호출하지 않도록 Spring 문서를 근거로 수정했다.

### 어디까지 검증했나?

- PostgreSQL 채팅 테스트 84개 통과
- 원격 Docker에서 nginx를 거쳐 95초 이상 연결 유지
- 메시지 알림·하트비트·연결 종료 후 정리 확인

실제 테스트 서버에서는 인증 모드와 호스트 nginx 설정까지 포함해 확인해야 한다. 프론트 화면에 연결하는 작업도 남아 있다.

## 채팅 시작과 숨긴 방 복원

밤에는 이슈 53을 `feature/chat-start`에서 구현했다.

- 확정된 참가를 기준으로 채팅을 시작하도록 했다.
- 참가 행을 잠가 동시에 요청해도 방이 중복 생성되지 않도록 했다.
- 기존 방이 있으면 재사용하고, 요청한 사용자의 숨김 상태만 해제했다.
- 모집 종료·취소 상태는 공통 정책으로 판단하도록 했다.
- 채팅방·채팅함에 읽기 전용 상태를 제공하고, 읽기 전용일 때는 메시지 전송을 차단했다.

기존 방에서 다시 채팅을 시작할 때 내 숨김 상태를 해제하는 것이 맞는지도 확인했다. 동작은 맞았지만, 시나리오의 Given이 앞 시나리오를 실행했다는 전제에 기대고 있었다. 해당 시나리오만 읽어도 조건을 알 수 있도록 전제 조건을 바로잡아야 했다.

숨김을 해제하기 위해 참여자 목록을 순회하던 부분은 `unhideMine(roomId, userId)`로 직접 갱신하도록 개선했다. 기본 구현 후에는 채팅 테스트 98개가 통과했고, 마지막 수정 후에는 채팅 시작 테스트 14개를 실행해 통과를 확인했다. 마지막 수정 후 전체 98개를 다시 실행하지는 않았다.

로컬 커밋까지 완료했고 push와 PR 생성은 아직 진행하지 않았다.

## 쌓인 브랜치에서 후속 작업 이어가기

읽음 처리 → 실시간 알림 → 채팅 시작 순서로 브랜치를 쌓아 작업했다.

읽음 처리 리뷰를 반영한 뒤 실시간 알림 브랜치를 rebase하면서 `markRead` 충돌을 해결했다. 조건부 갱신으로 실제 한 행이 변경됐을 때 이벤트를 보내고, DB를 다시 조회하지 않고 순번을 바로 반환하도록 맞췄다.

읽음 처리 PR이 병합된 뒤에는 `--update-refs`로 후속 두 브랜치를 함께 develop 위로 옮겼다. develop에 들어온 `phaseAt`도 반영했다.

실시간 알림 PR을 올리기 전에는 `synchronized` 사용과 `GlobalExceptionHandler` 등 계획 문서와 실제 코드의 차이를 확인해 PR 본문에 적었다.

## 원격 Docker 검증 환경 맞추기

원격 서버에서는 Gradle 배포판 다운로드가 시간 초과돼서 로컬에서 jar를 빌드했다. 원격 호스트에 로컬 파일을 bind mount할 수 없어 `dockerfile_inline`과 `COPY`로 전달했다.

테스트 서버의 `compose.prod.yaml`에는 frontend의 `AUTH_MODE`와 `BACKEND_URL`이 설정돼 있지 않았다. 그래서 프론트는 목업 모드로 실행되고 있었다. 원격 Docker에서 알림이 동작한 것을 확인했어도, 실제 테스트 서버의 프론트까지 연결해 확인한 것은 아니었다.

## 팀원 PR 리뷰와 패키지 기준

백엔드 패키지는 회원 역할 단위로 나누기로 했다. 채팅처럼 여러 역할이 함께 사용하는 기능은 별도의 기능별 하위 패키지를 만들지 않고 `service/` 바로 아래에 두기로 했다. 이 기준에 맞춰 `service/chat/`의 파일을 옮겼다.

- 분석 그룹 GitHub 이슈 등록 PR 167을 검토했다.
- 공개 모집 상세 PR 158에는 역할별 패키지로 나누고 불필요한 `Public` 접두사를 줄이자는 의견을 남겼다.
- 모집 목록·검색 PR 172에는 검색 조건을 요청 DTO로 묶도록 제안했다. 수정 후 기존 오류 응답이 유지되는지도 확인했다.
- 구독 결제 PR 178에는 `my` 패키지 분리와 단순 지갑 조회의 쿼리 메서드 전환 의견을 남겼다. 복잡한 조회까지 긴 쿼리 메서드로 바꾸면 오히려 읽기 어려울 수 있다는 점도 검토했다.
- CD 실행과 배포 상태를 확인했다.

필드가 하나뿐인 DTO를 두는 이유와 `@Min`, 읽음 표시 계산 방식도 확인했다. SSE 용어는 저장소 밖의 `sse.md`에 별도로 정리했고 커밋하지 않았다.

# 배운 점 & 느낀 점

repository를 살펴보니 JOIN이 6개나 이어지는 메소드도 있었다. 지금 프로젝트에서 PostgreSQL을 사용하는 방식으로는 더 개선할 방법을 찾기 어려웠다. 이걸 어떻게 개선할 수 있을지 더 찾아봐야 할 것 같다.

SSE는 개념만 이해하고 있었는데, 이번에 각 용어와 실제 동작 과정을 이해하게 됐다. 생각보다 형식을 맞추는 것이 중요했다.

오늘은 백엔드 구조에서 자잘한 문제가 계속 나오고 있다는 걸 느꼈다. 각자 AI를 사용하면서 개발하다 보니 불필요한 키워드가 붙거나, DTO를 사용하지 않거나, 정한 기준과 다르게 폴더를 나누는 문제가 있었다. 그래서 코드를 직접 눈으로 일일이 확인했다. 내 코드에서도 같은 문제가 나왔다.

결국 사람이 직접 확인하는 과정은 필요하다는 걸 느꼈다. 그러면서도 이런 부분까지 자동화할 수 있을까 고민하게 됐다.
