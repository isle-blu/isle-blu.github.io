# 오늘의 상황

> 어제 정한 대로 **DB 연결 방식을 표준 구성으로 다시 짰고**, 개발 서버 배포 구성과 배포 문서까지 만들었다.

- DB 연결을 Spring Initializr 표준 구성(PostgreSQL + Docker Compose + Testcontainers)으로 바꿨다.
- 원격 Docker를 쓰는 내 환경에서 테스트가 안 돌아서, 원격 안에서 테스트를 돌리는 방법을 찾았다.
- develop에 push하면 개발 서버에 자동으로 배포되는 워크플로를 만들었다.
- 배포·DB 관련 내용을 문서로 정리했다.

# 오늘의 과정

## 오늘의 결정

- **상황** : 전에 올린 DB 설정 PR은 이미 승인을 받은 상태였다. 그런데 그 방식에는 아쉬운 점이 많았다.
    - 값이 빠지면 `Driver ... claims to not accept jdbcUrl, jdbc:postgresql://${DB_HOST}...`처럼 원인을 알기 어려운 오류가 났다.
    - 로컬·CI·`.env` **세 곳의 값을 맞춰야** 했다.
    - 5432 포트를 고정해서 다른 컨테이너와 충돌할 수 있었다.
    - 테스트하려면 DB를 먼저 띄워 둬야 했다.
- **무엇으로 바꿨나** : 승인받은 PR을 닫고, Initializr 표준 구성으로 새 PR을 올렸다.
- **왜**
    - **백엔드 테스트가 매우 간단해진다.** Spring이 DB까지 자동으로 띄워 주니까, 따로 DB를 준비할 필요가 없다.
    - **개발에서만 동작하는 설정**이라 배포된 서버에는 영향이 가지 않는다.
    - 승인을 받았어도 더 나은 구조가 보였으니까, 그대로 머지하는 것보다 지금 바꾸는 게 낫다고 봤다.

<br/>

## 바꾼 DB 연결 방식

> 환경마다 **누가 접속 정보를 넣어 주는지**가 다르다.

| 언제 | 어떻게 연결되나 |
| --- | --- |
| `bootRun` | `spring-boot-docker-compose`가 backend 폴더의 `compose.yaml`을 띄우고 접속 정보도 자동으로 연결 |
| 테스트·CI | Testcontainers가 `@ServiceConnection`으로 자동 연결. CI 러너에 Docker가 있어서 **CI 설정은 따로 필요 없다** |
| 배포 | `SPRING_DATASOURCE_*` 환경 변수만 사용 (relaxed binding) |

> 어떻게 설정 없이 연결되는 걸까?

- 핵심은 **`ConnectionDetails`** 빈이다. 이 빈이 있으면 `spring.datasource.url`보다 우선한다.
- Compose 지원과 `@ServiceConnection`은 둘 다 이 빈을 **자동으로 만들어 주는 장치**다.

> 같이 알게 된 것

- `ports: - '5432'` => 호스트 포트를 무작위로 잡는다. 실제 포트는 Spring이 `docker compose ps`로 읽어 온다. => 포트 충돌 걱정이 없다.
- `lifecycle-management: start-only` => 앱을 꺼도 DB는 켜 둔다.
- `developmentOnly` => `bootJar`와 이미지에 들어가지 않는다. 테스트에서는 `skip.in-tests=true`가 기본값이다.
- Testcontainers는 컨텍스트 캐시 덕분에 테스트 클래스들이 **컨테이너 하나를 같이 쓴다**. 비정상 종료로 남은 컨테이너는 Ryuk가 지운다.
- `bootTestRun`과 `TestBackendApplication` => 매번 빈 DB로 앱을 띄운다.

> 확인한 것

- 테스트 통과 (컨테이너 기동 2.2초)
- `bootRun`이 PostgreSQL 18.7에 연결됨
- `bootJar`에 Compose 지원과 Testcontainers가 빠진 것까지 확인

<br/>

## 원격 Docker에서 막힌 부분

> 맥에서 원격 Docker 컨텍스트로 `bootRun`을 하면 실패했다.

```
ReadinessTimeoutException: Readiness timeout of PT2M reached ...
IOException while connecting to port 44622 (Connection refused)
```

- 원격에 DB는 떴는데, **맥이 원격의 무작위 포트에 닿지 못했다.**

> 그래서 테스트를 원격 안에서 돌렸다.

- backend 폴더를 `rsync`로 원격에 복사했다.
- 원격에서 JDK 21 컨테이너에 `/var/run/docker.sock`을 마운트하고 `./gradlew test`를 돌렸다.
    - Testcontainers는 Docker 게이트웨이 `172.17.0.1`로 붙었다.
    - 컨테이너가 root로 돌아서 `build`, `.gradle`이 root 소유가 됐다.
    - Gradle 캐시 볼륨을 붙이니 두 번째 실행부터 빨라졌다.
- Testcontainers는 `ssh://` 주소를 바로 지원하지 않고, `application.yml`도 읽지 않는다. => Docker 위치는 `.testcontainers.properties`나 `DOCKER_HOST`로 정한다.
- 이건 내 환경의 문제라서 **저장소에는 넣지 않고 개인 설정으로** 풀었다.

## 개발 서버 배포 구성

> develop에 push → 검사 → GHCR에 이미지 build·push → SSH로 서버에서 pull 후 실행

- 이미지는 backend·frontend를 matrix로 나눠 만든다.
- 서버에서는 `compose pull` 후 `up -d --no-build`로 띄운다.

```
인터넷 → 호스트 nginx(HTTPS) → 127.0.0.1:TEAM_PORT → 팀 nginx
                                                        ├ /api/ → backend
                                                        └ 나머지 → frontend
```

> 공용 서버라서 신경 쓴 점

- 포트는 **하나만, `127.0.0.1`에만** 연다.
- `COMPOSE_PROJECT_NAME`을 쓰고 `container_name`은 두지 않는다. => 다른 팀과 이름이 겹치지 않게
- `docker image prune`에 `org.opencontainers.image.source` 라벨 필터를 걸어서 **우리 이미지만** 지운다.

> 작은 요령들

- 이미지 태그는 `sha-<7자리>`와 `latest`. => 되돌릴 때는 `IMAGE_TAG=sha-<이전 커밋>`으로 다시 띄운다.
- `DEPLOY_HOST` 시크릿이 없으면 배포 단계만 notice를 남기고 건너뛴다. 워크플로는 실패로 표시하지 않는다. => 시연 기간에 **배포를 끄는 스위치**로도 쓸 수 있다.
- 서드파티 액션은 태그 대신 커밋 SHA로 고정했다.
- compose의 `${VAR:?}`로 빠진 값을 바로 알려 준다.
- 배포 뒤에는 팀 포트에 `curl`로 최대 30초 동안 헬스체크한다.
- PostgreSQL 18부터 데이터 경로가 바뀌어서, 볼륨은 상위 폴더인 `/var/lib/postgresql`에 마운트했다.

> 비밀값은 어디에 두나

| 무엇 | 어디 |
| --- | --- |
| 서버 접속 정보 | GitHub 환경 `develop`의 Secrets |
| 앱 비밀값 | 서버의 `.env` |
| 웹훅 | 저장소 Secrets |

- PR은 서버 설정이 끝난 뒤에 올리기로 했다.

## 배포·DB 문서

- 브랜치 전략 : develop은 개발 서버에 자동 배포한다. main(운영, 나중에 클라우드)은 아직 배포하지 않는다.
- 사진 저장 방식으로 서버 디스크와 S3 호환 스토리지를 비교했다.
    - 제안 : 저장소를 **인터페이스 뒤에 숨기고**, 개발 서버는 Docker 볼륨, 운영은 객체 스토리지로 간다.
- 아직 정하지 않은 것
    - 외부 테스터용 서버
    - 스키마 관리 (`ddl-auto`냐 Flyway냐)
    - `SERVER_FORWARD_HEADERS_STRATEGY` (인증 작업 때 넣는다)
    - 모바일에서 HTTPS 확인하는 방법

# 배운 점 & 느낀 점

개발·테스트 환경을 표준에 맞게, 그리고 더 편한 방식으로 교체하기 위해 승인받은 PR을 머지하지 않고 닫았다. 처음 시도하는 방식이지만 Spring이 표준으로 안내하는 구성이고, 팀원 모두에게 공부가 되었으면 해서 표준 방식으로 바꾸기로 결정했다. 문서로 정리해 팀원들에게 설명해야 할 내용이 더 늘어났다.

프로젝트를 진행하면서 내가 더 나아지는 부분이 있을까, 계속 고민하게 되는 경우가 있다. 이번에 개선한 것도 있고 팀원들에게 알려 줄 것도 늘어나면서 아직 내가 배우고 나아지고 있다는 생각이 들어서 안심이 되었다. 남은 프로젝트 기간 동안에도 계속 발전해 나가고 싶다.
