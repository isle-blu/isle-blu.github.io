# 오늘의 상황

> 오늘은 프로젝트 발표와 결과물 제출이 있는 날이었다. 그래서 제출할 기술문서를 코드와 대조해 마무리하고, 발표에서 받을 질문을 준비했다.

제출물에 들어갈 문서라서 설명이 실제 구현과 어긋나면 안 됐다. 팀검토본 사본을 만들어 문서의 수치와 설명을 실제 코드·CI 기록과 하나씩 맞춰 봤다. 결제 담당 팀원의 수정 내용도 반영했다. 오후에는 발표에서 받을 만한 채팅 질문을 정리하다가 후속 이슈 6개를 등록했고, 저녁에는 API 캡처와 ERD를 다시 만들어 문서를 끝냈다.

# 오늘의 과정

## 기술문서의 설명을 코드와 대조했다

버전, 토큰 유효 기간, SSE 하트비트 주기와 연결 수 제한, 결제 중복 제한 시간 같은 수치는 코드와 맞았다. 틀린 건 주로 "무엇이 됐고 무엇이 안 됐는지"를 적은 부분이었다.

- **"미실행"으로 적힌 테스트 4건** => 인증 경쟁 상황, 결제 동시성, 채팅 순번, AI 응답 검증이 실제로는 CI에서 이미 통과돼 있었다.
- **"스케줄러가 남아 있습니다"** => "이미 있다"로 읽혔다. 실제로는 보상 지급용 스케줄러가 없고, 있는 건 탈퇴 정리와 채팅 하트비트뿐이었다.
- **분석 서버 제약(읽기 전용, 권한 제거, 메모리 512MB)** => 운영용 Compose 설정에만 있는 내용이라 그렇게 밝혔다.
- **문서 기준 커밋 이후의 변경** => AI 분석 묶기 기준과 신고·제재 화면 연결이 바뀌어 있었다. 문서 기준은 그대로 두고 이후 변경은 따로 표시했다.
- **ERD** => 결제 시도와 제재 테이블이 빠져 있어서, 엔티티 코드의 외래 키를 기준으로 다시 그렸다.

## 테스트 근거는 이름이 아니라 시나리오로 확인했다

> 테스트가 있다는 것, 실행됐다는 것, 무엇을 검증했는지는 각각 따로 확인해야 한다.

"탈퇴·출금 동시성 2건"이라는 행을 시나리오 번호로 대조해 보니 절반만 맞았다.

- 탈퇴와 출금 신청 경합 => 출금과 관련 있음
- 회원 정보 파기와 되돌리기 경합 => 출금과 관계없음

정작 출금 정합성을 직접 검증하는 테스트는 빠져 있었다.

- 동시에 출금을 신청해도 잔액을 넘지 않는지
- 운영자가 같은 출금 요청을 동시에 처리해도 한쪽만 적용되는지

관계없는 1건을 빼고 출금 테스트를 근거에 넣었다. 결제·출금 행만 로컬 실행 결과가 근거였는데, 다른 행처럼 CI 결과로 통일했다. 새벽에 돌린 E2E 결과에는 실행 시각과 기준 커밋을 적어서, 오늘 새로 실행한 것처럼 보이지 않게 했다.

트러블슈팅 절은 따로 만들지 않았다. 5장이 이미 "문제 → 해결 → 감수한 점 → 근거" 구조라서, 실제로 겪고 고친 경위를 해당 절에 한 줄씩 넣는 쪽을 택했다. 리뷰에서 늦게 도착한 토큰 갱신 응답이 로그인 상태를 되살리던 문제, 결제와 운영자의 구독 부여가 서로 다른 잠금을 쓰던 문제 같은 것들이다.

## Swagger는 보안 설정만 보고 판단할 수 없었다

> 백엔드에서 경로를 허용해도, 외부 요청이 그 백엔드까지 도달해야 열린다.

Spring Security 설정에서는 Swagger 경로를 허용하고 있어서, 처음에는 문서에 "백엔드의 Swagger 주소에서 볼 수 있다"고 적었다. 그런데 우리 구조는 이렇다.

- 백엔드 컨테이너는 외부에 포트를 열지 않음
- nginx는 채팅 SSE 경로를 뺀 모든 요청을 Next.js로 보냄

테스트 서버에서 Swagger 주소를 직접 요청해 보니 Next.js의 404가 돌아왔다. 문장을 "테스트 서버와 Compose 실행에서는 열리지 않는다"로 고쳤다.

## API 응답 캡처는 브라우저에서 찍을 수 없었다

API 요청·응답 캡처도 처음에는 브라우저 Network 탭으로 찍으면 된다고 생각했다. 그런데 우리 프론트는 Next.js가 서버 쪽에서 백엔드를 부르는 BFF 구조라서, 브라우저에는 백엔드의 JSON 응답이 보이지 않는다.

그래서 테스트 서버의 프론트 컨테이너 안에서 `wget`으로 백엔드를 직접 불렀다. 여기서 두 번 막혔다.

1. **404** => 경로가 틀린 줄 알았는데, 목록의 첫 ID를 옮겨 적다가 숫자 하나를 잘못 적은 거였다. busybox `wget`은 404일 때 본문을 보여 주지 않아서 화면만으로는 원인을 알기 어려웠다. 실행한 명령과 출력을 나란히 놓고 대조해서 찾았다.
2. **한글이 `\uXXXX`로 출력** => `python3 -m json.tool`은 기본값으로 한글을 이스케이프한다. 그대로 보려면 `--no-ensure-ascii`가 필요했다.

이스케이프된 캡처는 그대로 쓰고 캡션에 이유를 적었다. 호출 시각은 응답 헤더의 `Date` 값으로 확인하고, 그 시각에 배포돼 있던 커밋을 함께 적었다.

## Word가 앞선 수정을 덮어썼다

스크립트로 사본을 고치는 동안 Word에서 같은 파일을 열어 둔 상태였다. Word 저장본이 처음 수정본을 연 상태에서 저장되는 바람에, 그 뒤에 넣은 실행 준비 표와 Swagger 문장 수정이 사라졌다. 제목 하나가 앞 문단 끝에 붙어 버린 것도 있었다.

두 수정을 다시 넣고, 그다음부터는 덮어쓰기 전에 Word 잠금 파일(`~$…`)과 파일 수정 시각을 먼저 확인했다.

## 열린 이슈가 곧 남은 일은 아니었다

개발 계획서를 정리하면서 열린 이슈 12개를 코드와 PR 기록으로 확인했다. 그중 3개는 이미 구현돼 있었다. PR 본문에 "남음: 없음"이라고 적혀 있는데 이슈만 열려 있던 경우도 있었다. 나머지는 Flyway 도입, 테스트 서버 프로필, 이미지 업로드 제한처럼 실제로 남은 일이었다.

## 채팅에서 SSE를 고른 이유

발표에서 나올 만한 채팅 질문을 정리했다.

- **왜 WebSocket이 아니라 SSE인가** => 우리 프로젝트에서 WebSocket은 오버엔지니어링이다. 보내기는 HTTP POST로 하고, 서버 → 브라우저는 "새 메시지 왔다" 알림만 보내면 된다. SSE는 일반 HTTP라 nginx → Next.js → 백엔드 구조를 그대로 탈 수 있고, 끊긴 연결은 브라우저가 다시 붙인다.
- **끊기면 메시지를 놓치나** => 메시지는 DB에 저장한다. 다시 연결되면 마지막 순번 이후를 REST로 다시 가져온다.
- **동시에 보내면** => 방 행을 잠가서 순번을 매긴다. 두 사람이 동시에 10개씩 보내도 순번이 1~20으로 매겨지는 테스트로 확인했다.
- **저장에 실패했는데 알림이 가면** => 커밋된 뒤에만 알림을 보낸다.
- **서버를 늘리면** => 지금은 SSE 연결이 서버 한 대의 메모리에 있다. 늘리려면 Redis pub/sub이나 PostgreSQL `LISTEN/NOTIFY`가 필요하다.

처음에는 "채팅 신고·차단은 없다"고 답했는데 틀렸다. 채팅 신고와 운영자의 채팅 정지가 이미 들어가 있었다. 신고·제재 작업 이후 갱신되지 않은 채팅 문서만 믿고 답한 게 원인이었다. 스팸 질문에는 신고와 제재로 답하되, 운영자가 처리하기 전까지는 막지 못한다는 한계도 같이 말하기로 했다.

이 내용을 채팅 README에 반영하고, 후속 기능은 이슈 6개로 등록했다.

- 사진·파일 보내기
- 메시지 수정·삭제
- 브라우저 알림
- 상대 차단
- 전송 횟수 제한
- 여러 서버 사이의 SSE 알림 전달

# 배운 점 & 느낀 점

오늘은 응용 프로젝트를 마무리하는 날이었다. 그래서 개발보다 발표자를 위해 피피티를 다듬고 발표 연습을 피드백하고, 문서들을 작성하는 데 집중했다. 이런 작업들을 하다보니 뭔가 마무리된다는 느낌을 받으면서도 아직 부족하고 개선하고 싶은 부분이 남아서 아쉬움도 들었다. 그래도 발표에서 좋은 구성이었다는 평을 들어서 발표 담당 팀원을 열심히 돕고 피드백한 보람이 있었다.

내일부터는 새로운 프로젝트의 시작이다. 어떤 팀이 될지, 어떤 기획을 하게 될 지 아직 모르지만 응용 프로젝트 때처럼 좋은 팀원을 만났으면 한다.
