# 오늘의 과정

## 로그인/회원가입 페이지 구현

로그인/회원가입 프론트엔드 페이지를 구현하면서, 이 둘을 브랜치를 나눠서 개발해야 할지 고민했다.

## 오늘의 결정 : 하나의 브랜치에서 개발하기

- **상황** : 로그인과 회원가입 페이지를 브랜치를 나눠서 개발해야 할지 고민했다.
- **무엇으로 바꿨나** : 하나의 브랜치에서 개발하기로 했다.
- **왜** : 서로 연동되는 부분이 많고, 공통으로 쓰는 것도 많아서.

이게 올바른 결정이었는지는 아직 고민이다.

## 채팅 기능 PR 리뷰

팀원이 올린 채팅 기능 PR을 리뷰했다. 수정 요청 4건과 디자인 제안 1건을 남겼다.

가장 급했던 건 빌드가 아예 안 되는 문제였다. 공용 함수 하나에 닫는 중괄호가 빠져 있어서 린트, 타입 검사, 빌드가 모두 실패했다.

나머지는 기능을 직접 돌려 보면서 찾은 문제들이었다.

- **메시지 작성자** : 메시지에 누가 보냈는지가 저장되지 않아서, 시연 회원을 바꾸면 다른 사람이 보낸 메시지도 전부 "나"의 메시지로 보였다.
- **검색 필터** : 검색이 300ms 늦게 실행되는데, 그때 입력 당시의 필터 값을 쓰고 있었다. 그래서 검색어를 치자마자 탭이나 정렬을 바꾸면 이전 상태로 되돌아갔다.
- **푸터** : 채팅에서 홈으로 가면 푸터가 사라졌다. `cacheComponents` 때문에 이전 채팅 화면이 숨겨진 채로 남아 있었고, 푸터를 숨기는 CSS가 그걸 감지한 거였다. 새로고침하면 다시 나타났다.

디자인 쪽으로는 역할 배지를 제안했다. 강조색을 새로 쓰지 않고, 테스터는 회색 바탕, 개발자는 테두리만 있는 배지로 구분하는 방식이다.

문제마다 임시 복사본이나 브라우저에서 직접 재현해 보고 코멘트를 남겼다.

  → 줄바꿈이 안 되게 막고, 필요 없는 메뉴가 지워지면서 괜찮아졌다.

# 배운 점 & 느낀 점

## 브랜치를 나누지 않는다면 커밋이라도

로그인과 회원가입을 하나의 브랜치에서 개발하기로 했으니, 커밋이라도 나눠서 정리하는 게 좋겠다고 생각했다. 그래야 리뷰어가 커밋 단위로 따라가면서 볼 수 있으니까.

그런데 공통 부분이 또 발목을 잡았다. AI로 개발하다 보니 공통 부분을 하나로 통합해 버린 것이다. 아직 push 전이라 커밋을 다시 나눌 수 있었다.

앞으로는 이 부분을 더 주의해야겠다.
