# 세션 인증 VS JWT 

> 세션 방식 : 로그인 정보를 서버가 저장한다. JWT 방식 : 클라이언트가 토큰을 가지고 있다가 요청마다 보낸다.

- 세션 방식에서는 브라우저가 세션 ID를 쿠키로 보낸다. 서버가 한 대라면 서버에 저장된 로그인 정보를 바로 찾을 수 있다. 하지만 서버가 여러 대라면? => 서버끼리 세션을 공유할 방법이 필요하다.
- JWT 방식에서는 요청을 받은 서버가 토큰을 확인한다. 서버가 이전 요청의 로그인 상태를 기억하지 않아도 되므로 **Stateless** 방식이라고 한다.

서버가 여러 대라는 이유만으로 JWT를 사용해야 하는 것은 아니다. 세션 저장소를 공유하는 방법도 있다.

이전에 만든 `JwtAuthenticationFilter`는 들어온 토큰을 검사하는 역할이었다. 토큰이 맞다면 아이디와 권한을 `Authentication`으로 만들어 `SecurityContextHolder`에 넣는다. => Spring Security가 그 요청을 로그인한 사용자의 요청으로 볼 수 있게 된다.

그런데 첫 로그인 때는 아직 토큰이 없다. 그럼 이 토큰은 어디서 만들어 줄까? 오늘 배운 로그인 API가 아이디와 비밀번호를 확인하고 JWT를 발급한다.

# JWT 로그인 API 실습

> 로그인 정보를 확인하고 JWT를 발급하는 API

`POST /api/auth/login`으로 아이디와 비밀번호가 들어온다. 인증에 성공하면 Access Token을 돌려준다. 이 과정을 나눠 보면 다음과 같다.

1. `AuthController`가 아이디와 비밀번호를 받는다.
2. `AuthService`가 `AuthenticationManager`에 인증을 요청한다.
3. 인증에 성공하면 `JwtProvider`로 Access Token을 만든다.
4. 발급한 토큰을 `LoginResponse`에 담아 반환한다.

## 로그인 요청과 응답

먼저 사용자가 보낸 아이디와 비밀번호를 `LoginRequest`에 담는다.

```java
package com.ncafe.backend.dto.auth;

import lombok.Data;
import lombok.NoArgsConstructor;

@Data
@NoArgsConstructor
public class LoginRequest {
    private String username;
    private String password;
}
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

응답은 `LoginResponse`로 보낸다. 토큰 종류는 `Bearer`로 정해두었으니, 생성자에는 발급한 Access Token만 넣는다.

```java
package com.ncafe.backend.dto.auth;

import lombok.Data;
import lombok.NoArgsConstructor;

@Data
@NoArgsConstructor
public class LoginResponse {
    private String accessToken;
    private String tokenType = "Bearer";

    public LoginResponse(String accessToken) {
        this.accessToken = accessToken;
    }
}
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

여기서 Builder 패턴도 배웠다. 필드가 여러 개라면 이름을 보며 값을 넣을 수 있어 편리하다. 다만 이번 `LoginResponse`는 전달할 값이 토큰 하나라 생성자를 사용했다.

<br/>

## 인증과 토큰 발급: `AuthService`

`AuthService`가 아이디와 비밀번호를 받아 직접 비교하는 것은 아니다. Spring Security의 `AuthenticationManager`에게 인증을 맡긴다.

1. `UserDetailsService`가 아이디에 맞는 사용자를 찾는다.
2. `PasswordEncoder`가 입력한 비밀번호와 저장된 해시를 비교한다.
3. 맞는 사용자라면 `Authentication`에 아이디와 권한이 담겨 돌아온다.
4. 이 정보를 `JwtProvider`에 넘겨 Access Token을 만든다.

```java
@Service
public class AuthService {
    private final AuthenticationManager authenticationManager;
    private final JwtProvider jwtProvider;

    public AuthService(AuthenticationManager authenticationManager, JwtProvider jwtProvider) {
        this.authenticationManager = authenticationManager;
        this.jwtProvider = jwtProvider;
    }

    public LoginResponse login(LoginRequest request) {
        Authentication authentication = authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(
                request.getUsername(), request.getPassword()
            )
        );

        String username = authentication.getName();
        String role = authentication.getAuthorities().stream()
            .findFirst()
            .map(GrantedAuthority::getAuthority)
            .orElse("ROLE_USER");

        String accessToken = jwtProvider.createAccessToken(username, role);
        return new LoginResponse(accessToken);
    }
}
```

*코드 출처: [뉴렉처](https://newlecture.com/) 

아이디나 비밀번호가 맞지 않으면 인증이 실패하므로 토큰을 만들지 않는다.

<br/>

## 요청을 받는 `AuthController`

컨트롤러는 로그인 요청을 받는 곳이다. `@RequestBody`가 요청 본문의 JSON을 `LoginRequest`로 바꿔준다. 그 객체를 서비스에 넘기고 결과를 응답한다.

```java
@RestController
@RequestMapping("/api/auth")
public class AuthController {
    private final AuthService authService;

    public AuthController(AuthService authService) {
        this.authService = authService;
    }

    @PostMapping("/login")
    public ResponseEntity<LoginResponse> login(@RequestBody LoginRequest request) {
        return ResponseEntity.ok(authService.login(request));
    }
}
```

*코드 출처: [뉴렉처](https://newlecture.com/) 

로그인 API는 토큰이 없는 사람이 들어오는 곳이다. 그래서 `/api/auth/**`를 `permitAll()`로 열어두어야 한다. 응답은 `ResponseEntity.ok(...)`로 `200 OK`와 함께 돌려준다.

# 로그인과 권한 확인 실습

DB에 회원 정보를 연결하기 전이라, 실습에서는 메모리에 임시 계정을 넣어 로그인 과정을 확인했다. `USER`와 `ADMIN`을 따로 만들면 역할에 따른 접근도 비교할 수 있다. 임시 계정의 비밀번호도 `PasswordEncoder`로 해시해 넣는다.

```java
@Bean
public AuthenticationManager authenticationManager(
        AuthenticationConfiguration configuration) throws Exception {
    return configuration.getAuthenticationManager();
}

@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

@Bean
public UserDetailsService userDetailsService(PasswordEncoder encoder) {
    UserDetails user = User.builder()
        .username("newlec")
        .password(encoder.encode("123"))
        .roles("USER")
        .build();

    UserDetails admin = User.builder()
        .username("admin")
        .password(encoder.encode("123"))
        .roles("ADMIN")
        .build();

    return new InMemoryUserDetailsManager(user, admin);
}
```

*코드 출처: [뉴렉처](https://newlecture.com/) (SecurityConfig의 관련 메서드 발췌, import 생략)*

로그인 후에는 URL마다 접근할 수 있는 권한도 달라야 한다.

- `/api/auth/**` : 로그인 전에도 접근할 수 있다.
- `/api/admin/**` : `ADMIN` 권한이 필요하다.
- 그 외 경로 : 로그인한 사용자만 접근할 수 있다.

Postman에서는 먼저 로그인 API로 토큰을 발급받는다. 그다음 API 요청의 `Authorization` 헤더에 `Bearer <토큰>`을 넣어 확인한다.

- 토큰 없이 `GET /api/menus` → 인증이 필요하므로 거부
- 일반 사용자 토큰으로 `GET /api/menus` → 접근 가능
- 일반 사용자 토큰으로 `GET /api/admin/menus` → 권한이 없어 거부
- 관리자 토큰으로 `GET /api/admin/menus` → 접근 가능

토큰을 확인해 **누구인지 알아내는 것**이 인증이고, 그 사용자가 **해당 URL에 접근할 수 있는지 판단하는 것**이 인가라는 차이도 다시 확인했다.

> 로그인에 실패했다면? 토큰을 발급하지 않고, 서버 오류 대신 `401 Unauthorized`를 응답하도록 처리해야 한다.

# BFF에서 토큰은 어디에 둘까?

어제 배운 BFF 구조에서는 브라우저가 내부 Spring Boot API를 바로 호출하지 않았다. 로그인도 **브라우저 → Next.js 서버 → Spring Boot API** 순서로 요청할 수 있다.

토큰을 브라우저의 JavaScript가 읽을 수 있는 곳에 두면 노출될 수 있다. 프론트엔드 서버가 토큰을 관리한다면 브라우저에는 보호된 쿠키나 세션을 사용할 수 있다. 결국 **누가 토큰을 보관하고 내부 API 요청에 붙일지**를 먼저 정해야 한다.
