# 오늘의 상황

> 오늘은 정원 우체통의 AI 엽서 생성 계획을 쓰고, 저녁에는 nginx·Java 취약점에 대응했다.

오전에는 어제 정한 컬럼명 네이밍 전략을 커뮤니티 엔티티에도 적용해서 병합했다. 그다음 일기로 AI 엽서를 만드는 기능을 개발하기 전에, 범위와 비용, 제한을 먼저 정해야 해서 계획 문서를 썼다. 저녁에는 nginx에 심각한 취약점이 나와서 팀 서버가 노출됐는지부터 확인해야 했다.

# 오늘의 과정

## 커뮤니티 엔티티 컬럼명 정리

> 어제 정한 snake_case 네이밍 전략을 커뮤니티 엔티티에도 적용했다.

- 필드 이름과 같은 `@Column(name = ...)` 6개를 지웠다.
- 다른 옵션이 없던 `deleted_at`은 `@Column`을 통째로 지웠다.
- `@Table` 인덱스의 `columnList`는 그대로 뒀다. => 여기에는 **네이밍 전략이 적용되지 않아서** DB 컬럼 이름을 직접 적어야 한다.
- 커뮤니티 테스트 45개가 통과했다. 컬럼 이름을 직접 쓰는 native SQL 테스트도 들어 있다.

<br/>

## 정원 우체통 AI 엽서 생성 계획

> 정원 모드 반려동물의 일기 하나를 골라 동의를 받고, AI 수채화 엽서를 비동기로 만든다.

- 시나리오 11개와 6단계 작업 순서로 계획 문서를 썼다.
- 범위는 생성, 목록, 상세, 이미지, 삭제까지다.
> 리뷰를 받고 고친 것

- 이슈와 계획의 범위가 다르다는 지적을 받았다. => 이슈 본문도 계획에 맞췄다.
- 제한이 동시 요청과 삭제에도 유지되는지 정의하라는 의견을 받았다. => 동시 요청은 그날 횟수 행을 잠가서 한 건씩 처리한다.
- 반려동물 삭제와 엽서 생성이 겹치는 경합을 지적받았다. => DB 외래 키가 마지막으로 막는다. 다이어리가 같은 경합을 처리하는 방식을 따랐다.

> 비교 없이 정한 것

- 요청마다 `consent: true`를 받는다. => 일기 내용이 외부 서비스로 나가니까.
- 비용은 팀 통장에서 내고, 결제와 키 발급은 내가 한다.
- 이미지는 1K PNG로 고정한다. => 해상도에 따라 비용이 달라진다. (1K 약 $0.067, 2K 약 $0.10)
- 하루 제한 값(회원당 5장, 전체 100장)은 설정으로 뺐다. => 결제 상황에 따라 늘릴 수도 있으니까, 코드 수정 없이 바꾼다.
- 생성은 비동기(202 + 스케줄러)로 한다. => 외부 호출이 최대 60초까지 걸릴 수 있다. 미디어 작업과 같은 방식이다.
- 엽서가 있으면 반려동물을 지울 수 없다. 일기를 모두 지워도 엽서는 남을 수 있으니까. => 기존의 "기록이 있으면 삭제를 막는다" 조건에 엽서를 더했다.
- 만드는 중인 엽서도 지울 수 있다. => 작업이 끝났을 때 엽서가 없으면 받은 그림을 저장하지 않는다.
- 남의 반려동물은 403, 다른 반려동물의 엽서는 404다. 반려동물·다이어리와 같은 기준이다.

## nginx·Java 취약점 대응

> nginx에 HTTP/2 메모리 손상으로 원격 코드 실행까지 가능한 취약점(CVSS 9.2)이 나왔다. 우리 서버는 노출됐을까?

- 팀 nginx(`stable-alpine`)는 태그를 고정하지 않아서, 배포할 때 pull로 최신 버전을 받는다. => 오늘 배포에서 패치 버전(1.30.7)을 받은 것으로 봤다. 다만 서버에서 버전을 직접 확인하지는 않았다.
- 호스트 nginx는 1.28.3(Ubuntu)이고 `http2 on` 상태라 **노출된 것으로 판단했다.**
- Ubuntu 패키지는 버전 숫자는 그대로 두고 패치만 덧붙인다. => 패치 여부는 버전이 아니라 changelog로 확인해야 한다.
- 비밀값은 재발급하기로 했다. `POSTGRES_PASSWORD`는 `.env`만 바꾸면 안 되고, DB 쪽 비밀번호도 같이 바꿔야 한다.

> Java는?

- Spring Boot 4.1.2는 올해 4월 공지의 대상 버전(4.0.0~4.0.5)이 아니다.
- JDK 21.0.13은 10월 정기 패치는 들어갔지만, 그 뒤에 나온 긴급 패치(인증서 신뢰 문제)는 아직 안 들어간 것으로 보였다.

<br/>

## 팀원 PR 리뷰

- **지도 저장소 예외 → 503** : DB 접근 예외를 모두 503으로 바꾸면, 무결성 오류나 잘못된 JPA 호출까지 "다시 시도하세요"가 된다. => **일시적 장애만 503**으로 하고, 나머지는 원인을 남겨 500으로 하자고 했다. PostgreSQL 잠금 타임아웃도 503에 넣자고 하고 승인했다.
- **날짜별 산책 조회** : 날짜 변환이 `2026-11-17+09:00`, `+10000-01-01`까지 받아들인다. => 원본 문자열이 `YYYY-MM-DD`인지 먼저 검사하자고 했다. 산책과 좌표를 따로 조회하면 그 사이에 커밋된 좌표 때문에 상태가 틀릴 수 있어서, 같은 스냅샷에서 읽자고 했다.
- **소셜 계정 연결·해제 계획** : 연결 콜백이 지금 로그인한 회원이 시작한 요청인지 state로 검증하기, DB 이전은 새 앱이 요청을 받기 전에 끝내고 복구 절차 적기, 컨트롤러는 도메인당 하나로 하기를 의견으로 남겼다.
- **관리자 신고 목록 계약** : 기본 필터(대기 상태)를 검증하려면 다른 상태의 신고도 데이터에 섞어야 한다고 짚고 승인했다.
- **다이어리·질문 분리** : 4번 왕복하고 승인했다. 이전 데이터를 남긴 채 같은 localStorage에 새 데이터를 쓰면 5 MiB 한도에 걸려 기존 기록도 못 여는 문제가 가장 컸다. 활성 질문이 3개 이상이면 앞의 2개만 배정되는 것, 공백 답변이 질문을 진행시키는 것, 시나리오 번호 중복도 짚었다.
- **핀 조회 쿼리 검증** : 원본 쿼리를 직접 검증하는 조건을 구조 문서에 적고, 위도·경도 범위와 문구는 산책 API와 공통 상수로 쓰자고 했다.

## 오늘의 결정

### 1. 이번 엽서는 일기 글만으로 그리기

- **상황** : 기억 뽑기, 참조 사진, 질문 답변, 관리자 판매 연계까지 이번에 넣을지 정해야 했다.
- **무엇으로 바꿨나** : 나는 이번에는 일기 글만으로 그리고, 나머지는 후속 이슈로 빼기로 했다.
- **왜** : 질문 답변과 프로필 사진 정책이 아직 없고, 기억 뽑기는 화면 기능이니까.

### 2. 사진만 있는 일기는 따로 후속 이슈로

- **상황** : 글 없이 사진만 있는 일기도 엽서를 만들 수 있게 할지 정해야 했다.
- **무엇으로 바꿨나** : 이번에는 막고, 나중에 가능하게 하자고 내가 제안해서 후속 이슈를 따로 만들었다.
- **왜** : 이번에는 글로 그림을 만드니까. 나중에 풀 때도 API 형식은 그대로 두고, 일기 내용만 비울 수 있게 하면 된다.
    - 프로필 사진 작업과 같은 이슈로 묶으면 같이 늦어지니까 후속 항목을 둘로 나눴다.

### 3. 다시 시도 API는 만들지 않기

- **상황** : 처음 설계는 실패한 엽서를 같은 엽서로 다시 시도하고, 3번까지 허용하는 API였다.
- **무엇으로 바꿨나** : 다시 시도 API를 뺐다. 자동 재시도와 실패 안내는 화면과 함께 후속 이슈에서 설계한다.
- **왜** : 비용과 구현만 보고 사용자 경험은 보지 않은 설계였다. 나는 사용자 편의가 아니라 개발자 편의만 본 것 같다고 판단했다.
    - 서버 탓인 실패를 사용자가 직접 눌러서 처리하게 된다.
    - "3번까지" 같은 서버 사정이 사용자에게 드러난다.

### 4. 그림은 외부 API(Gemini)로 만들기

외부 API 없이 하는 방법을 먼저 검토했다.

| 방법 | 문제 |
| --- | --- |
| 오픈 모델을 서버에서 직접 실행 | 공용 개발 서버에 부담이 크다. (CPU로 한 장에 수십 초, 메모리 4~8GB) |
| 미리 그린 그림 | 매번 새 그림이 아니다. |
| 사진 필터 | 사진 없는 일기에 쓸 수 없다. |

- **상황** : 일기로 수채화 엽서를 만들 방법을 정해야 했다.
- **무엇으로 바꿨나** : 나는 "일단 외부 api로 하자"고 정했다. 외부 후보 4개 중에서는 Gemini 이미지 모델을 쓴다.
- **왜** : Gemini는 화풍 지정에 강하고, 참조 사진을 쓰는 후속 이슈에도 그대로 이어진다.

### 5. 유료 등급 키만 쓰기

- **상황** : Gemini API는 무료 등급과 유료 등급이 있다.
- **무엇으로 바꿨나** : 유료 등급 키만 쓴다.
- **왜** : 무료 등급은 보낸 내용을 서비스 개선에 쓸 수 있다. => 사용자의 일기를 그 조건으로 보낼 수는 없다.

### 6. 하루 제한은 서버에서 막기

- **상황** : 프론트 데모에 하루 5장 제한이 있고, 결제에는 예산 알림도 있다.
- **무엇으로 바꿨나** : 서버에서 회원당 5장, 팀 전체 100장으로 막는다.
- **왜** : 둘 다 실제 비용을 막지 못한다.
    - 데모는 브라우저 저장소만 본다.
    - 예산 알림은 알림만 보낼 뿐 요청을 막지 않는다.
    - 전체 상한은 키가 유출되거나 버그로 요청이 몰릴 때를 대비한다.

### 7. 전체 상한을 넘으면 503이 아니라 409

- **상황** : 팀 전체 상한을 넘었을 때 돌려줄 상태 코드를 정해야 했다. 처음에는 AI가 503을 추천했다.
- **무엇으로 바꿨나** : 409로 정했다.
- **왜** : 지금 공통 예외에서 503은 저장소 장애를 뜻해서 의미가 맞지 않는다. => 다음 날이면 풀리는 **상태 충돌**로 봤다.

### 8. 횟수는 엽서와 따로 세기

- **상황** : 하루 횟수를 엽서 행으로 셀지, 따로 셀지 정해야 했다.
- **무엇으로 바꿨나** : 따로 센다. 엽서를 지워도 횟수는 돌려주지 않는다.
- **왜** : 엽서를 지우고 다시 만드는 식으로 제한을 피할 수 있으니까.

### 9. 실패하면 회원당 횟수만 돌려주기

- **상황** : 다시 시도 API를 뺐으니, 생성이 실패했을 때 횟수를 어떻게 할지 정해야 했다.
- **무엇으로 바꿨나** : 회원당 횟수는 돌려주고, 전체 횟수는 돌려주지 않는다.
- **왜** :
    - 서버나 Gemini 탓인 실패로 사용자가 제한을 잃으면 안 되니까.
    - 전체 횟수는 실제로 Gemini를 부른 횟수다. 시간 초과여도 이미 과금됐을 수 있다.

### 10. 기억 뽑기 API(`/draw`)는 만들지 않기

- **상황** : 계획에 `GET /postcards/draw`가 있었다. 나는 "url에 굳이 넣을 필요는 없어 보이는데"라고 짚었다.
- **무엇으로 바꿨나** : 서버 API를 없애고, 프론트가 목록 API를 `size=1`로 불러 전체 개수를 받고 무작위 page를 고른다.
- **왜** :
    - draw는 동사라서 자원 중심 경로 규칙에 맞지 않는다.
    - 기억 뽑기는 엽서 기능이 아니라 "다이어리에서 하나 고르기"다.
    - 미리 보면서 다시 뽑아도 제한과 비용을 쓰지 않는다.

### 11. 도메인 이름은 card가 아니라 postcard

- **상황** : 나는 도메인 이름으로 "card는 어색한가?" 하고 물었다.
- **무엇으로 바꿨나** : postcard로 정했다.
- **왜** : card는 UI 카드 컴포넌트나 결제 카드와 헷갈린다. 프론트 데모의 타입 이름과도 같다.

### 12. 요청할 때 일기 내용을 엽서에 복사하기

- **상황** : 생성이 끝나기 전에 일기가 고쳐지거나 지워질 수 있다.
- **무엇으로 바꿨나** : 요청할 때 일기 내용을 엽서에 복사한다.
- **왜** : 그래야 요청한 내용 그대로 엽서를 만들 수 있다. 일기와 엽서의 생명주기도 묶이지 않는다.

### 13. 원본은 `recordId` 대신 `source: {kind, id}`로

- **상황** : 나는 엽서의 원본을 `recordId` 하나로 두는 게 맞는지 물었다. 그래서 pull로 확인해 보니, 팀원 PR에서 일기와 질문 답변이 나뉘고 일기 ID 이름도 통일돼 있었다.
- **무엇으로 바꿨나** : 원본을 종류와 ID로 나눠 둔다.
- **왜** : 일기 ID와 질문 답변 ID가 섞이지 않게 한다. 프론트 모델과 이름도 맞춘다.

### 14. 호스트 nginx 대신 팀 서비스를 내리기

- **상황** : 노출된 호스트 nginx는 우리가 직접 다룰 수 없었다.
- **무엇으로 바꿨나** : 팀 서비스를 내리고, `.env`를 내 PC로 옮겨 자동 배포를 막기로 했다.
    - 순서는 `down`(`-v` 없이, 데이터 볼륨은 남긴다) → `.env` 옮기기다.
- **왜** :
    - `.env`가 없으면 자동 배포가 시작 단계에서 멈춘다.
    - `.env`를 먼저 지우면 compose 명령 자체가 실패하니까 순서가 중요하다.
    - `stop`이 아니라 `down`을 쓴 건, 멈춘 컨테이너에도 환경변수가 남아 `docker inspect`로 보이기 때문이다.
