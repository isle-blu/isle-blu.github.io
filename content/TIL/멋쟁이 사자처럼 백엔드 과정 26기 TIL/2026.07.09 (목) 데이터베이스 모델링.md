# 등장 배경

## 데이터베이스 등장 이전

- 파일 시스템 기반 데이터 관리 사용
- 프로그램마다 따로 데이터 파일을 가짐 ex) 은행 시스템 : 고객 관리 프로그램 - 고객 정보 데이터, 계좌 관리 프로그램 - 계좌 정보 데이터 -> 각 프로그램이 중복으로 가지는 데이터 발생 -> 실시간으로 동기화되지 않아 프로그램 별로 데이터 내용에 차이가 생김  
    =>`데이터 결함` 문제 발생

## 데이터베이스의 등장

- `데이터 결함` 문제를 해결하기 위해 등장
- 시스템 내의 프로그램 들의 데이터를 한 곳에 통합
- 시스템의 공공 자산으로써 데이터 관리
- 실시간 변경을 반영 => 데이터의 중복성을 없앰, 데이터 결함 제거 => 이러한 특장을 `무결성`이라고 함.

## 데이터베이스 등장 시 직면한 문제

데이터베이스는 동시성, 성능, 보안 문제를 해결해야했다. => 관리 시스템이라는 중재자를 거쳐서 접근하고, SQL이라는 명령어를 통해서만 소통하는 구조를 통해 해결

### SQL

> 데이터베이스 관리 시스템과 소통을 위해 사용하는 명령어

- DDL :
    - CREATE
    - ALTER
    - DROP
- DML :
    - SELECT
    - INSERT
    - UPDATE
    - DELETE
- DCL :
    - GRANT
    - REVOKE

# 데이터베이스 모델링

> 현실의 우리(역할자)가 할 행위와 행위에 대한 흐름(프로세스)를 찾고 이중 어떤 것을 데이터베이스로 설계하는 과정

- 시스템에는 저장해야 할 데이터가 있다. 이것은 우리가 일상적으로 속해 있는 시스템에도 마찬가지이다.
- 여기서 데이터로 저장하는 것은 시스템에서 해당 **데이터의 관리자(업무자가) 저장하기로 결정한 것**이다.
- 무엇을 저장할 지 = 어떤 행위의 내역을 기록할 지

## 모델링 3단계

### 1. Concept Design

> 현실 세계의 비즈니스를 분석해 데이터베이스에 저장할 Entity, 속성, 행위(관계) 찾아내고 정의하는 단계 여기서 업무자가 저장하겠다고 결정한 것들이 데이터베이스로 저장되게 된다.

- Entity : 데이터로 저장될 대상
    - `Key Entity` : 현실 세계의 행위의 주체와 대상을 나타내는 엔티티 ex) 사용자, 상품, 부서, 창고
    - `관계 / 행위(Relationship / Action) Entity` : Key Entity에 해당하는 존재들의 행위와 상호작용, 관계를 나타내는 엔티티 ex) 주문, 결제, 등록
    - 엔티티는 환경에 따라 다르게 표현된다. -> 엔티티(설계/모델링) = 클래스(OOP) = 테이블(RDB) = 구조체(C/C++)
- Attribute(속성) : 엔티티(주체, 대상)이 가지는 특징
- 관계 : 엔티티들이 어떻게 연결되는 지 나타내는 것
    - 종류 : 1:1(일대일) / 1:N(일대다) /N:M(다대다)

> 주의사항 엔티티의 속성을 작성할 때 해당 엔티티의 이름이 속성명에 포함되면 안된다. ex) 등록 - 등록일자(x) / 등록 - 일자(o) 해석 시 해당 엔티티 명과 속성을 자연스럽게 읽기 때문에 속성명에 포함하지 않는 것이다. ex) 등록 등록일자(?!) / 등록 일자(good)

#### ERD

> ERD(Entity-Relationship Diagram, 개체-관계 다이어그램)는 개념 설계 결과를 다이어그램으로 표현하는 설계도다.

<ERD에서 사용하는 도형과 선>

- 각 도형은 엔티티, 관계, 속성을 나타낸다.
- 선은 엔티티, 관계, 속성 간 연결을 나타내고, 관계가 어떤 종류인지(몇대몇인지) 보여준다. ![이미지](https://cdn.likelion.net/classroom/kdt-backendj-26th/til/4c2aee5b-3af8-4d85-a825-380b0da24ecc.png)

#### 3형식과 4형식

> 문장에는 3형식과 4형식이 있다. (아래 예시는 한국어 기준이다)

- 3형식 : 주어 + 목적어 + 동사 -> 고객이 상품을 주문한다.
- 4형식 : 주어 + 간접목적어 + 직접목적어 + 동사 -> 고객이 상품을 장바구니에 담는다.
- 3형식은 `주어 - 동사 - 목적어` : `엔티티 - 관계 - 엔티티`의 형식을 가져 설계에 큰 어려움이 없다.
- 4형식은 3형식과 달라 모델링을 떠올리기 어렵다. 아래와 같이 2개의 동사(관계)를 사용하는 형식을 가지면 된다. -> `고객 - 담기 - 장바구니 - 포함 - 상품` : `엔티티 - 관계 - 엔티티 - 관계 - 엔티티` => "고객은 장바구니에 담고, 장바구니에는 상품이 포함된다." 해석하게된다.

## 관계형 데이터 베이스

> 데이터를 행(row)과 열(column)로 이뤄진 테이블(표)의 형태로 정리하고, 테이블 간의 연관관계를 바탕으로 데이터를 관리하는 데이터베이스

- 현재 가장 많이 쓰이는 데이터베이스의 종류
- **참조**를 통해 무결성과 데이터 신뢰성을 제공한다.

### 참조?

> 데이터를 중복해서 적지 않고, 데이터가 있는 위치만 가리키는 것

- 과거 데이터를 파일로 관리하던 시절에는 각 프로그램이 데이터를 따로 관리해 중복해서 데이터 작성 -> 데이터 결함 발생!
- 데이터베이스가 등장하고, 공통으로 관리하는 데이터는 데이터베이스에 저장 -> 데이터베의 위치(데이터베이스)만 각 프로그램에서 관리 => <참조>를 통해 데이터 결함 해결
