# 자바의 값 표현

![이미지](https://cdn.likelion.net/classroom/kdt-backendj-26th/til/6467f9ce-4c25-42b3-b20d-01ffab36d6bb.png)

1. 정수
    - 자바에서는 2, 8, 10, 16진법으로 표현 가능 => 분야, 형식, 네트워크 패킷 등에 따라 다르게 사용하기 때문에 모두 지원 필요
     - 컴퓨터의 bit 연산 : 같은 전기선(비트 수)끼리 연산 가능 -> bit 수에 따라 자료 타입이 달라짐
	     - 8bit(byte)
	     - 16bit(short)
	     - 32bit(int - 기본형)
	     - 64bit(long - 현대 컴퓨터의 연산 최대 bit 수) : 리터럴에 접미사 `L`을 붙임

> 정수 표기법(접두사)
<div style="margin-left: 40px;">

| 진법   | 예시 접두사 | 예시          |
| ---- | ------ | ----------- |
| 2진수  | 0b     | 0b0101_0000 |
| 8진수  | 0      | 010         |
| 10진수 | 없음     | 50          |
| 16진수 | 0x     | 0x3C        |

</div>

2. 실수
	- 32bit(float) : 리터럴로 접미사 `F`를 붙임 
	- 64bit(double - 기본형)
3. 문자 : char, 현대에는 유니코드 사용
4. 진리 값(논리형) : boolean, 참/거짓을 가리는 true, false를 값으로 가짐

# 자바 변수 선언

> 번역기는 우리가 작성한 단어를 이해하지 못한다. -> 번역기가 이해할 수 있게 번역기가 아는 키워드를 붙여 변수를 사용하겠다도 선언해야한다.

1. 변수 선언 시 규칙
    - 변수명 첫 글자는 무조건 영문자
    - 변수명에 공백 삽입 금지
    - 한글은 가능하지만 절대 사용 X => 유니코드 지원으로 가능은 하지만, 하위 버전에서 호환이 안됨
2. 변수의 저장 공간은 언제 마련되나? => 번역(컴파일) 시에 마련된다.
    - 일종의 프로그램 실행을 위한 준비물로, 인터프리터와 달리 미리 컴파일해서 변수 공간을 마련한다.
3. 변수끼리 자료형의 크기(bit수)가 다르면? => 계산이 되지 않고 오류가 난다.
    - But, 현대에는 묵시적으로 하위 자료형을 상위 자료형으로 바꾸고 계산해준다.
4. 고정 소수점 VS 부동 소수점 => 승리자는 부동 소수점 : 저장공간을 효율적으로 활용해, 정수 부분 / 소수 부분 크기가 변해도 표현이 가능

# Code / Buffer

> 코드 : 사물이나 생각 등을 기록하기 위한 문자(기호, 부호)

- 컴퓨터에서 코드 : 전기선으로 기록하기 위해 별도로 만든 코드(숫자로만 이뤄짐)
    1. ASCII : 컴퓨터 초창기에 만들어진 코드
        - 영어권에서 많이 사용하는 문자만 포함
        - 8bit = 1byte 코드들로 구성
        - 한글, 일본어 등을 사용하려면 2바이트 이상 사용해야 했고 여러개의 코드표가 별도로 필요했음 (EUC-KR, EUC-JP ...) => 코드표를 잘못 사용하면 문자가 깨지는 현상 발생
    2. UNICODE
        - 한글, 일본어 등 세계의 많은 문자가 포함
        - 기본적으로 멀티바이트의 형식을 가짐
        - 종류

|인코딩|특징|적합한 경향|
|---|---|---|
|UTF-8|세계 공용어인 영어는 1바이트로 충분하기에 사용, 가장 대중적(살짝 이기적..이지 않나..)|웹, 이메일 등 영어 기반 메타 데이터가 많은 곳에 사용, 하지만 다른 문자의 경우 매우 비효율적|
|UTF-16|2바이트 단위로 문자를 다루기에, 대다수의 문자가 문제없이 사용가능|JAVA 언어, 윈도우 시스템 처럼 속도, 단순성이 중요한 곳에 사용|
|UTF-32|3바이트 이상의 문자까지 쉽게 다루기 위해 사용, 그런데 매우매우 비효율적|단순성이 최우선인 상황에서만 사용|

## Buffer

> 잠시 모아두는 공간, 임시 대기소

- 사용 목적
    - buffer가 없다면 수신 받는 곳은 항상 waiting(대기)상태를 유지해야하기 때문에 다른 작업을 못함. -> 항상 송신하는 곳과 동기화되어야 함. => buffer라는 임시 대기소를 두고, 작업이 끝났을 때 buffer안에 있는 것을 수신. => 비동기 수신 가능
- 위와 같은 이유로 데이터를 받는 곳에는 항상 버퍼가 있다.
