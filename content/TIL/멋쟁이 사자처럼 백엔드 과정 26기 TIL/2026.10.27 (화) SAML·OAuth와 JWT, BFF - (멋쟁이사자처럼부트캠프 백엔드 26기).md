오늘은 인증을 여러 서비스에서 다루는 방식부터 JWT, BFF 구조까지 배웠다. 어제는 Spring Security로 로그인한 사용자를 확인했다면, 오늘은 서버가 여러 대일 때 그 로그인 정보를 어떻게 주고받는지가 이어졌다.

# SAML과 OAuth

서버가 한 대일 때는 로그인 정보를 그 서버에서 관리하면 된다. 그런데 서비스가 여러 개로 나뉘면 매번 따로 로그인해야 할까? 이 문제를 설명하면서 **SSO(Single Sign-On)**를 배웠다. 한 번의 로그인 결과를 신뢰 관계에 있는 여러 서비스에서 이용하는 방식이다.

## SAML

> 인증을 맡은 곳의 로그인 결과를 다른 서비스에 전달하는 SSO 방식

SAML에서는 사용자를 인증하는 **IdP**와 서비스를 제공하는 **SP**가 나뉜다. 사용자가 IdP에서 로그인하면 SP는 전달받은 인증 결과를 확인한다. 로그인 결과를 교환할 때 XML 기반의 메시지를 사용한다.

처음에는 여러 서버의 인증 정보를 한 서버에 모으는 정도로 이해했다. 정리해 보니 중요한 것은 서버의 대수 자체보다 **서로 다른 서비스가 같은 인증 결과를 신뢰하는 것**이었다.

<br/>

## OAuth

> 사용자가 가진 자원에 다른 애플리케이션이 접근할 수 있도록 권한을 위임하는 방식

OAuth는 간편 로그인에서 접해 봐서, 큰 서비스가 인증 기능을 외부에 열어 주는 방식이라고 생각했다. 여기서는 사용자, 접근 권한을 요청하는 애플리케이션, 토큰을 발급하는 서버, 실제 데이터를 가진 서버를 구분한다.

- **리소스 소유자:** 자신의 데이터에 대한 접근을 허락하는 사용자
- **클라이언트:** 사용자를 대신해 접근을 요청하는 애플리케이션
- **인가 서버:** 동의를 확인하고 토큰을 발급하는 곳
- **리소스 서버:** 토큰을 확인하고 데이터를 제공하는 곳

SAML과 OAuth를 각각 조직 안의 SSO와 외부 서비스 연동 사례로 접했다. 다만 OAuth의 핵심은 다른 서비스에 **접근 권한을 위임**하는 것이라는 점을 기억해야겠다.

# 세션에서 JWT로

세션 방식에서는 서버가 로그인 상태를 저장하고, 브라우저는 **세션 ID가 담긴 쿠키**를 보낸다. 서버가 여러 대라면 한 서버에 저장된 세션을 다른 서버가 바로 알 수 없다. 세션 저장소를 공유할 수도 있지만, 서버 사이에서 인증 상태를 관리할 방법이 필요해진다.

JWT를 이용하면 클라이언트가 토큰을 가지고 있다가 요청마다 전달하고, 서버는 받은 토큰을 검증해 현재 요청의 사용자를 확인할 수 있다. 이렇게 요청마다 인증 정보를 확인하는 방식을 **Stateless**라고 배웠다.

## JWS와 JWE

JWT를 공부하면서 서명 방식인 **JWS**와 암호화 방식인 **JWE**를 구분했다.

```text
Base64URL(헤더).Base64URL(페이로드).서명
```

JWS의 헤더에는 서명 알고리즘 등의 정보가, 페이로드에는 전달할 정보가 들어간다. 마지막 서명은 헤더와 페이로드가 바뀌지 않았는지 확인하는 데 쓴다. 처음에는 페이로드를 암호화한 값이라고 생각했는데, **서명은 내용을 숨기지 않는다.** Base64URL 인코딩도 암호화가 아니어서 페이로드는 읽을 수 있다.

JWE는 내용을 암호화하는 방식이다. 오늘은 JWS의 서명과 JWE의 암호화가 서로 다른 목적이라는 점까지 이해했다.

<br/>

## JWT를 사용하기 위한 설정

JWT를 직접 만들고 검사하려면 먼저 Spring Boot 프로젝트에 JJWT를 추가해야 한다. 실습에서는 `build.gradle`에 API, 구현체, JSON 처리 모듈을 나눠 넣었다.

```gradle
dependencies {
    implementation 'io.jsonwebtoken:jjwt-api:0.12.6'
    runtimeOnly 'io.jsonwebtoken:jjwt-impl:0.12.6'
    runtimeOnly 'io.jsonwebtoken:jjwt-jackson:0.12.6'
}
```

서명에 사용할 비밀키와 토큰의 만료 시간도 필요하다. 값을 자바 클래스 곳곳에 적기보다는 `application.yml`에 모으고, `JwtProperties`로 읽어 오는 흐름을 배웠다.

```yaml
jwt:
  secret: "${JWT_SECRET}"
  access-token-expiration: 1800000      # 30분
  refresh-token-expiration: 1209600000  # 14일
```

`@ConfigurationProperties(prefix = "jwt")`를 사용하면 `jwt` 아래의 설정값을 자바 객체의 필드에 연결할 수 있다. 예를 들어 `access-token-expiration`은 `accessTokenExpiration`으로 읽어 온다.

```java
@Component
@ConfigurationProperties(prefix = "jwt")
public class JwtProperties {
    private String secret;
    private long accessTokenExpiration;
    private long refreshTokenExpiration;

    // 각 필드의 getter와 setter
}
```

*코드 출처: [뉴렉처](https://newlecture.com/) (주요 필드만 발췌)*

## `JwtProvider`: 발급과 검증

설정값을 준비한 뒤에는 `JwtProvider`에서 토큰을 만들고 검사한다. Access Token은 API 요청에 사용할 수 있도록 사용자 아이디와 역할을 담고, Refresh Token은 Access Token을 다시 발급받을 때 사용한다.

```java
@Component
public class JwtProvider {
    private final JwtProperties jwtProperties;
    private SecretKey secretKey;

    public JwtProvider(JwtProperties jwtProperties) {
        this.jwtProperties = jwtProperties;
    }

    @PostConstruct
    public void init() {
        byte[] keyBytes = jwtProperties.getSecret().getBytes(StandardCharsets.UTF_8);
        this.secretKey = Keys.hmacShaKeyFor(keyBytes);
    }

    public String createAccessToken(String username, String role) {
        long now = System.currentTimeMillis();
        return Jwts.builder()
                .subject(username)
                .claim("role", role)
                .issuedAt(new Date(now))
                .expiration(new Date(now + jwtProperties.getAccessTokenExpiration()))
                .signWith(secretKey)
                .compact();
    }

    public String createRefreshToken(String username) {
        long now = System.currentTimeMillis();
        return Jwts.builder()
                .subject(username)
                .issuedAt(new Date(now))
                .expiration(new Date(now + jwtProperties.getRefreshTokenExpiration()))
                .signWith(secretKey)
                .compact();
    }

    public String getUsername(String token) {
        return parseClaims(token).getSubject();
    }

    public String getRole(String token) {
        return parseClaims(token).get("role", String.class);
    }

    public boolean validateToken(String token) {
        try {
            parseClaims(token);
            return true;
        } catch (ExpiredJwtException e) {
            return false;
        } catch (JwtException | IllegalArgumentException e) {
            return false;
        }
    }

    private Claims parseClaims(String token) {
        return Jwts.parser()
                .verifyWith(secretKey)
                .build()
                .parseSignedClaims(token)
                .getPayload();
    }
}
```

*코드 출처: [뉴렉처](https://newlecture.com/) (단계별 코드를 한 클래스로 정리, import 생략)*

`@PostConstruct`에서 문자열 비밀키를 서명에 사용할 `SecretKey`로 바꾼다. 발급할 때는 사용자 정보와 만료 시각을 넣고 서명한다. 다시 토큰이 들어오면 `parseSignedClaims()`로 서명과 만료 여부를 확인한다.

<br/>

## `JwtAuthenticationFilter`: 요청에서 토큰 확인

토큰을 만드는 코드가 있어도 들어오는 요청에서 꺼내 쓰지 않으면 로그인 상태를 알 수 없다. 그래서 `OncePerRequestFilter`를 상속한 필터에서 `Authorization` 헤더를 읽는다.

```http
Authorization: Bearer <JWT 토큰>
```

앞의 `Bearer `를 제외한 토큰을 `JwtProvider`로 검증한다. 유효하다면 아이디와 권한으로 `Authentication` 객체를 만들고 `SecurityContextHolder`에 넣는다.

```java
public class JwtAuthenticationFilter extends OncePerRequestFilter {
    private final JwtProvider jwtProvider;

    public JwtAuthenticationFilter(JwtProvider jwtProvider) {
        this.jwtProvider = jwtProvider;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {
        String token = resolveToken(request);

        if (token != null && jwtProvider.validateToken(token)) {
            String username = jwtProvider.getUsername(token);
            String role = jwtProvider.getRole(token);

            Authentication authentication = new UsernamePasswordAuthenticationToken(
                    username,
                    null,
                    Collections.singletonList(new SimpleGrantedAuthority(role))
            );
            SecurityContextHolder.getContext().setAuthentication(authentication);
        }

        filterChain.doFilter(request, response);
    }

    private String resolveToken(HttpServletRequest request) {
        String bearerToken = request.getHeader("Authorization");
        if (StringUtils.hasText(bearerToken) && bearerToken.startsWith("Bearer ")) {
            return bearerToken.substring(7);
        }
        return null;
    }
}
```

*코드 출처: [뉴렉처](https://newlecture.com/)

토큰이 없는 요청도 로그인 같은 공개 API일 수 있으므로, 필터에서 인증 객체를 만들지 않고 다음 필터로 넘긴다. 이후 URL별 인가 규칙이 접근 가능 여부를 결정한다. `filterChain.doFilter()`를 호출해야 다음 필터와 컨트롤러까지 요청이 이어진다.

<br/>

## `SecurityConfig`: 필터와 접근 권한 등록

필터를 만들기만 해서는 실제 요청에 적용되지 않는다. `SecurityFilterChain`에 등록하고, 토큰 없이 호출할 수 있는 경로와 권한이 필요한 경로를 나눈다.

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .csrf(AbstractHttpConfigurer::disable)
        .sessionManagement(session ->
            session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
        )
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**", "/error").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated()
        )
        .addFilterBefore(
            new JwtAuthenticationFilter(jwtProvider),
            UsernamePasswordAuthenticationFilter.class
        );

    return http.build();
}
```

*코드 출처: [뉴렉처](https://newlecture.com/) (설정 메서드 발췌)*

`STATELESS`로 세션에 인증 상태를 저장하지 않고, 요청마다 JWT 필터가 토큰을 확인하도록 했다. `/api/auth/**`는 로그인처럼 토큰을 얻기 전에도 호출해야 하므로 열어 두었다. `/api/admin/**`는 관리자 권한이 필요하다.

> 일반적으로 **세션 ID를 담은 쿠키** 방식을 더 많이 사용한다. 하지만 다른 서버에 JWT를 명시적으로 보낼 때는 `Authorization` 헤더를 사용한다. 쿠키도 HTTP 요청에서는 `Cookie` 헤더로 전달되므로, 둘은 ‘세션 ID 쿠키’와 ‘Authorization 헤더의 토큰’으로 구분해서 기억하면 되겠다.

## 비밀번호 해시와 토큰 서명

비밀번호 해시와 JWT 서명도 목적이 다르다. 비밀번호는 DB에 원문 대신 해시 값을 저장하고, 로그인할 때 입력값을 `PasswordEncoder`로 비교한다. JWT 서명은 발급한 뒤 토큰 내용이 바뀌지 않았는지 확인한다. 비밀번호 해시를 토큰에 담는 것은 아니다.

# BFF 아키텍처

> 클라이언트의 요청을 프론트엔드 서버가 받고, 그 서버가 내부 API와 통신하는 구성

내가 그린 구성에서는 **내부 API에 접근할 수 있는 대상을 프론트엔드 서버(BFF)로 제한**했다. 브라우저는 프론트엔드 서버에 요청하고, 프론트엔드 서버가 내부 API를 호출한다. 내부 API는 데이터베이스와 통신한다.

![BFF를 통한 내부 API 접근 구조](./assets/bff-architecture-2026-10-27.svg)


처음에는 이 구조가 CSR을 막는 방식이라고 생각했다. 그런데 SSR과 CSR은 **화면을 그리는 방식**이고, BFF는 **브라우저와 내부 API 사이에 서버를 두는 구조**다. CSR 화면도 BFF에 요청할 수 있다. 중요한 것은 브라우저가 내부 API에 직접 접근하지 않도록 경로를 구성하는 것이다.

<br/>

## Next.js가 BFF를 맡는다면

Next.js는 화면을 제공하면서 `route.ts`로 API 요청도 받을 수 있다. 브라우저는 이 경로에 요청하고, Next.js 서버가 내부 Spring Boot API와 통신하는 식이다.

```ts
export async function GET() {
  return Response.json({ message: "API 응답입니다." });
}
```


Docker Compose의 내부 네트워크에 Spring Boot API와 DB를 두고 외부에는 프론트엔드만 공개하면, 클라이언트가 내부 API를 직접 호출하는 경로를 줄일 수 있다. 프론트엔드에서 인증을 확인하더라도 내부 API의 권한 확인까지 생략하면 안 된다는 점도 함께 배웠다.

Next.js의 Middleware는 보호할 페이지 경로를 확인하고, 인증되지 않은 요청을 로그인 페이지로 돌려보내는 데 사용할 수 있다. 다만 페이지 접근을 확인하는 것과 내부 API의 권한을 확인하는 것은 각각 필요하다.

# 오늘 느낀 점

스프링 시큐리티를 여기서 배우기 이전에는 단순히 JWT를 쓰라고 해서 쓰는 느낌이 강했다. 이번에 여러 인증 방식을 배우고 왜 JWT까지 이어지게 됐는지 배우면서, 이제 왜 그걸 사용해야하는지 직접 대답할 수 있게 된 거 같다. 그 외에도 세션 ID 쿠키 방식을 이해하면서, 부족한 인증 관련 지식을 채울 수 있어서 좋은 기회였던 거 같다.
