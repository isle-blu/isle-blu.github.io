# 인터페이스와 의존성 주입

## 인터페이스를 사용하는 이유

> 인터페이스를 사용하면 상황에 따라 다른 구현체를 넣을 수 있다.

Service나 Repository를 사용하는 쪽이 구체적인 구현 클래스에 직접 의존하면, 구현이 바뀔 때 사용하는 코드도 영향을 받는다. 인터페이스에 의존하면 사용하는 쪽의 코드를 바꾸지 않고 다른 구현체를 주입할 수 있다.

## IoC 컨테이너와 의존성 주입

객체를 직접 `new`로 만들고 연결하는 대신, 스프링의 IoC 컨테이너가 빈을 생성하고 관리하며 필요한 의존성을 주입한다. 개발자는 생성자를 통해 어떤 객체가 필요한지 표현하고, 스프링은 그에 맞는 빈을 찾아 전달한다.

> IoC는 객체의 생성과 연결을 제어하는 주체가 애플리케이션 코드에서 스프링 컨테이너로 바뀌는 것을 말한다.

## 생성자 주입을 사용하는 이유

의존성을 주입하는 방법에는 필드 주입, 생성자 주입, 세터 주입이 있다.

생성자 주입을 사용하면 객체를 만들 때 필요한 의존성을 전달받으므로 필드를 `final`로 선언할 수 있다. 이를 통해 객체가 만들어진 뒤 해당 필드에 다른 값을 다시 대입하지 못하게 한다.

또한 두 객체가 생성자를 통해 서로를 필요로 한다면, 스프링이 빈을 생성하는 과정에서 순환 참조를 발견하고 오류를 발생시킨다. 생성자 주입이 순환 참조 자체를 방지하는 것은 아니지만, **순환 참조 문제를 빈 생성 시점에 발견할 수 있다.**

# 3계층 구조와 요청 처리 흐름

> Controller는 요청과 응답을 담당하고, Service는 업무 로직과 데이터 조립을 담당하며, Repository는 데이터에 접근한다.

스프링 MVC에서는 톰캣이 일반적인 컨트롤러를 직접 호출하지 않는다. 요청을 받은 `DispatcherServlet`이 URL에 맞는 컨트롤러 메서드를 찾아 실행한다.

클라이언트 → 톰캣 → DispatcherServlet → Controller → Service → Repository → 응답

이 흐름을 통해 각 계층이 맡은 역할을 구분할 수 있다. 컨트롤러에서 직접 데이터를 조회하거나, 리포지토리에서 화면 응답을 조립하면 역할의 경계가 흐려질 수 있다.

# DTO 작성 방식

## Request DTO와 Response DTO

이번에 작성한 조회용 Request DTO에는 쿼리스트링으로 전달받을 검색 조건 등의 파라미터를 담았다. Response DTO에는 화면에 보여줄 데이터와 이후 API 호출에 필요한 `id` 등의 값을 담았다.

값이 없을 수 있는 DTO 필드에는 `int`, `long` 같은 기본형 대신 `Integer`, `Long` 같은 참조형을 사용한다. 기본형은 `null`을 표현할 수 없기 때문이다. 다만 Request DTO가 모두 쿼리스트링을 위한 것은 아니며, 요청 본문을 전달받기 위한 DTO도 있다.

## Repository와 Service의 역할

이번에 배운 구조에서는 Repository가 엔티티를 조회하고, Service가 조회한 데이터를 응답에 필요한 DTO 형태로 가공한다.

데이터를 조회하는 역할과 응답 데이터를 구성하는 역할을 나누는 것은 SRP와도 연결된다. 각 부분이 맡는 책임을 분명히 해, 서로 다른 이유로 변경되는 코드를 한곳에 섞지 않는 것이다.

Repository가 반드시 엔티티만 반환해야 하는 것은 아니다. 필요에 따라 DTO 형태로 조회할 수도 있으므로, 위 내용은 **이번에 적용한 역할 분리 방식**으로 이해했다.

## 화면의 용도에 따른 Response DTO 분리

메뉴 목록과 카테고리 목록은 같은 화면에 표시될 수 있지만, 각각 필요한 데이터가 다르다. 따라서 메뉴 목록 응답과 카테고리 목록 응답을 별도의 DTO로 구성할 수 있다.

메뉴 목록 응답에는 화면에 표시할 메뉴 이름·가격·이미지뿐 아니라, 상세 조회나 장바구니 추가에 필요한 메뉴 ID도 담을 수 있다. DTO는 화면에 보이는 값만이 아니라 **그 화면에서 이어지는 동작에 필요한 값**까지 고려해 설계해야 한다.
