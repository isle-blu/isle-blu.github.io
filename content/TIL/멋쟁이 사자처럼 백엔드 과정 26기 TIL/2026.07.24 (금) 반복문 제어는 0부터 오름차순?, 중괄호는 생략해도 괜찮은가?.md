> 이번 강의를 들으면서 강사님이 권장하신 방식과 내가 사용하던 방식이 대비된다는 것을 알았다.

- 강사님의 제시하신 근거는 충분히 납득할 수 있었다.
- 하지만 나와 같이 하는 개발자도 많을 거라 생각해, 다른 의견이 궁금했다.

# 반복문 인덱스는 0부터 오름차순이어야 하는가

> 반복문에서 횟수를 표현하는 경우 항상 0부터 오름차순으로 작성하는 것을 권장하셨다.

- 나는 자원을 조금이라도 아끼는 방식을 써왔다. 그래서 처음에 당황했었다.

---

## 1. 강사님의 의견

> **반복을 제어하는 곳**에서는 몇번 반복할 지, 바로 알 수 있게 적는 게 좋다. 그래서 조건식은 항상 `0`부터 오름차순으로 쓴다.

```java
// 지침에 맞는 코드
for (int i = 0; i < 10; i++) {
    int value = 10 - i;   // 실제 다루고 싶은 값은 몸통에서 계산
    System.out.println(value);
}

// 지침에서 지양하는 코드
for (int i = 10; i > 0; i--) {
    System.out.println(i);
}
```

## 2. 내가 가진 의문

아래 코드가 `i + 1` 연산을 매번 하지 않으니 자원을 더 아끼는 것 아닌가?

```java
int i = 0;
while (i < 10) {
    System.out.printf("%d, Hello\n", i + 1);  // 매 반복마다 덧셈
    i++;
}

int i = 1;
while (i <= 10) {
    System.out.printf("%d, Hello\n", i);      // 덧셈 없음
    i++;
}
```

확인 결과: 클로드와 대화를 해본 결과 미시적으로는 맞지만 실무적으로는 무의미하다. 정수 덧셈 한 번은 나노초 이하이고, JIT 컴파일러가 이런 단순 반복 덧셈은 자동 최적화한다. 반복 횟수가 10번이든 천만 번이든 사람이 체감할 차이를 만들지 못한다.

## 3. 배경 조사: 0-based 인덱싱은 어떻게 관례가 됐나

### 실질적 기원 — C 언어의 메모리 오프셋

배열 인덱스는 "첫 원소로부터 몇 칸 떨어져 있는가(offset)"를 뜻한다고 한다. 첫 원소는 0칸 떨어져 있으므로 `arr[0]`이다. C언어가 이를 대중화했고, 이후 대부분의 언어가 이 흐름을 따랐다.

### 이론적 뒷받침 — Dijkstra의 1982년 메모

"Why numbering should start at zero"에서 Dijkstra는 반열린구간 `a ≤ i < b` 표기를 옹호했다.

> <근거>

- 길이 계산이 항상 깔끔하다

```java
for (int i = 0; i < 10; i++) { ... }
// 개수 = 10 - 0 = 10개.  코드의 "10"이라는 숫자를 보자마자 "10번 돈다"는 게 바로 보임
```

- 빈 수열을 자연스럽게 표현할 수 있다

```java
for (int i = 5; i < 5; i++) { ... } // 조건이 처음부터 false → 0번 실행. 자연스러움
```

- 연속된 두 구간을 이어붙일 때 겹치거나 빠지는 부분이 없다

```java
구간 A: 0 ≤ i < 5   (0,1,2,3,4)
구간 B: 5 ≤ i < 10  (5,6,7,8,9)
```

> 다익스트라의 결론

- 이 세가지 근거를 바탕으로 0부터 시작하는 반열린 구간 즉 `for (int i = 0; i < n; i++)`과 같은 패턴이 가장 자연스럽다고 결론지었다.

## 반론

- "장점이 특정 연산에만 국한된 것 아니냐"는 반박
- "순환논법이다"라는 지적
    - "오프셋은 0부터 시작한다 → 인덱스는 오프셋이다 → 인덱스는 0부터 시작해야 한다"는 순환 구조
- 역사적으로 1-based도 충분히 길고 성공적인 전통을 가지고 있다
    - Fortran, COBOL, Pascal, Ada, Smalltalk 등 긴 역사를 가진 1-based 언어들이 존재
- 성능 이점은 근거 약하다.

→ 정착의 결정적 이유는 **이론적 우월성보다 "C 이후 대다수 언어가 따라갔다"는 관성과 생태계 통일성**에 가깝다.

**참고**: [Wikipedia: Zero-based numbering](https://en.wikipedia.org/wiki/Zero-based_numbering), [hisham.hm의 반론 글](https://hisham.hm/2021/01/18/again-on-0-based-vs-1-based-indexing/)

## 나는 어떻게 할 것인가

- 기본적으로 강사님의 의견을 따를 것 같다. 대부분의 경우 가독성과 협업 면에서 이득이 많아.
- 단 내림차순이 필요한 경우, 고민을 할 것 같다. 강의에서는 `10-i`와 같은 방식을 사용했지만, 개인적인 의견으로는 가독성 자체는 이것도 나쁘지 않다는 생각이 든다.

# 중괄호 생략 문제

> 반복문에서 중괄호를 생략할 수 있다면, 생략하는 게 맞을까?

- 강사님은 생략을 권장하셨다.
- 이번에는 내가 처음 가졌던 의견부터 설명해보려고 한다.(의견이 나중에 바꼈다는 얘기다)

## 중괄호 문제가 대두된 배경

> Apple 사의 `goto fail`버그가 배경이 되었다.

```c
if ((err = SSLHashSHA1.update(&hashCtx, &signedParams)) != 0)
    goto fail;
    goto fail;   // 중괄호가 없어 이 줄이 항상 실행됨 (들여쓰기는 눈속임일 뿐)
```

- 이 저 한줄의 실수로 인해, 치명적인 보안 문제가 발생했었다.
- 이 이슈로 강조된 의견은 다음과 같다.
    - 이와 같은 문제가 발생하지 않게 중괄호를 반드시 사용하자.
    - 배포 전에 테스트를 반드시 진행하자.

## 중괄호 생략 반대

> 원래 내 입장이다. 찾아보니 기존 자료는 이쪽이 우세했다.

1. Google Java Style Guide 원문(4.1.1절)
    - "if, else, for, do, while 문에는 중괄호를 쓴다. 본문이 비어있거나 단일 문장만 있는 경우에도 마찬가지다."
2. Airbnb JavaScript Style Guide 등 다른 대기업 표준들도 대부분 동일하게 **"한 줄이어도 무조건 중괄호"**를 규정

## 중괄호 생략 찬성(또는 기존의견 반박)

1. codecentric 블로그
    - 진짜 원인은 스타일이 아니라, 애초에 goto fail이 중복으로 존재해서는 안 됐다는 점이라고 주장
2. Adam Langley(Google 보안 엔지니어)도 비슷한 지적
    - "코딩 스타일이 중괄호 없는 if를 허용해서 이 사태에 기여했을 수도 있지만, 중괄호가 있어도 잘못된 들여쓰기는 얼마든지 가능하니 그다지 설득력 있는 얘기는 아닌 것 같다."
3. 중괄호 언어에서, "생략 가능한 상황"을 넓혀가는 흐름
    - Python이 30년 넘게 유지해온 설계 철학이 최근 들어 인기
    - Kotlin: 람다식이나 단일 표현식 함수에서 중괄호를 생략하는 문법을 적극 지원
    - Swift: guard let, 트레일링 클로저 등에서 중괄호 사용을 최소화하는 문법 설계

## 나는 어떻게 할 것인가

- 확실히 중괄호가 늘어날 수록 코드 자체가 복잡해져, 생략가능하다면 생략하는 게 좋을 거 같다.
- 이번 강의 동안 직접 써보고 경험해보는 게 좋을 것 같다.
- swift는 if, for에서 반드시 중괄호를 쓰게한다.(애플 거라 goto fail 이후로 강제로 넣게 되었다고 한다..)
    - 이런 경우가 있으니 작성하는 내용의 중요도에 따라 고민은 해볼 수도 있지 않을까 한다.(그래도 그냥 안쓰는 게 좋은 거 같기도..)
