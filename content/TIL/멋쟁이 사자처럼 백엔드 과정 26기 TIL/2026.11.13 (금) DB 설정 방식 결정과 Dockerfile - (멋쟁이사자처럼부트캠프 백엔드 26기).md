- 그런데 DB 설정 방식에서 문제가 생겨서, Spring 표준 구성으로 바꾸기로 했다. (아직 적용 전)

# 오늘의 과정

## 처음에 만든 DB 설정

> `postgres:18-alpine`을 Compose로 띄우고, 접속 정보는 `.env`에서 읽는다. 저장소에는 `.env.example`만 올린다.

- compose에서는 `${VAR:?메시지}`로 값을 받았다. => 값이 없으면 compose가 실패하고 메시지를 보여 준다.
- 기본값은 두지 않았다. 굳이 둘 이유가 없다고 봤다.
- `application.properties`의 datasource 값도 `${DB_HOST}` 같은 **환경 변수로만** 받았다.
- 로컬에서 실행할 때는 `.env`를 셸 환경 변수로 불러왔다.

```bash
set -a; . ../.env; set +a
```

- CI에서는 GitHub Actions의 `services:`로 Postgres를 띄우고, `pg_isready`로 준비될 때까지 기다렸다.
    - 그런데 `services`에서는 `env` 컨텍스트를 쓸 수 없어서, 같은 값을 두 번 적어야 했다.

<br/>

## Compose를 만들며 처음 알게 된 것

- Postgres 18부터 데이터 경로가 `/var/lib/postgresql/<버전>/docker`로 바뀌었다. => 볼륨은 `/var/lib/postgresql`에 마운트한다.
- healthcheck에서는 `$${POSTGRES_USER}`처럼 `$$`로 써야 compose가 치환하지 않고 컨테이너에 그대로 넘긴다.

> DB 이름·사용자·비밀번호를 바꿨는데 적용이 안 된다면?

- 이 값들은 **볼륨을 처음 만들 때만** 적용된다.
- 바꾸려면 `docker compose down -v`로 볼륨까지 지우고 다시 띄워야 한다.

<br/>

## 기본값을 모두 뺐더니 생긴 문제

1. 해석하지 못한 `${DB_HOST}`가 **글자 그대로** 남았다. => `Driver claims to not accept jdbcUrl` 오류가 났는데, 메시지만 보고는 원인을 알기 어려웠다.
2. IDE의 실행 버튼은 `.env`를 읽지 않는다.

<br/>

## Spring Boot에서 DB 설정을 다루는 방식

> 일반적인 방식은 4가지였다.

| 방식 | 내용 |
| --- | --- |
| a. 설정 안에 기본값 | `${VAR:기본값}` |
| b. 프로필 분리 | `application-local.yml`에 로컬 값 |
| c. spring-boot-docker-compose | `bootRun`이 compose를 띄우고 접속 정보를 자동으로 연결 |
| d. 전부 환경 변수 | 12-factor 방식 |

<br/>

## 오늘의 결정

- **상황** : 기본값 없는 환경 변수 방식은 오류 원인을 알기 어렵고, IDE에서 바로 실행되지 않았다.
- **무엇으로 바꾸나** : **c. spring-boot-docker-compose + Testcontainers(`@ServiceConnection`)**
- **왜**
    - Spring Initializr가 기본으로 만들어 주는 구성이고, CI에서도 따로 설정하지 않아도 그대로 동작한다.
    - 처음에 AI는 b(프로필 분리)를 추천했다. 그런데 추천한 이유가 원격 Docker를 쓰는 **나 한 명의 환경**이었다. => 팀 설정을 개인 환경에 맞추지 않기로 했다.

> 내 환경(원격 Docker)은 어떻게?

- 저장소 밖에서 설정한다.
- `bootRun` => git에서 뺀 `application-remote.yml`
- Testcontainers => Spring 설정을 읽기 **전에** Docker에 연결해서 yml로는 설정할 수 없다. => `~/.testcontainers.properties`나 `DOCKER_HOST`를 쓴다.

> Docker Compose 지원의 특징

- 테스트에서는 기본으로 꺼져 있다. (`skip.in-tests=true`)
- 기본 동작은 앱을 끄면 DB도 멈춘다. => `lifecycle-management=start-only`로 바꿀 수 있다.
- `compose.yaml` 위치 문제로 backend 폴더로 옮길 예정이다.

## Dockerfile

### 백엔드

> 빌드용 이미지와 실행용 이미지를 나누는 **멀티 스테이지** 빌드

- `temurin:21-jdk`에서 빌드하고, `temurin:21-jre`에서 실행한다.
- gradle 설정 파일을 먼저 복사한다. => 의존성 레이어를 캐시로 재사용할 수 있다.
- 테스트는 CI가 맡으니까 `bootJar -x test`로 빌드한다.
- root가 아닌 `app` 사용자로 실행한다.

### 프론트

- `output: "standalone"`을 설정했다.
- 그런데 standalone 결과물에는 `public/`과 `.next/static/`이 빠져 있다. => 따로 복사해야 한다.
- 단계는 `deps → build → runner`로 나눴다.
- `HOSTNAME=0.0.0.0`을 설정했다.
