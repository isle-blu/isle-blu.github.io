스프링 3계층에서 각 계층이 맡는 역할은 배웠지만, 실제로 메서드 이름과 URL을 어떻게 작성해야 하는지는 별개의 문제였다. 오늘은 메서드 이름, Controller의 URL 매핑과 매개변수, 응답 방식을 살펴봤다.

# 3계층의 메서드 이름

> 클래스 이름에 어떤 데이터를 다루는지 이미 나타나 있다면, 메서드 이름에서 같은 말을 반복하지 않는다.

`MenuController` 안에서 메뉴 목록을 가져오는 메서드는 `getMenuList()`보다 `getList()`로 작성한다. 클래스 이름과 메서드 이름을 함께 읽으면 어떤 데이터를 가져오는지 알 수 있기 때문이다.

- Controller와 Service : 일반적으로 생성은 `create`, 조회는 `get`, 수정은 `update`, 삭제는 `delete`를 사용
- Repository : DB에서 데이터를 **찾는다**는 의미로 `find`를 사용
- 실제 메서드 이름은 팀에서 정한 규칙을 우선해서 작성

> 내가 가진 의문

클래스가 여러 대상을 다루게 된다면 `getList()`만으로는 무엇을 조회하는지 모호할 수도 있지 않을까? 이런 경우에는 어떻게 이름을 짓는 게 좋을지, 앞으로 여러 프로젝트를 해보면서 고민해봐야겠다.

# Controller의 URL과 HTTP 메서드

> URL로 다루는 데이터를 나타내고, HTTP 메서드로 어떤 작업을 할지 구분한다.

클래스에는 `@RequestMapping`으로 공통 URL을 작성한다. 각 메서드에는 `@GetMapping`, `@PostMapping`처럼 요청 방식에 맞는 어노테이션을 붙이고, 공통 URL 뒤에 필요한 경로를 작성한다.

예를 들어 클래스의 공통 경로가 `/api/v1/menus`이고, 상세 조회 메서드에 `@GetMapping("/{id}")`를 붙였다면 최종 요청은 `GET /api/v1/menus/{id}`가 된다.

수정에는 `PUT`과 `PATCH`를 사용할 수 있다.

- `PUT` : 리소스의 전체 내용을 교체하는 요청
- `PATCH` : 리소스의 일부 내용을 변경하는 요청

따라서 둘 다 수정에 사용하지만, **요청이 무엇을 변경하는지**에 따라 구분해야 한다.

## Controller의 매개변수

> 요청값이 URL의 어느 부분에 있는지에 따라 받는 방법이 달라진다.

- `@PathVariable` : `/menus/{id}`처럼 URL 경로에 있는 식별자를 받는다.
- `@RequestParam` : `/menus?categoryId=1`처럼 쿼리스트링에 있는 값을 받는다.
- `@RequestBody` : 요청 본문으로 보낸 JSON 데이터를 DTO로 받는다.

예를 들어 특정 메뉴를 조회하거나 삭제할 때는 경로의 `id`를 `@PathVariable`로 받는다. 메뉴 생성·수정에 필요한 데이터를 JSON 본문으로 보냈다면 `@RequestBody`로 Request DTO를 받는다.

# Controller의 응답

> 응답할 데이터는 DTO에 담고, 상태 코드를 별도로 지정할 때는 `ResponseEntity`를 사용한다.

이번에 배운 방식에서는 각 메서드의 응답에 필요한 데이터를 기준으로 DTO를 작성했다. DTO 이름에는 **어떤 데이터인지, 어떤 작업인지, 요청과 응답 중 무엇인지**를 담는다. 메뉴 생성 응답이라면 `MenuCreateResponseDto`와 같이 작성한다.

`ResponseEntity`를 사용하면 HTTP 상태 코드와 응답 본문을 함께 지정할 수 있다. 응답할 데이터가 있다면 본문에 DTO를 넣는다.

삭제 후 돌려줄 데이터가 없다면 본문 없이 `204 No Content`를 반환한다.

```java
return ResponseEntity.noContent().build();
```
