# 오늘의 상황

> 피드백에 첨부한 이미지를 제출 후에도 다시 볼 수 있게 연결하고, 팀원이 이어서 작성할 수 있도록 프로젝트 기술문서를 정리했다.

먼저 피드백 이미지 업로드부터 조회까지 백엔드 API와 프론트 화면을 연결하고, 이미지를 다시 요청할 때도 접근 권한을 확인하도록 했다. 그다음에는 기술문서의 구성과 서식을 잡고, 문서 설명이 최신 코드와 맞는지, 캡처와 테스트 결과가 어떤 환경의 기록인지 하나씩 대조했다.

---

# 오늘의 과정

## 피드백 이미지 업로드부터 조회까지

피드백에 이미지를 첨부하고 제출한 뒤에도 다시 볼 수 있도록 연결했다.

- PNG·JPG·WEBP 이미지를 한 장당 5MB까지 업로드
- 피드백 항목과 기타 의견에 이미지 주소를 함께 제출
- 항목마다 최대 5장으로 제한하고, 내용 없이 이미지만 제출하는 경우 차단
- 제출한 테스터와 해당 프로젝트 개발자가 이미지를 조회
- 이미지 업로드 코드를 여러 기능이 함께 쓰는 위치로 이동

처리 흐름은 이렇다.

이미지 선택 → 파일 업로드 → 이미지 주소 반환 → 피드백 제출 시 항목별로 연결

파일 업로드와 피드백 저장은 시점이 다르다. 그래서 파일을 올렸다고 바로 피드백에 연결되는 게 아니다. 제출하지 않아서 남는 파일을 정리하는 작업은 따로 남겨 두었다.

## 이미지 조회에도 접근 권한 적용

> 피드백 이미지는 주소를 안다고 누구나 볼 수 있으면 안 된다.

피드백 이미지에는 테스터의 화면이나 개인정보가 담길 수 있다. 그래서 공개 이미지와 저장 위치를 분리했다.

- 테스터 => 자신의 참가 정보를 기준으로 확인
- 개발자 => 자신의 프로젝트에 속한 피드백인지 확인
- 조회 응답에는 `Cache-Control: no-store` 적용

업로드할 때만 권한을 보는 게 아니라, 이미지를 다시 요청하는 시점에도 권한을 확인하도록 했다.

업로드·제출·조회·접근 차단 테스트를 추가했고, 화면 연결을 직접 확인하는 시나리오 10개도 통과했다.

## 팀원이 이어서 쓸 수 있는 기술문서

기술문서는 기능 소개로 끝나는 게 아니라, 다른 사람이 프로젝트를 실행하고 구조를 이해할 수 있어야 한다는 기준으로 구성했다.

1. 프로젝트 개요
2. 개발 환경과 실행 방법
3. 시스템 구조
4. 데이터와 API 설계
5. 핵심 구현과 기술적 고민
6. 테스트와 배포
7. 회고와 개선 과제

팀원이 내용을 추가하거나 고칠 수 있도록 구현 상태표, 최초 실행 준비표, API 예시, 업무 규칙표, 검증 결과표 자리를 마련했다.

기술 선택도 사용한 기술 이름만 나열하지 않고 이 흐름으로 설명하도록 정리했다.

문제 → 선택한 방법과 이유 → 효과와 제약

## 문서 서식과 이미지 배치

폰트가 환경에 따라 다르게 표시되는 문제가 있어서 문서 폰트를 맑은 고딕으로 통일하기로 했다. 여백과 문단 간격을 조정하고, 제목·표·설명이 페이지에서 어색하게 갈라지지 않도록 정리했다.

직접 넣은 이미지도 본문 흐름에 맞게 배치했다.

- 이미지 크기를 본문 폭에 맞춤
- 캡션이 이미지와 함께 이동하도록 조정
- 상태 흐름도는 글씨를 읽을 수 있도록 별도 페이지에 배치

이미지는 넣는 것만으로 끝나지 않았다. 무엇을 보여 주는 이미지인지 설명하고 본문과 연결해야 했다.

## 실행 설정을 필수와 선택으로 나누기

프로젝트 실행에 꼭 필요한 설정과 특정 기능을 쓸 때만 필요한 설정을 구분했다. 선택 환경변수 13개는 세 묶음으로 정리했다.

- AI·소셜 로그인
- 카카오페이·토스 테스트 결제
- 가입 크레딧

각 변수에는 용도, 설정 조건, 기본값, 설정하지 않았을 때의 동작을 적었다. 변수 이름만 적으면 처음 실행하는 사람은 이걸 꼭 채워야 하는지 판단하기 어렵다. 어떤 기능에 필요하고 비워 두면 어떻게 되는지까지 있어야 판단할 수 있다.

<br/>

## 문서 설명을 최신 코드와 대조하기

문서를 쓰는 동안에도 기능 구현이 계속 바뀌어서, 기존 설명이 최신 코드와 맞는지 확인했다.

- **결제** => 크레딧 결제와 PG 테스트 결제는 지원하므로, PG 연동 전체가 미구현인 것처럼 적지 않도록 수정할 내용을 정리했다. 실제 금전 거래 전환, PG 환불, 은행 송금 연동은 남은 과제로 구분했다.
- **ERD** => 전체 테이블을 보여 주는 그림인지 핵심 관계만 요약한 그림인지 밝혀야 했다. 핵심 테이블 19개만 보여 주는 ERD에는 생략한 범위를 설명하도록 했다.
- **측정 수치** => AI 모델의 메모리 사용량처럼 측정 근거를 확보하지 못한 수치는 확정적으로 쓰지 않도록 교체 문구를 마련했다.

## 캡처와 테스트 결과의 범위 구분

> 성공 화면 하나만으로 전체 기능이 검증됐다고 설명할 수는 없다.

문서에 넣을 화면과 결과를 준비하면서 어떤 환경에서 나온 것인지 나눴다.

- 배포 서버의 실제 데이터로 조회한 화면
- 배포 서버의 컨테이너 실행 상태
- 같은 모집에서 참여 확정·피드백 제출·재조회를 확인한 화면
- 로컬 시연 데이터를 사용한 E2E 테스트 결과

로컬 시연 데이터로 통과한 테스트를 실제 백엔드·DB 연동 검증처럼 적지 않도록 캡션을 구분했다.

검사와 배포 결과도 같은 커밋의 기록인지 확인하고, 실행일·커밋·실행 링크를 남기도록 정리했다. 현재 시각을 출력한 결과는 서버가 시작된 시각이 아니라 캡처한 시각이라는 점도 구분했다.

# 배운 점 & 느낀 점

문서 작성이 생각보다 어려웠다. AI의 도움을 받았는데도, 문서에 맞는 크기와 화질로 캡처하려면 개발자 도구로 화면 크기를 조절해서 명령어로 캡처해야 했다. 터미널을 찍을 때는 출력 결과가 잘 보이도록 배율도 조절해야 했다.

이런 작업이 은근히 시간을 많이 잡아먹었다. AI도 도입됐으니, 이런 부분을 좀 더 편하게 할 수 있는 방법을 강구해야겠다는 생각을 했다.
