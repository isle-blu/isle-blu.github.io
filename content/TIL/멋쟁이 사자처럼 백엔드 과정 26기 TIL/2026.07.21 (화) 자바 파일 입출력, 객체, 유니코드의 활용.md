# 유니코드 저장 방식

> 유니코드의 저장 방식은 BE와 LE가 있다.

![이미지](https://cdn.likelion.net/classroom/kdt-backendj-26th/til/6f579044-4ca2-44f5-a285-7c3fa65f3dbe.png)

---

- 엔디안 : 여러 바이트로 이뤄진 값을 저장할 때, 어느 바이트를 먼저 놓을지 정하는 규칙
    - 앞자리 혹은 뒷자리를 먼저 저장하는 지에 따라 효율이 달라지기에 이것에 대한 논쟁이 많았다.
    - 현재 LE(Little Endian)이 대중적으로 많이 사용되고, BE(Big Endian)은 일부에서 사용된다.
- 유니코드 UTF-16과 UTF-32는 2바이트 이상을 사용한다. 그래서 저장할 때 어느 바이트를 앞에 쓸 것인가를 정해야한다.
- 컴퓨터의 입출력은 항상 **1byte** 씩 가능하다. 이 1byte 씩 보내는 것을 어떤 순서로 할지 정하는 것이 엔디안이다.

> 유니코드 숫자 저장에 대한 고민

- 유니코드는 문자를 숫자 형태의 코드로 전환한다. => 그럼 실제 숫자를 숫자 형태의 코드로 바꿔야할까?
- 그래서 Binary 저장 방식과 Text 저장 방식으로 논쟁이 생겼다.
- 각각의 장단점이 있기에 상황에 따라 저장 방식을 다르게 했다.

|관점|텍스트(문자열) 저장|바이너리(값) 저장|
|---|---|---|
|장점|사람이 열어 바로 확인하기 쉽습니다.|저장 용량과 처리 효율이 유리한 경우가 많습니다.|
|단점|숫자 저장도 문자 코드로 변환되어 공간 낭비가 생깁니다.|사람이 읽기 어렵고 해석 규약(엔디안 등)이 필요합니다.|
|대표 사례|CSV, 로그, 설정 파일 등이 해당됩니다.|이미지, 오디오, 실행 파일, 직렬화 데이터 등이 해당됩니다.|

# 객체 지향

## 함수

> 입력 값에 따라 출력값이 달라지는 것

![이미지](https://cdn.likelion.net/classroom/kdt-backendj-26th/til/c64d1400-1454-4b23-b86b-af93ff9f06c0.png)

- 프로그래밍에서 의미하는 수학에서 말하는 함수와 크게 다르지 않다.
- 하지만 프로그래밍에서는 반복되는 코드를 함수라는 형태로 묶어서 재사용하기 위해서 사용한다는 차이가 있다.
    - 코드 파편화 : 코드가 길어지는 것을 함수로 분리하여 구조화를 돕는다.
    - 코드 집중화 : 여러 곳에서 사용되는 코드를 함수로 묶어 재사용성을 높이고 유지보수를 편하게 한다.
    - 코드 은닉화 : 함수 내부를 감춰, 함수를 사용하는 사람은 내부를 볼 수 없다.

> 하지만 함수도 늘어나면 정리가 필요해진다.

- 이것을 어떻게 정리할 지 고려한 결과, 데이터(무엇)을 다루는 지를 기준으로 묶어서 정리했다.
- 함수는 행위, 행위의 주체는 역할자, 행위의 대상은 데이터로 설정한다.
- 여기서 주체는 개체(Entity)이고, 이 주체에 이름을 붙이고 실체를 구현하면 그것이 객체(object)가 된다.
