오늘은 Docker Compose로 여러 컨테이너를 함께 관리하는 방법과 Spring Security에서 사용자 인증 정보를 직접 제공하는 방법을 배웠다.

# Docker Compose

> 여러 컨테이너의 설정을 하나의 파일에 적고 함께 실행·관리하는 도구

DB → 백엔드 → 웹 서버처럼 서로 의존하는 컨테이너가 있다. 백엔드가 DB보다 먼저 시작되면 연결 과정에서 문제가 생길 수 있으므로, Compose에서는 의존 관계를 설정해 실행 순서를 관리한다. 종료할 때는 실행할 때의 역순으로 내린다.

## Compose의 네트워크

Compose는 기본적으로 서비스들이 함께 사용할 네트워크를 만든다. 같은 네트워크에 있는 컨테이너는 `db`처럼 **서비스 이름**으로 서로를 찾을 수 있다.

처음에는 컨테이너들이 같은 IP를 쓰기 때문에 이름을 붙이는 것으로 이해했다. 정확히는 각 컨테이너가 **서로 다른 내부 IP**를 받는다. 컨테이너를 다시 만들면 IP가 바뀔 수 있으므로, 연결할 때는 IP보다 서비스 이름을 사용하는 것이다.

컨테이너 내부의 포트는 호스트의 포트와 구분된다. 하지만 `ports`로 호스트에 공개한 포트는 이미 사용 중인 호스트 포트와 충돌할 수 있다.

<br/>

## Compose 파일 작성

```yaml
version: '3.8' # 이젠 사용하지 않는 옵션

services:
  # 1. PostgreSQL 데이터베이스 상자 설정
  postgres-db:
    image: postgres:16
    container_name: my-postgres
    environment:
      POSTGRES_DB: mydatabase
      POSTGRES_USER: myuser
      POSTGRES_PASSWORD: mypassword
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data

  # 2. 스프링 부트 백엔드 앱 상자 설정
  backend-app:
    build: .
    container_name: my-backend
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres-db:5432/mydatabase
      SPRING_DATASOURCE_USERNAME: myuser
      SPRING_DATASOURCE_PASSWORD: mypassword
    depends_on:
      - postgres-db

# 3. 데이터베이스 데이터를 보존하기 위한 공간 선언
volumes:
  postgres_data:
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

`services`에는 실행할 서비스를 정의하고, 맨 아래의 `volumes`에는 사용할 이름 있는 볼륨을 선언한다. 예시에서는 `postgres_data`를 선언한 뒤 PostgreSQL 컨테이너의 데이터 저장 경로에 연결했다.

> [!note] `version` 옵션
> 예전에는 `version: '3.8'`처럼 Compose 파일의 형식 버전을 적었다. Docker Compose가 업데이트되면서 파일 형식이 Compose Specification으로 통합되어, 지금은 `version`을 사용하지 않는다.

서비스 안에서 사용한 항목도 정리했다.

| 항목 | 역할 |
|---|---|
| `image` | 사용할 이미지를 지정한다. 로컬에 없으면 레지스트리에서 가져온다. |
| `build: .` | 현재 경로의 `Dockerfile`을 기본으로 사용해 이미지를 만든다. |
| `environment` | 실행되는 컨테이너에 환경 변수를 설정한다. |
| `ports` | `호스트 포트:컨테이너 내부 포트` 형식으로 연결한다. |
| `volumes` | 볼륨과 컨테이너 안에서 연결할 경로를 지정한다. |
| `container_name` | 자동으로 생성되는 이름 대신 컨테이너 이름을 직접 지정한다. |
| `depends_on` | 적어 둔 서비스가 먼저 시작되도록 의존 관계를 설정한다. |

> [!note] `healthcheck`로 DB 준비 완료 확인
> 위 예시처럼 `depends_on`에 `- postgres-db`를 적으면 DB 컨테이너가 **시작될 때까지만** 기다린다.
> 시작됐다고 해서 바로 연결할 준비가 끝난 것은 아니다.<br/><br/>
> PostgreSQL 서비스에 `healthcheck`를 정의해 연결 가능 여부를 확인하고, 백엔드의 `depends_on`에 `condition: service_healthy`를 지정하면 DB가 정상 상태가 된 뒤 백엔드를 시작할 수 있다.
> 예를 들어 `pg_isready`로 PostgreSQL이 연결을 받을 준비가 되었는지 검사한다.

# Spring Security

> **인증**은 사용자가 누구인지 확인하는 과정이고, **인가**는 그 사용자가 요청한 곳에 접근할 수 있는지 판단하는 과정이다.

## URL별 접근 권한 설정

처음에는 모든 페이지에서 로그인을 요구했다. 공개 페이지와 로그인한 사용자만 볼 수 있는 페이지를 구분하려면 URL별로 인가 규칙을 설정해야 했다.

- `permitAll()` : 로그인하지 않아도 접근할 수 있다.
- `authenticated()` : 로그인한 사용자만 접근할 수 있다.
- `hasRole("ADMIN")` : 해당 역할을 가진 사용자만 접근할 수 있다.


```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/", "/css/**", "/js/**").permitAll()
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .requestMatchers("/my/**").authenticated()
    .anyRequest().authenticated()
);
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

로그인 화면도 직접 만든 페이지에서 사용할 수 있도록 `formLogin` 설정을 수정했다. 이번에 중요했던 점은 **어떤 페이지를 공개할지 정하는 것**과 **로그인을 어디에서 처리할지 정하는 것**이 별개의 설정이라는 것이다.

```java
http.formLogin(form -> form
    .loginPage("/login")
    .permitAll()
);
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

## 커스텀 `UserDetails`와 `UserDetailsService`

이전에는 `InMemoryUserDetailsManager`에 계정을 직접 등록했다. 이번에는 계정 정보를 직접 제공하기 위해 `UserDetails`와 `UserDetailsService`를 구현하는 방법을 배웠다.

> `UserDetails`는 Spring Security가 인증에 사용할 사용자 정보의 규격이다. `UserDetailsService`는 로그인할 때 그 사용자 정보를 찾아 반환하는 역할을 한다.

그런데 로그인 후 이름이나 닉네임을 화면에 보여주려면 어떻게 해야 할까? `UserDetails`를 직접 구현하면 로그인 아이디, 비밀번호, 권한뿐 아니라 이름·닉네임도 함께 담아둘 수 있다.

**CustomUserDetails.java 예시**

```java
package com.example.security.user;

import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.userdetails.UserDetails;

import java.util.Collection;

public class CustomUserDetails implements UserDetails {
    private final String username; // 로그인 아이디
    private final String password; // 암호화된 비밀번호
    private final String name;     // 사용자 이름 (추가 정보)
    private final String nickname; // 닉네임 (추가 정보)
    private final Collection<? extends GrantedAuthority> authorities; // 권한 목록

    public CustomUserDetails(String username, String password, String name, String nickname, Collection<? extends GrantedAuthority> authorities) {
        this.username = username;
        this.password = password;
        this.name = name;
        this.nickname = nickname;
        this.authorities = authorities;
    }

    // 커스텀으로 추가한 Getter 메서드
    public String getName() {
        return name;
    }

    public String getNickname() {
        return nickname;
    }

    // UserDetails 인터페이스 필수 구현 메서드들
    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return authorities;
    }

    @Override
    public String getPassword() {
        return password;
    }

    @Override
    public String getUsername() {
        return username;
    }

    // 계정 만료 여부 (true: 만료 안 됨)
    @Override
    public boolean isAccountNonExpired() {
        return true;
    }

    // 계정 잠금 여부 (true: 잠기지 않음)
    @Override
    public boolean isAccountNonLocked() {
        return true;
    }

    // 비밀번호 만료 여부 (true: 만료 안 됨)
    @Override
    public boolean isCredentialsNonExpired() {
        return true;
    }

    // 계정 활성화 여부 (true: 활성화)
    @Override
    public boolean isEnabled() {
        return true;
    }
}
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

`CustomUserDetailsService`에서는 `loadUserByUsername()`을 구현했다. 이 메서드가 사용자를 찾아 `CustomUserDetails`를 반환하고, 사용자를 찾지 못했다면 `UsernameNotFoundException`을 던진다.

<br/>

**CustomUserDetailsService.java**

```java
package com.example.security.user;

import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class CustomUserDetailsService implements UserDetailsService {

    // 실제 프로젝트에서는 JPA Repository나 MyBatis Mapper 등을 주입받아 사용한다.
    // private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {

        // 1. DB에서 username으로 회원 정보를 조회하는 과정을 시뮬레이션한다.
        // 예: Member member = userRepository.findByEmail(username)
        //         .orElseThrow(() -> new UsernameNotFoundException("사용자를 찾을 수 없습니다: " + username));

        // 예시를 위한 임시 가상 DB 조회 처리
        if (!"newlec@newlecture.com".equals(username)) {
            // 사용자가 없으면 반드시 UsernameNotFoundException 예외를 던져야 한다.
            throw new UsernameNotFoundException("존재하지 않는 사용자입니다: " + username);
        }

        // DB에서 가져온 회원의 권한 정보 생성 (ROLE_ 접두사 사용)
        List<SimpleGrantedAuthority> authorities = List.of(new SimpleGrantedAuthority("ROLE_USER"));

        // 2. 조회한 DB 회원 정보를 커스텀 UserDetails 객체에 담아서 반환한다.
        // (주의: 비밀번호는 반드시 BCrypt 등으로 암호화된 상태로 DB에 들어있어야 한다)
        return new CustomUserDetails(
            "newlec@newlecture.com",
            "$2a$10$8.UnVuG9HHgffUDAlk8qfOUVGkqRzgVymGe07xd00DMxs.AQp.o.O", // "1111"의 BCrypt 암호화 값
            "뉴렉처",
            "newlec_nick",
            authorities
        );
    }
}
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

여기서는 실제 DB를 조회하는 대신 아이디가 일치하는지만 검사한다. 나중에 DB를 연결할 때는 이 부분에서 사용자를 조회한 뒤 `CustomUserDetails`로 변환하면 된다.

사용자가 없는 경우 `null`을 반환하는 대신 예외를 던져야 한다.

```java
throw new UsernameNotFoundException("사용자를 찾을 수 없습니다.");
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

기존의 메모리 사용자 설정을 빼고 커스텀 서비스를 사용한다면 보안 설정은 아래처럼 구성할 수 있다. 다만 여기의 `formLogin(Customizer.withDefaults())`는 **기본 로그인 화면을 사용하는 코드**다. 내가 앞에서 설정한 커스텀 로그인 화면과는 구분해서 봐야 한다.

<br/>

**SecurityConfig.java — 예시**

```java
package com.example.security.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(authorize -> authorize
                .requestMatchers("/", "/menus", "/menus/*").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .requestMatchers("/my").hasRole("USER")
                .anyRequest().authenticated()
            )
            .formLogin(Customizer.withDefaults());

        return http.build();
    }
}
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

<br/>

인증 후 `Authentication`의 principal을 커스텀 타입으로 꺼내면 추가한 이름과 닉네임에 접근할 수 있다.

```java
Authentication authentication = SecurityContextHolder.getContext().getAuthentication();
CustomUserDetails userDetails = (CustomUserDetails) authentication.getPrincipal();

System.out.println("로그인한 사용자 이름: " + userDetails.getName());     // 뉴렉처
System.out.println("로그인한 사용자 닉네임: " + userDetails.getNickname()); // newlec_nick
```

*코드 출처: [뉴렉처](https://newlecture.com/)*

비밀번호도 구분해서 이해했다. DB에는 평문이 아닌 해시 값을 저장하고, 로그인할 때 입력한 비밀번호와 저장된 해시를 `PasswordEncoder`로 검증한다. 이 과정은 권한을 판단하는 **인가가 아니라 인증**에 해당한다.

# 오늘 느낀 점

도커 컴포즈는 그동안 주어진 설정을 그대로 사용해서 크게 신경 쓰지 않았다. 그런데 이번에 어떤 일을 해주는지 배우고 나니 예상보다 편리한 도구라 놀랐다. 의존 관계를 잘 설정하면 컨테이너를 실행하고 종료할 때 생기는 문제도 많이 줄일 수 있겠다고 느꼈다.

스프링 시큐리티에서는 드디어 내가 만든 로그인 화면에서 로그인할 수 있겠구나 싶어 좋았다. 그동안 모든 화면에서 로그인을 요구해 불편했는데, URL별 권한과 `formLogin` 설정으로 이 문제를 해결하는 과정을 겪으니 이해가 더 잘되는 것 같았다.
