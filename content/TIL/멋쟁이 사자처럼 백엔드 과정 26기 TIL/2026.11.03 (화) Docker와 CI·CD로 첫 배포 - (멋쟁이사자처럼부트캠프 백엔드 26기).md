# 오늘의 상황

> 오늘은 Docker로 실행 환경을 만들고, CI/CD를 붙여서 테스트 서버에 첫 배포를 했다.

- CI/CD 작업은 이번이 처음이었다.
- 저녁에는 크레딧 PR을 마무리하고, 이슈 템플릿과 문서 구조를 정리했다.

# 오늘의 과정

## Docker로 실행 환경 만들기

> 백엔드, 프론트엔드에 각각 Dockerfile을 만들고, compose 파일은 세 개로 나눴다.

- **기본** : 공통 설정
- **개발용** : 소스 폴더를 컨테이너에 붙임 => 저장하면 바로 반영
- **운영용** : 빌드 없이 이미지 저장소에서 받은 이미지로 띄움

요청 흐름은 `브라우저 → nginx → frontend → backend → db`

- 백엔드는 프론트가 서버 안에서 부르는 구조(BFF) => 백엔드 포트는 밖에 열지 않았다.

## CI/CD 붙이기

- **CI** : PR이 올라오면 4가지를 검사
    - 프론트 lint·build, 백엔드 테스트, 백엔드·프론트 Docker 빌드
- **CD** : develop에 머지되면 이미지 빌드 → GHCR에 올림 → 서버에서 새 이미지로 다시 띄움 → 응답 확인
- release 브랜치는 쓰지 않기로 했다. => 테스트 서버에는 develop만 배포

> 배포로 컨테이너가 새로 뜨면 IP가 바뀔 수 있지 않을까?

- nginx는 시작할 때 찾은 IP를 계속 쓴다. => 에러가 나기 전에 미리 resolver를 설정해서, nginx가 새 IP를 다시 찾을 수 있게 했다.

<br/>

## 서버 배포에서 막힌 부분

### 1. docker 권한

> 서버에서 docker를 실행했는데 왜 `permission denied ... docker.sock`이 났을까?

- SSH 문제가 아니라, 계정이 docker 그룹에 없어서였다.
- 계정을 docker 그룹에 넣고 다시 로그인 => 해결

```bash
sudo usermod -aG docker <계정>
```

### 2. 호스트 nginx 라우팅

> 강의 문서의 설정 스크립트, 그대로 실행해도 될까?

- 안 된다. 스크립트는 **새 서버를 전제**로 하고 있었다.
    - 그대로 돌리면 계정을 새로 만들고, 기존 nginx 기본 설정까지 지워 버린다.
    - 우리 서버는 다른 팀과 같이 쓰는 공유 서버 => 다른 팀 설정까지 영향을 줄 수 있음
- 그래서 스크립트로 설정 내용만 생성하고, 다른 팀처럼 팀 이름으로 설정 파일을 따로 만들었다.
- `nginx -t`로 검사 → reload
- 라우팅을 먼저 해 두고, 그다음에 certbot으로 HTTPS 인증서를 발급했다.

### 3. 패키지 비공개로 첫 배포 실패

> 저장소를 공개했는데 왜 배포가 실패했을까?

- 저장소를 공개해도 **GHCR의 이미지 패키지는 기본이 비공개**였다.
- 비공개면 서버에서 이미지를 받을 때 로그인이 필요 => 첫 배포 실패
- 패키지 두 개를 공개로 바꾸고 실패한 job만 다시 실행 => **첫 배포 성공!**
    - HTTPS로 정상 응답, http로 들어오면 https로 넘어가는 것까지 확인했다.

### 마무리

- develop과 main에 브랜치 보호 규칙 설정
    - 직접 push 금지, CI 검사 4개 통과, 팀원 1명 승인이 있어야 머지 가능
- README에 Docker 실행 방법 정리

## 저녁 작업

- 크레딧 PR : develop과 충돌이 늘어나서 다시 합침 → 어떻게 합쳤는지 리뷰 답글로 설명 → 머지
- 프로젝트 보드에 빠져 있던 이슈 6개를 옮겼다.
- 문서 위치와 이름 규칙 정리, 중복된 e2e 정리 (아직 push 전)
- 팀원 PR 리뷰 : 번호를 일괄로 바꾸면서 다른 문서의 번호까지 잘못 바뀐 부분을 짚었다.

## 오늘의 결정

> 이슈 템플릿 3개(기능 요청, 버그 제보, 작업 이슈)를 만들었다.

- **상황** : 처음엔 Given/When/Then, 완료 조건, 범위, 단계 칸까지 넣었다.
- **무엇으로 바꿨나** : 사용자 시나리오 중심으로 줄였다. => 템플릿마다 필수 2칸, 참고 1칸
- **왜** : 이슈는 해야 할 일을 정하는 곳이지, 모든 계획을 담는 곳이 아니라고 생각했다.

# 배운 점 & 느낀 점

> 오늘 진짜 배운 건 **GHCR 같은 이미지 저장소를 왜 써야 하는지**와 **CI/CD를 어떻게 설정하는지**였다.

| 방식 | 공유 서버 부담 | 배포 속도 | 롤백 | 설정 난이도 |
|---|---|---|---|---|
| 이미지 저장소 (우리는 GHCR) | 낮음 | 빠름 | 쉬움 | 중간 |
| 서버에서 빌드 | 높음 | 느림 | 어려움 | 쉬움 |

- 이미지 저장소를 쓰면 빌드는 CI에서 하고, 서버는 빌드된 이미지를 받아서 실행만 한다.
- 지금 서버는 다른 팀과 같이 쓰는 공유 서버 => 서버에서 빌드하면 부담이 커진다.
- 빌드된 이미지를 받기만 하니까 배포도 빠르고, 이미지 태그를 쓰니까 롤백도 쉽다.

CI/CD 작업 자체가 처음이라 더 어려웠다. 하지만 자동으로 배포하는 것은 생각보다 훨씬 편했다. 이미지 저장소 방식도 설정은 어려웠지만, 이것만 해 두면 그 뒤 관리가 매우 쉬워지고 속도도 빠르다는 점에서 앞으로도 계속 사용해야된다는 것을 확실히 느낀 것 같다. 앞으로 이 부분도 더 자세히 공부할 필요가 있을 거 같다.
