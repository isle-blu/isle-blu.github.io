오늘은 배포의 역사를 정리했다. 프로젝트에서 배포를 맡고 있어서, 배포가 어떻게 지금의 모습이 됐는지 공부해야 할 것 같았다. 배포의 역사는 각 시대의 배포 방식이 고통을 만들고, 그 고통을 없애려고 다음 방식이 나온 과정이다. 그래서 단계마다 **"무엇이 고통이었나 → 무엇을 해결했나 → 무엇이 남았나"** 를 따라가며 읽었다.

<br/>

# 배포란 무엇일까

> 처음 세운 정의 : 배포는 프로그램을 사용자가 사용할 수 있게 하는 것.

- 다듬은 정의 : 배포는 만든 프로그램(과 그 변경)을 **실행 가능한 환경에 올려서** 사용자가 쓸 수 있게 하는 과정이다.
- 여기에 두 가지 관점을 더했다.
    1. 마지막 단계를 누가 맡는가(개발자 몫이냐, 사용자 몫이냐)가 시대마다 다르다.
    2. 배포는 한 번으로 끝나지 않고, **변경을 계속 전달하는 일**이다.

## 배포의 두 층

1. **인프라 준비(프로비저닝)** : 서버를 마련하고 OS와 런타임을 설치하는 일
2. **앱 배포(디플로이)** : 그 위에 내 코드를 올리고 실행하는 일

- 가상화와 클라우드는 1층을 바꿨다.
- 2층은 CI/CD부터 본격적으로 바뀌었다.
- 컨테이너는 두 층을 **이미지 하나로** 합쳤다.

# 배포의 역사

> 연 단위로 디스켓을 출고하던 방식에서, 원하는 상태를 선언하면 시스템이 알아서 맞추는 방식으로 바뀌었다.

| 단계 | 시기 | 배포의 모습 | 남은 고통 (→ 다음 단계) |
| --- | --- | --- | --- |
| ① 패키지 소프트웨어 | 1970~90년대 | 디스켓이나 CD로 출고, 설치는 사용자가 직접 | 사용자 환경을 통제할 수 없고, 출고하면 되돌릴 수 없음 |
| ② 웹과 물리 서버 | 90년대 중반~2000년대 | FTP로 올리고 WAR를 복사해 재시작. 새벽에 수작업 | 서버 조달이 느리고, 자원이 낭비되고, 서버마다 상태가 다름 |
| ③ 가상화 | 2000년대 (VMware, Xen) | 물리 서버 한 대를 VM 여러 개로 나눠 씀 | 물리 용량의 한계, VM이 무거움 |
| ④ 클라우드 | 2006년 AWS EC2 이후 | API 호출 하나로 몇 분 만에 서버를 빌림 | 서버는 금방 생기는데 배포는 여전히 드물고 무서움 |
| ⑤ CI/CD와 DevOps | 2009~2011년쯤 | 커밋하면 빌드, 테스트, 배포가 자동으로 진행 | 개발 환경과 운영 환경의 차이 |
| ⑥ 컨테이너 | 2013년 Docker | 앱과 실행 환경을 이미지 하나로 묶음 | 컨테이너가 수백 개가 되면 사람이 관리 불가 |
| ⑦ 오케스트레이션과 그 이후 | 2014~15년 Kubernetes, 서버리스, GitOps | 원하는 상태를 선언하면 시스템이 맞춤 | 진행 중 |

- 연도는 공부하면서 정리한 대략적인 시기다. 출처를 따로 확인하지는 않았다.

# ① 패키지 소프트웨어 → ② 웹과 물리 서버

> 실행 환경이 사용자 PC에서 **회사가 통제하는 서버**로 옮겨갔다. => 버그를 한 곳에서 고치면 모든 사용자에게 바로 반영된다.

## ① 패키지 소프트웨어 (1970~90년대)

- 최종 빌드 확정(골드 마스터) → 디스켓이나 CD로 대량 복제 → 매장 유통 → 사용자가 직접 설치
- 사용자 PC의 OS와 하드웨어를 통제할 수 없었다. => 최소 사양 표기가 생기고, 호환성 테스트가 큰 비용이 됐다.
- 출고하면 **되돌릴 수 없었다.** 패치 디스크를 우편으로 보내거나 다음 버전을 기다려야 했고, 출시 주기는 연 단위였다.

## ② 웹과 물리 서버 (90년대 중반~2000년대)

- 개발자 PC에서 빌드 → FTP나 SSH로 업로드 → WAR를 톰캣에 복사 → 재시작. 보통 새벽에 점검 공지를 띄우고 진행했다.
- 개발자 PC와 서버가 서로 다른 컴퓨터였다. => 여기서 **"내 컴퓨터에선 되는데"** 가 생겼다.
- 브라우저 호환성 문제(IE 대 넷스케이프)는 여전했지만, 핵심 로직은 서버에서 실행됐다.
- 새로 생긴 고통은 네 가지다.
    - 서버 조달에 몇 주가 걸렸다.
    - 서버 한 대에 앱 하나만 올려서 CPU를 10~20%만 썼다.
    - 서버마다 상태가 달라졌다.
    - 개발팀과 운영팀 사이에 벽이 있었다.
- 더 전의 메인프레임도 중앙 컴퓨터에서 프로그램을 돌렸다. => 웹은 **중앙 집중으로 돌아간** 것이다.

## 스노우플레이크 서버

> 사람이 손으로 설치하고 패치하면서 고유한 상태가 쌓여, **똑같이 다시 만들 수 없게 된 서버**

- "세상에 똑같은 눈송이는 없다"는 비유에서 왔다. Martin Fowler의 글로 널리 퍼졌다.
- 해결책은 나중에 나오는 **불변 인프라**다. "서버를 애완동물이 아니라 가축처럼 다루라(Pets vs Cattle)"도 같은 맥락이다.
- 데이터 웨어하우스 회사 Snowflake는 이 용어와 상관없이, 창업자들의 스키 사랑과 "눈송이는 구름에서 태어난다"는 뜻으로 붙인 이름이다.

# ③ 가상화 → ④ 클라우드

> 두 단계 모두 **1층(인프라 준비)** 을 바꿨고, 2층(앱 배포) 절차는 거의 그대로였다.

## ③ 가상화 (2000년대)

> 한 대의 물리 컴퓨터를 여러 대의 완전한 컴퓨터처럼 보이게 만드는 것

- 하이퍼바이저가 CPU, 메모리, 디스크를 쪼개서 나눠 주고, VM마다 자기 OS를 통째로 갖는다.
- IBM 메인프레임은 1972년(VM/370)에 이미 가상화를 썼다. x86은 가상화가 어려웠는데 VMware(1999)와 Xen(2003)이 우회했고, 2005~06년 CPU가 가상화를 직접 지원하면서 보급됐다.
- 해결한 것
    - 서버 여러 대를 한 대로 합쳐 자원 낭비를 줄였다.
    - VM은 파일이라 스냅샷과 복제가 가능해졌다. => 배포 전 스냅샷으로 거칠게나마 되돌릴 수 있게 됐다.
- 남은 것 : 물리 서버는 여전히 직접 사야 했다. VM은 수 GB에 부팅이 몇 분이었고, VM 안의 설정은 사람 손으로 했다.

## 복사할 수 있다 ≠ 재현할 수 있다

> 가상화는 스노우플레이크 문제를 **일부만** 해결했다.

- 시작점이 다르다 → 해결됨. 골든 이미지를 복제하면 태어나는 순간에는 똑같다.
- 태어난 뒤 달라진다 → 해결 안 됨. 급한 패치와 설정 수정이 쌓이면 다시 제각각이 된다. => **구성 표류(configuration drift)**
- 골든 이미지 자체도 눈송이다. 어떻게 만들었는지는 만든 사람 머릿속에만 있다.

=> 복사는 결과물을 똑같이 찍어 내는 것이고, **재현은 만드는 방법을 알아서 언제든 처음부터 다시 만드는 것**이다. 재현은 ④의 구성 관리와 IaC, ⑥의 불변 인프라가 채운다.

## ④ 클라우드 (2006년~)

> 거대 기업이 가진 컴퓨터 자원을 쪼개서 빌려준다. => 사용자 입장에서는 용량의 끝이 사실상 없어진다.

- Amazon이 2006년 S3와 EC2를 공개했다. "연말에 남는 서버를 빌려줬다"는 이야기는 Amazon CTO가 부인했다.
- 바뀐 것
    - 서버 마련이 몇 주에서 **몇 분**으로 줄었다.
    - 선투자 대신 쓴 만큼만 내고, 트래픽에 따라 늘렸다 줄일 수 있다. (오토스케일링)
- 가장 중요한 변화는 **"API로 서버를 만든다"** 는 점이다. => 서버 생성이 함수가 되자 코드로 자동화할 수 있게 됐다.
- 그래서 재현 도구가 쏟아졌다.
    - 구성 관리 : Puppet(2005), Chef(2009), Ansible(2012)
    - IaC : CloudFormation(2011), Terraform(2014)

| 서비스 모델 | 무엇을 빌리나 | 예 |
| --- | --- | --- |
| IaaS | 서버만 | EC2 |
| PaaS | 실행 환경까지, 코드만 올린다 | Heroku(2007) |
| SaaS | 완성된 소프트웨어 | Gmail |

- 남은 것 : 서버는 몇 분이면 생기는데, 배포는 여전히 한 달에 한 번 새벽에 사람 손으로 했다.

# ⑤ CI/CD와 DevOps (2009~2011년쯤)

> 배포가 무서워서 드물게 하던 악순환을 **"아프면, 더 자주 하라(If it hurts, do it more often)"** 로 끊었다.

## 악순환

1. 배포가 무섭다. 되돌리기 어렵고 손으로 해서 실수가 난다.
2. 그래서 드물게 한다. (한 달에 한 번)
3. 한 번에 나가는 변경이 쌓인다.
4. 문제가 생기면 어느 변경이 원인인지 찾기 어렵다.
5. 배포가 더 무서워진다. => 다시 1번으로

- 여기에 **머지 지옥**(배포 직전 한꺼번에 합치며 터지는 충돌)과 개발팀·운영팀의 정반대 목표(빠른 기능 vs 안정)가 겹쳤다.

## 해결책 : 자주, 작게, 자동으로

| 개념 | 하는 일 | 이정표 |
| --- | --- | --- |
| CI (지속적 통합) | 하루에도 여러 번 메인 브랜치에 합치고, 합칠 때마다 자동 빌드와 테스트 | 1990년대 말 XP에서 시작, Hudson이 2011년 Jenkins로 이어짐 |
| CD (지속적 전달/배포) | 테스트를 통과한 결과물을 언제든 배포 가능한 상태로(전달), 더 나아가 자동으로 운영까지(배포) | 책 『Continuous Delivery』(2010) |
| DevOps | 개발과 운영의 벽을 허물고, 만든 사람이 운영까지 책임지는 문화 | 2009년 Flickr의 "하루 10번 이상 배포" 발표, DevOpsDays 시작 |

## 되돌리기를 쉬운 일로 만드는 배포 전략

- **블루-그린** : 구버전과 신버전을 둘 다 띄우고 트래픽만 넘긴다. => 롤백이 몇 초면 끝난다.
- **카나리** : 사용자 일부에게만 신버전을 먼저 내보내고 점점 늘린다. 탄광의 카나리아에서 온 이름이다.
- **롤링** : 서버를 한 대씩 차례로 교체한다.

> 남은 것

- 파이프라인은 빌드 결과물(JAR)만 옮긴다. => **"테스트 서버에서는 됐는데 운영에서는 터졌다"** 가 남았다.

# ⑥ 컨테이너 → ⑦ 오케스트레이션

> 컨테이너는 **환경까지 통째로 묶어** 옮기고, 오케스트레이션은 그 컨테이너들을 **사람 대신 관리**한다.

## ⑥ 컨테이너 (2013년 Docker)

- JAR가 돌려면 JDK 버전, OS와 시스템 라이브러리, 설정 파일과 환경 변수, 타임존과 로케일이 필요하다. 이 층들이 서버마다 달랐다. => 해답은 환경까지 통째로 묶어 옮기는 것이다.
- 규격이 정해진 해운 컨테이너처럼, 안에 뭐가 들었든 어디서나 똑같이 다룬다.
- VM과의 차이 : VM은 각자 OS를 통째로 갖고, 컨테이너는 **호스트 OS 커널을 공유**한다. => GB 대신 MB, 몇 분 대신 몇 초
- Docker가 처음은 아니었다. chroot(1979), FreeBSD jail(2000), 리눅스 namespaces와 cgroups, LXC(2008)가 있었다. Docker는 이걸 쓰기 쉽게 포장했다.
    - Dockerfile은 환경을 코드로 적는다. (재현)
    - 이미지는 변하지 않는 파일 하나다.
    - 레지스트리로 어디서든 받는다.
- 1층과 2층이 이미지 하나로 합쳐졌다. 실행 중인 컨테이너는 고치지 않고 새 이미지로 교체한다. => 이것이 **불변 인프라**이고, 스노우플레이크 문제의 완성된 해결책이다.
- 컨테이너는 리눅스 커널을 공유한다. 그래서 Mac이나 Windows에서 Docker를 돌리면 내부적으로 리눅스 VM 위에서 돌아간다. WSL을 Docker 엔진으로 쓰는 것도 "VM 위의 컨테이너"다.

## ⑦ 오케스트레이션 (2014~15년 Kubernetes)

> 서버 20대에 컨테이너 300개가 돌면, 사람이 하던 일을 Kubernetes가 대신한다.

- Google 사내 시스템 Borg의 경험에서 나왔고, 이름은 그리스어로 "조타수"다.

| 사람이 하던 일 | Kubernetes 기능 |
| --- | --- |
| 죽은 걸 알아채기 | 헬스 체크 (liveness/readiness probe) |
| 여유 있는 서버에 다시 띄우기 | 스케줄러, 자동 복구 |
| 몇 개로 늘릴지 판단하기 | 오토스케일러 (HPA) |
| 새 컨테이너로 트래픽 보내기 | Service (서비스 디스커버리, 로드밸런싱) |
| 롤링 배포 | Deployment |

- 핵심은 **명령에서 선언으로**의 전환이다.
    - "3번 서버에 하나 띄워"가 아니라 "항상 5개 있어야 해"라고 선언한다.
    - 시스템이 원하는 상태와 현재 상태를 계속 비교해서 맞춘다.

## 그 이후

- **서버리스** (AWS Lambda, 2014) : 함수만 올리고 실행된 만큼만 낸다.
- **GitOps** (2017) : 원하는 상태를 Git에 적으면 시스템이 따라간다. => 배포가 곧 커밋이다.
