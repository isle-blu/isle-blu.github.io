# 오늘의 과정

## CI의 DB 연결 부족

CI에서 DB 연결이 부족해졌다. 테스트 설정이 다르면 Spring 컨텍스트가 따로 만들어지는데, 컨텍스트마다 DB 연결 풀이 유지되면서 연결이 계속 쌓이고 있었다.

처음에는 테스트 컨텍스트 캐시 수를 제한해 봤다. 최종적으로는 그 설정을 제거하고 CI의 Hikari 풀 최대 크기를 5로 줄였다. 실패 원인도 로그에 전체가 나오도록 바꿨다.

## 채팅 화면을 실제 백엔드에 연결하기

이슈 54를 작업하면서 목업으로 동작하던 채팅함과 채팅방을 실제 API에 연결했다.

- 채팅함 검색·역할 필터·정렬
- 최근 메시지 조회와 이전 메시지 더 보기
- 메시지 전송, 채팅방 이름 변경·삭제
- 종료된 채팅방의 읽기 전용 표시
- 메시지 최대 10,000자 제한 반영

API를 연결하면서 실패했을 때의 화면도 정해야 했다. 메시지를 보내지 못하면 작성한 글을 입력창에 돌려주고, 조회에 실패하면 빈 목록과 구분해서 보여 주도록 했다.

서버에서 다시 받은 메시지 목록과 화면에 남아 있는 목록을 어떻게 합칠지도 정했다. 순번이 겹치면 중복을 제거하고, 두 목록 사이에 공백이 생기면 서버 목록으로 교체하기로 했다.

## 실시간 채팅과 읽음 처리

SSE로 메시지와 읽음 이벤트를 받아 화면에 반영했다.

- 로그인한 일반 회원의 탭마다 SSE 연결 하나 유지
- 새 메시지와 재연결 시 빠진 메시지 조회
- 채팅함 카드와 헤더의 안 읽은 메시지 수 갱신
- 화면에 표시된 마지막 메시지 순번으로 읽음 처리
- 상대가 아직 읽지 않은 내 메시지에 1 표시

읽음 처리는 채팅방이 실제로 보이는 탭에서만 하도록 했다. 다른 탭 뒤에 가려져 있으면 읽었다고 처리하지 않는다.

스크롤도 조건을 나눴다. 최근 대화를 보고 있으면 새 메시지로 이동하지만, 지난 대화를 읽는 중에는 위치를 유지한다. 이때 새 메시지가 붙기 전의 스크롤 거리로 판단해야 긴 메시지가 들어와도 의도대로 동작한다.

일시적인 서버 오류는 1 → 2 → 4 → 8 → 16 → 30초 간격으로 재시도하고, 읽음 처리의 인증 오류나 404는 재시도하지 않도록 했다.

## 테스트 서버에서 실시간 메시지가 안 올 때

이렇게 연결한 실시간 채팅이 테스트 서버에서는 제대로 동작하지 않았다. 채팅을 보내면 상대 화면에 메시지가 바로 뜨지 않고, 새로고침해야 보였다. 내가 보낸 메시지는 알림 없이 바로 화면에 붙으니까 상대 메시지만 안 보이는 증상이 나왔다.

> 로컬에서는 됐는데 테스트 서버에서만 안 된다 => 코드보다 앞단(nginx)을 의심해볼 만하다

서버 앞단의 nginx에 SSE 경로 설정이 없었다. nginx는 기본적으로 응답을 모았다가 내보내기 때문에, 조금씩 와야 하는 알림이 브라우저까지 바로 오지 않을 수 있다.

처음에는 `proxy_buffering off`만 넣었는데 해결되지 않았다. 설정에 `Connection "upgrade"`가 들어가 있었는데, 나는 이 설정을 몰랐다. 주석에 웹소켓에 대한 설명이 적혀 있어서 웹소켓 설정이라는 걸 알게 됐고, 찾아보고 나서야 무슨 설정인지 알았다. SSE에서는 이 설정 때문에 안 된 것이었다. 그래서 기존 `location /`와 별도로 SSE 경로를 따로 빼고, 필요한 설정을 함께 넣었다.

```nginx
location ^~ <SSE 경로> {
    proxy_pass <기존 값>;

    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host  $host;

    proxy_http_version 1.1;
    proxy_set_header Connection "";

    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 1h;
    gzip off;
}
```

- `proxy_buffering off` => 응답을 모으지 않고 바로 보낸다
- `Connection ""` => 웹소켓처럼 연결을 전환하지 않고 HTTP를 그대로 쓴다
- `proxy_read_timeout 1h` => 기본값은 60초라서, 그동안 데이터가 없으면 연결이 끊긴다
- `location ^~` => 정규식 location이 있어도 이 경로를 먼저 고른다

`proxy_set_header`를 블록 안에 하나라도 쓰면 바깥 값을 물려받지 않는다. 그래서 기존 `location /`의 헤더를 다시 적어야 했다.

공유 서버라서 조심할 부분도 있었다. 우리 `server` 블록 안의 이 경로에만 적용되니 다른 팀 설정은 바뀌지 않지만, reload는 서버 전체에 적용되니까 `nginx -t`로 먼저 검사해야 한다. 백업을 `sites-enabled`에 두면 설정으로 같이 읽힐 수 있어서 홈 폴더에 두는 게 좋다.

다만 여러 설정을 한 번에 넣어서 고쳤기 때문에 설정을 하나씩 따로 확인해 보지는 못했다. 다음에 비슷한 문제가 생기면 개발자 도구에서 SSE 요청에 응답이 오는지부터 봐야겠다.

## 채팅함 미리보기 응답 줄이기

채팅함 카드는 최근 메시지를 한 줄만 보여 주는데, API는 최대 10,000자 전체를 내려주고 있었다.

그래서 SQL 조회 단계에서 최근 메시지의 앞 100자만 가져오도록 바꿨다. 방 100개가 모두 10,000자 한글 메시지로 끝난다면, 최근 메시지 본문 합계가 약 3MB에서 약 30KB로 줄어드는 계산이다.

서비스 계층에서 자르면 DB에서 애플리케이션까지는 전체 내용이 넘어오니까 쿼리에서 잘랐다. 100자·101자 경계와 이모지가 걸리는 경우를 테스트했고, 메시지 상세 조회는 전체 내용을 그대로 유지했다.

공백 없는 긴 글에도 말줄임표가 보이도록 카드에 `overflow-wrap: anywhere`를 추가했다.

## 모집 관리 화면에서 채팅 시작하기

이슈 195를 작업하면서 지원자 목록, 피드백 카드, AI 추가 질문 대화상자와 AI 버전 비교 화면에서 채팅을 시작할 수 있게 연결했다.

채팅 시작에는 피드백 ID가 아니라 참가 ID가 필요해서 피드백 목록과 AI 그룹 리뷰 응답에도 이 값을 추가했다.

- 성공하면 해당 채팅방으로 이동
- 기존 방이 있으면 같은 방으로 이동
- 실패하면 이유를 보여 주고 현재 화면 유지
- 요청 중에는 중복 클릭 방지

모집 화면에서 채팅 기능을 호출하되, 두 기능 모듈이 서로 직접 의존하지 않도록 화면 쪽에서 연결했다.

### 채팅 시작 입력 검증과 실패 안내

화면에서 정해진 값을 넘기더라도 서버 액션에서 입력을 다시 검사하도록 보완했다. 기존 검사 조건은 그대로 두고 단위 테스트로 확인할 수 있도록, 참가 ID와 돌아올 주소를 검사하는 코드를 함수로 분리했다.

- 참가 ID는 숫자로만 이루어진 문자열인지 확인
- 돌아올 주소는 모집 관리 경로로 시작하는지 확인
- 조건을 통과하지 못하면 채팅 시작 요청을 보내지 않고 안내 반환

입력 검사에 실패했을 때의 안내도 고쳤다. 기존 문구에 연결된 오류 코드는 백엔드에서 참가 상태가 채팅 조건을 만족하지 않을 때도 쓰는 코드였다. 그래서 액션 인자가 잘못된 경우에는 공통 문구를 보여 주도록 바꿔서, 입력 형식 오류와 실제 참가 상태 오류의 안내를 나눴다.

단위 테스트에는 아래 입력을 넣었다.

- 정상적인 숫자 문자열과 모집 관리 주소
- 문자가 섞인 ID, 빈 문자열, 숫자 타입, undefined
- 로그인 경로, `//`로 시작하는 주소, 끝의 `/`가 빠진 모집 관리 경로처럼 허용하지 않는 주소

마지막으로 채팅 버튼 브랜치를 최신 develop 기준으로 rebase했고, 백엔드의 참가 ID 추가와 화면 연결까지 모두 병합했다.

# 배운 점 & 느낀 점

오늘 가장 기억에 남는 건 CI의 DB 연결 부족이었다. DB 연결에 제한이 있다는 것도 이번에 처음 알았다. 테스트의 DB 연결 수는 풀 하나의 크기뿐 아니라, 동시에 유지되는 컨텍스트 수까지 함께 봐야 한다. 사소하지만 놓치기 쉬운 부분이라 기억해 둬야겠다고 생각했다.

실시간 채팅을 테스트 서버에 올렸을 때는 nginx 설정에서 한 번 더 막혔다. `proxy_buffering off`를 넣고도 안 됐을 때는 진짜 뭔가 잘못된 줄 알았다. `upgrade` 설정도 몰랐는데, 주석 덕분에 웹소켓 설정이라는 걸 알게 됐고 찾아보고 나서야 이해했다. 이 설정이 들어가 있어서 SSE에서 안 된 것이었다.

이제 각 설정이 어떤 건지 확인하고 기억하는 게 앞으로 내가 해야 할 일인 것 같다. 그래야 같은 문제가 다음에 생기지 않을 테니까. 이건 별도로 블로그에 기록해 둬야겠다.
