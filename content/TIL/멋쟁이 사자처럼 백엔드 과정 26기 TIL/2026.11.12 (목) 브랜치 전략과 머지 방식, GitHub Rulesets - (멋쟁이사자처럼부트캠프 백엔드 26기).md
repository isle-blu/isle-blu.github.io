# 오늘의 상황

> 새 프로젝트가 시작됐다. 코드를 쓰기 전에 팀이 함께 쓸 저장소의 **브랜치 전략과 보호 규칙**부터 세웠다.

- 여러 명이 한 저장소에서 바로 작업을 시작하려면, 브랜치를 어떻게 나누고 어떤 방식으로 머지할지부터 정해야 했다.
- 그래서 브랜치 전략, GitHub 보호 규칙, 이슈·PR 템플릿, CI를 먼저 만들고, 주말 분담안도 정리했다.

---

# 오늘의 과정

## 브랜치 전략

> 소규모 팀 프로젝트라서 Git Flow에서 release 브랜치를 빼고 `main`, `develop`, `feature`, `hotfix`만 쓰기로 했다.

<br/>

## 오늘의 결정

- **상황** : develop과 main은 계속 살아 있는 브랜치인데, 머지 방식을 정하지 않으면 PR마다 다르게 머지될 수 있었다.
- **무엇으로 바꿨나** : 브랜치 방향마다 머지 방식을 나눴다.
    - feature → develop => **Squash merge**
    - develop → main, hotfix → main, main → develop => **Merge commit만**
- **왜** : Squash merge와 Rebase and merge는 **커밋 해시를 새로 만든다.**
    - develop과 main은 계속 쓰는 브랜치라서, 해시가 새로 만들어지면 두 브랜치의 히스토리가 갈라진다. => 다음 PR부터 이미 반영한 커밋이 또 나오거나 충돌이 난다.
    - 반대로 feature → develop은 PR 하나가 커밋 하나가 돼서 깔끔하다. 대신 PR 제목이 그대로 develop의 커밋 메시지가 되니까, **PR 제목 형식이 중요해진다.**

<br/>

## 그 밖의 주의사항

1. 여러 명이 같이 쓰는 feature 브랜치에서는 **rebase나 force push를 하지 않는다.** => 다른 사람의 로컬 히스토리가 깨진다. develop의 최신 내용은 merge로 받는다.
2. `origin/develop`에서 새 브랜치를 만들면 **upstream을 해제**한다. => 안 하면 실수로 `git push`를 했을 때 develop으로 올라갈 수 있다.

```bash
git branch --unset-upstream
```

<br/>

## GitHub 설정

### 기본 브랜치를 develop으로

- PR을 열 때 기본 base가 develop이 된다. => 실수로 main에 PR을 여는 일이 줄어든다.

### 템플릿은 기본 브랜치에 있는 파일을 읽는다

> 이슈·PR 템플릿과 `issues` 이벤트 워크플로는 PR의 base 브랜치가 아니라 **기본 브랜치**의 파일을 읽는다.

- 오늘 직접 겪은 실수였다. 템플릿을 feature 브랜치에만 올려 두니 적용되지 않았다.

### Rulesets로 브랜치 보호

> 브랜치 보호 규칙을 묶어서 걸 수 있는 GitHub 기능

- 삭제 금지, force push 금지
- PR 필수와 승인 1명
- 새 커밋을 올리면 기존 승인 취소(dismiss stale approvals)
- 허용할 머지 방식 => 브랜치마다 다르게 정할 수 있다. develop은 squash와 merge, main은 merge만 허용했다.
- 필수 CI 검사 => CI가 한 번 돌아서 검사 이름이 생긴 뒤에야 지정할 수 있다. 그래서 빈 프로젝트 PR을 먼저 머지해서 CI가 처음 도는 지점을 만들었다.

> "머지 전 최신 상태 요구(Require branches to be up to date)"는 켜야 할까?

- 켜지 않았다.
- 켜면 누가 머지할 때마다 열려 있는 PR을 모두 갱신하고 CI를 다시 돌려야 한다. => 작은 팀에서는 비용이 효과보다 크다.

> 규칙은 일찍 걸어 두자

- Rulesets를 걸기 전에 머지된 PR #1은 의도와 달리 Merge commit으로 머지됐다. 규칙이 없을 때라 막을 수 없었다.

<br/>

## GitHub Actions

- **이슈·PR 메타 워크플로** : 연 사람을 담당자로 지정하고, 제목의 유형(`Feat:` 등)으로 라벨을 붙인다.
- **CI** : 프론트는 lint와 build, 백엔드는 test로 나눴다. PR에서 돌던 실행만 취소하고, develop에 push해서 돈 실행은 끝까지 돌게 뒀다.
- **서드파티 액션은 커밋 SHA로 고정** : 태그는 나중에 다른 코드를 가리키도록 바뀔 수 있다. => 공급망 공격의 위험이 있다.

<br/>

## 주말 분담안

> 주말 동안 각자 따로 일하게 돼서, **서로 기다리는 지점**을 먼저 그리고 각 지점에 대안을 적었다.

- 예를 들어 DB가 늦으면 메모리 저장소로 먼저 진행한다. => 누군가를 기다리다 막히는 일이 줄어든다.
- 인증 기반 작업의 목표는 월요일부터 도메인 담당이 "로그인한 회원 id"를 바로 꺼내 쓸 수 있게 하는 것이다.
    - 서비스 계층이 Spring Security를 직접 알지 않고 어댑터를 거쳐 꺼내게 했다. => 인증 방식을 바꿔도 도메인 코드가 그대로다.

# 배운 점 & 느낀 점

팀이 정해졌는데, 내가 가장 개발하고 싶었던 기획을 개발할 수 있게 됐고 팀원들도 너무 좋은 사람들을 만나서 좋았다. 그래서 좀 더 의욕을 냈던 것 같다.

나는 팀에서 사용할 여러 규칙과 데브옵스를 구축하려고 했다. 팀원들이 아직 미숙한 분야였기 때문이다. 그래서 이번에는 CI/CD를 내가 하고, 부트캠프가 끝난 뒤 서버를 이전하게 되면 그때 다른 팀원이 그 작업을 하는 방식을 떠올렸다. 설정을 마치면 정리해서 팀원들에게 알려줄 생각이다. 그러면 다음에 팀원이 그 작업을 할 때 부담이 좀 줄어들 것 같다.

규칙은 항상 중요하면서도 어려운 것 같다. 규칙이 없으면 여러 문제가 터질 가능성이 높고, 너무 과한 규칙은 프로젝트를 지연시키고 불만을 만들 수도 있다. 그래서 그 중간을 찾으려고 노력했다. 그래도 잘 정해진 것 같아서 다행이라고 생각한다. 결과는 더 지켜봐야 하지만.
