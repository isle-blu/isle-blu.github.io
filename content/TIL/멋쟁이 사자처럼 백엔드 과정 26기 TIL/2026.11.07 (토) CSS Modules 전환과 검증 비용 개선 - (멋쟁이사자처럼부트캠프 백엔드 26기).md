# 오늘의 상황

> 프론트 구조 개편을 마무리하고, Tailwind를 CSS Modules로 전환했다. 이후에는 테스트와 AI의 반복 검증 비용도 줄이기 위해 기준을 정리했다.

전날 올린 구조 개편 PR을 병합한 뒤 채팅 메시지 한도를 늘렸다. 프론트에서는 컴포넌트별 파일 배치와 스타일을 정리하고, 기존 화면을 유지했는지 비교했다.

# 오늘의 과정

## 프론트 구조 개편 마무리

PR 152의 리뷰를 확인하고 구조 개편을 먼저 병합했다. import·조건문 공백, JSX 들여쓰기, 불필요한 빈 줄과 이전 세션 모듈의 경로 설명은 [PR 154](https://github.com/likelion-backendschool-9th/test-moa/pull/154)로 분리했다.

타입 검사·lint·빌드와 구조 테스트 46개, E2E 311개 통과를 확인했다.

## 채팅 메시지 한도 늘리기

서버의 메시지 한도를 500자에서 10,000자로 늘리고 [PR 155](https://github.com/likelion-backendschool-9th/test-moa/pull/155)를 올렸다.

- 공백과 줄바꿈을 그대로 저장하도록 확인했다.
- 채팅함에서도 최근 메시지 전체를 반환하는지 확인했다.
- 10,001자 거절, 이모지의 UTF-16 경계, 줄바꿈 보존을 테스트했다.

관련 테스트 33개가 통과했다. 다만 테스트 통과와 기존 DB의 컬럼 변경은 별도로 확인했다.

### 기존 데이터가 있는 DB에서도 바뀔까?

원격 Docker의 PostgreSQL에서 다음 순서로 검증했다.

1. 기존 코드로 `varchar(500)` 컬럼과 메시지 데이터를 만든다.
2. 변경한 코드를 `ddl-auto: update`로 실행한다.
3. 컬럼이 10,000자로 확장되고 기존 메시지가 보존되는지 확인한다.

테이블을 지우지 않고 컬럼을 확장하면서 기존 메시지가 유지되는 것을 확인했다. 프론트 입력 한도 변경은 이슈 54로 분리하고, PR에는 배포 후 확인 절차도 남겼다. 기록 시점에 PR 155는 아직 병합 전이다.

### 다음 채팅 작업 계획

대화방 이름 변경·삭제 작업을 계획하면서 `ChatRoom`이 참가와 모집글을 모두 참조하는 이유도 살펴봤다. 참가를 통해 모집글을 찾을 수 있는데 같은 관계를 중복 저장하고 있어서, 이슈 156으로 분리했다.

엔티티에서 필드를 지워도 기존 DB의 `NOT NULL` 컬럼은 남을 수 있다. 그래서 코드에서 관계를 제거하는 것과 DB 변경을 함께 계획해야 했다. 이 부분은 계획과 이슈 등록까지 진행했다.

## Tailwind에서 CSS Modules로 전환하기

Tailwind를 사용하면서 클래스가 길어질수록 JSX를 읽고 관리하기 어렵다고 생각했다. Tailwind에 대한 비판 중 마크업이 복잡해진다는 의견에 나도 공감했다. 그래서 스타일은 CSS Modules로 분리하고, 컴포넌트와 스타일 파일, 관련 훅은 같은 폴더에 모았다. 관련 코드는 가까이 두면서 각각의 내용을 읽고 수정하기 쉽게 만들고 싶었다.

- 컴포넌트 119개를 이름과 같은 폴더로 묶었다.
- 컴포넌트 옆에 `.module.css`와 관련 `hook.ts`를 배치했다.
- Tailwind 클래스를 CSS Modules로 옮기고 Tailwind 의존성을 제거했다.
- 색·간격·글자 크기·모서리·모션 값은 전역 토큰으로 정리했다.
- 반복되는 패널은 공통 컴포넌트로 묶었다.
- E2E는 스타일 클래스 대신 속성으로 요소를 찾도록 수정했다.

### 같은 스타일을 옮겨도 결과가 달라졌다

기존에는 CSS 우선순위에 밀려 적용되지 않던 스타일이 전환 후 나타나는 경우가 있었다. 스켈레톤 모서리와 첨부 이미지 비율을 수정했고, 호출하는 쪽에서 덮어쓸 기본 스타일에는 `:where()`를 사용했다. 다른 CSS Module의 요소와 연결해야 하는 부분은 `data-*` 속성을 사용했다.

### 화면 비교와 구조 검사

기준 커밋과 변경 코드를 각각 빌드해 화면을 픽셀 단위로 비교하는 도구를 만들었다. 라이트·다크 모드와 두 화면 폭에서 총 160장 모두 0픽셀 차이를 확인했다. macOS뿐 아니라 원격 Docker의 Linux 환경에서도 동일하게 통과했다.

구조 검사에는 다음 규칙을 추가했다.

| 규칙  | 검사 내용                                  |
| --- | -------------------------------------- |
| R4  | 컴포넌트가 전용 폴더에 배치됐는지                     |
| R5  | CSS Module 값이 정한 토큰·기준을 따르는지           |
| R6  | 정의되지 않은 CSS 변수를 사용하는지                  |
| B8  | 컴포넌트의 `api.ts`가 시연 코드·백엔드 통신을 직접 호출하는지 |

검사기가 TSX에서 정의한 CSS 변수를 놓치는 오탐도 수정했다. 최신 develop을 병합하면서 출금 처리 폼의 충돌을 해결한 뒤, 구조 테스트 55개·전체 E2E 314개와 타입 검사·lint·빌드 통과를 확인했다.

이 작업은 [PR 161](https://github.com/likelion-backendschool-9th/test-moa/pull/161)로 올리고 병합했다. 다만 hover·포커스·애니메이션 등 일부 상태의 직접 확인은 남겨 뒀다. 기존부터 있던 디자인 문제와 기계적인 클래스 이름 정리도 후속 범위로 구분했다.

## 테스트와 AI 검증 비용 줄이기

테스트 수와 반복 실행 비용을 줄이는 작업을 했다. 테스트 실행뿐 아니라 로그 확인과 반복 리뷰에 드는 AI 토큰 비용도 너무 컸기 때문이다.

고정 문구·개수·세부 배치에 집중된 E2E를 줄이고, 입력 규칙·계산·경계값은 브라우저 없이 실행하는 단위 테스트 11개로 분리했다. E2E는 314개에서 143개로 줄였다.

기본 검증은 정적·단위 검사로 두고, 화면 동작이 바뀌면 관련 E2E를 선택하도록 기준을 정리했다.

### 줄이는 과정에서 생긴 공백 확인하기

리뷰하면서 빠진 검증도 보완했다.

- 출금 목록에 전체 계좌번호가 노출되지 않는지 확인
- 다른 사람의 프로젝트로 모집을 작성할 수 없는지 확인
- 단위 테스트로 확인하는 규칙과 직접 봐야 하는 화면 동작을 문서에서 구분

최종적으로 단위 테스트 11개·구조 테스트 55개·선택 E2E 8개가 통과했다. 축소 후 전체 E2E 143개를 모두 실행한 것은 아니다.

이 작업은 [PR 164](https://github.com/likelion-backendschool-9th/test-moa/pull/164)로 올리고 오전에 병합했다.

## 같은 검증을 반복하지 않도록 기준 남기기

테스트 개수만 줄이는 데서 끝내지 않고, AI가 검증하는 방식도 정리했다.

- 코드·설정·환경이 같으면 기존 검증 결과를 재사용한다.
- 문서 수정이나 커밋 정리만으로 빌드·E2E를 반복하지 않는다.
- 성공 로그는 요약 위주로 보고, 실패 로그는 필요한 구간부터 확인한다.
- 재리뷰는 이전 검토 이후 변경된 부분부터 확인한다.
- 단위 검사로 옮긴 범위, 남긴 E2E, 자동 확인에서 제외한 범위를 대응표로 남긴다.

관련 이슈 165를 만들고 PR·프로젝트에 연결했다. 실제 토큰 절감량을 측정한 것은 아니지만, 반복 비용을 줄이기 위한 기준을 마련했다.

## 팀원 PR 리뷰

운영자 출금 API PR 157을 리뷰했다. 테이블 이름이 바뀌면서 기존 데이터를 못 읽게 될 가능성을 검토했지만, 서버에 기존 데이터가 없다는 설명을 확인하고 해당 차단 의견을 철회했다. 출금 관련 단위 테스트 27개 통과도 확인했다.

# 배운 점 & 느낀 점

이번에는 컴포넌트와 관련된 파일을 가까이 모으면서도 마크업과 스타일은 나눠서 관리하는 방식을 선택했다. Tailwind 클래스로 JSX가 복잡해지는 것이 관리하기 어렵다고 생각했기 때문이다.

테스트 실행·로그 확인·반복 리뷰에 드는 AI 토큰 비용도 개선하고 싶었다. 테스트를 줄이는 작업과 함께, 어떤 검증을 실행하고 기존 결과를 언제 재사용할지 기준을 정리했다.

나는 여전히 프론트엔드보다 백엔드가 훨씬 어렵게 느껴진다. 아직 구조가 적응이 되지 않고, 자유도가 상대적으로 더 높게 느껴져서 그런거 같다. 이번에 구조를 파악하면서 어느정도 이해를 했다고 생각한다. 그래도 아직 부족하기 때문에 추가적인 공부가 필요할 거 같다.
