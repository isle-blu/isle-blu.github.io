## 업무 시스템·URL 구조·Git 기초

# Interface

> 어떠한 기기, 소프트웨어 등을 인간이 다룰 수 있게 해주는 **접점**

- 접점을 통해 다른 무언가를 조작하거나
- 어떠한 방식으로 접점을 가지느냐의 따라 종류가 구분됨.

## 인터페이스의 종류

|종류|설명|
|---|---|
|UI|User Interface, 사용자가 직접 보고 다루는 인터페이스, 아래 적힐 콘솔, Shell도 일종의 UI로 볼 수 있음.|
|Console|어떤 **장치**를 다루기 위해 제공하는 접점, 물리적인 직접 접근이 가능, 현대에는 물리적인 장치 뿐만 아니라 네트워크를 거치지 않은 접점을 콘솔이라고 하기도 함.|
|Shell|컴퓨터 내부의 OS에 접근하고, OS가 관리하는 APP을 다룰 수 있게 하는 UI, 사용자가 복잡한 OS와 APP을 보이지 않게 가리는 역할도 함, Windows의 탐색기 / Unix 계열 OS의 bash, zsh가 있음|
|CUI|Character UI, 문자로 이루어진 UI|
|GUI|Graphical UI, 그래픽 위주의 UI|
|CLI|(임시)|
|Terminal|Terminal의 사전적 의미는 "끝, 종점", 즉 터미널은 끝 단에 있는 기기, 즉 "단말기"(ex - 휴대폰, ATM 기기 등)를 뜻함, 현대에는 소프트웨어로 많이 대체되어 사용.|

## Operating System(OS)

> 한국 말로 운영체제로, 기기 내부에 여러 APP들을 사용자가 운영(operating)할 수 있게 해주는 시스템

- OS는 APP을 관리하는 **주체**
- 사용자는 OS를 통해 APP에 접근
- 사용자와 OS를 이어주는 것이 바로 **UI**

> 왜 개발자는 Linux를 사용할까? 우리가 컴퓨터를 사용하는 이유는 특정 "소프트웨어"를 쓰기 위해서다. 개발을 위한 소프트웨어는 Linux 환경에 적합하기 때문에 Linux 환경을 선호한다.

# Git branch와 merge, conflict

## Branch

> 프로젝트에서 현재 목적(기능 추가, 버그 수정)에 맞게 **작업을 분리**해서 관리할 수 있게하는 Git의 하위 기능

### branch 규칙

1. 소문자 사용 : 가독성을 위해 소문자 영어만 사용한다.
2. 케밥 케이스(kebab case) : 단어 사이에 하이픈 "-"을 넣어 연결하는 네이밍 규칙
3. 의미는 명확하게 : 작업의 목적과 내용이 잘 드러나도록 작성

### 자주 사용되는 접두사

- 브랜치의 이름만 보고 해당 브랜치가 어떤 작업을 하려고 만들어졌는지 확인하고 공유하기 위해 통용되는 접두사 들이다.
- "접두사/작업내용"의 형식을 가진다. ex) feature/login

|접두사|내용|
|---|---|
|feature 또는 feat|새로운 기능을 개발할 때|
|fix 또는 bugfix|버그를 수정할 때|
|hotfix|긴급한 운영 환경 버그를 수정할 때|
|refactor|기능 변경 없이 코드 구조를 개선할 때|
|docs|문서 작성이나 수정 시|
|test|테스트 코드 작성 및 수정 시|
|chore|빌드 스크립트 수정, 패키지 관리 등 반복적인 작업 시|

## Merge

> branch로 독립해 **작업한 내용을 병합**하는 Git의 하위 기능

> Fast-Forward Merge? merge 명령어의 기본 설정 branch를 병합할 때, 별도의 commit 없이 병합되는 것을 말한다. 조건 : 현재 branch에 commit이 없고, 병합하려는 branch에 commit이 있는경우 => merge를 통한 commit 메시지가 작성되지 X

```
#Fast-Forward Merge 동작 과정
main:      A---B        # main에 추가 commit X 
                 \
feature:          C---D

merge 후 (fast-forward):
main:      A---B---C---D
                        ↑
                 main, feature 둘 다 여기
```

### Conflict

> **동일한 파일**을 여러 branch에서 다르게 수정하고 merge할 때 발생하는 충돌

#### 상황과 해결 방안

|상황|해결 방안|
|---|---|
|양쪽이 같은 라인을 수정|해당 파일의 코드를 직접 수정 후 저장, 커밋|
|한쪽이 수정 + 한쪽이 삭제|파일을 삭제할지 말지 결정 후 커밋|
|충돌이 너무 심한 경우|없던 일로 되돌리기(git merge --abort)|
|branch를 폐기해야 하는 경우|강제 삭제 (git branch -D)|

### branch / merge 관련 명령어

|명령어|동작|
|---|---|
|git branch|현존하는 브렌치 목록, 현재 가리키고 있는 브랜치는 "*" 로 표시|
|git branch <브랜치 이름>|<브랜치 이름>의 브랜치를 새로 생성|
|git branch -d <브랜치 이름>|<브랜치 이름>의 브랜치를 삭제|
|git branch -D <브랜치 이름>|<브랜치 이름>의 브랜치를 강제 삭제|
|git switch <브랜치 이름>|<브랜치 이름>의 브랜치로 전환|
|git switch -c <브랜치 이름>|<브랜치 이름>의 브랜치를 생성하고 해당 브랜치로 전환|
|git restore|이전 commit한 내용으로 돌림, Modified된 내용이 이전으로 돌아감|
|git merge <브랜치 이름>|<브랜치 이름>의 브랜치와 현재 브랜치를 병합|
|git merge --no-ff <브랜치 이름>|브랜치 병합 시 Fast-Forward merge라도 Commit 메시지, merge history를 남김|
|git merge --abort|충돌 나기 전의 브랜치로 롤백|
