# 오늘의 과정

## 팀에 CI/CD 흐름 설명

> 우리 배포가 어떻게 도는지 팀원들에게 설명했다.

- **feature 브랜치에 push** : 아무것도 돌지 않음
- **PR** : 검사만 돎 (프론트 lint·build, 백엔드 test) => 승인 1명을 받으면 Squash merge
- **develop에 머지** : 검사 → 이미지 빌드 → GHCR 업로드 → 서버에서 새 이미지로 재시작 → Campfire 알림
- 따로 나온 질문은 없었지만, 지금 우리 배포 방식을 이해하는 데는 도움이 된 것 같다.

<br/>

## 커뮤니티 설계와 헥사고날

> 커뮤니티, 엽서 기능은 처음부터 설계해야 할까?

- 프론트 데모에 커뮤니티·우체통·엽서 동작이 이미 정해져 있었다. => 새로 설계하기보다 **데모가 정한 동작을 서버로 옮기는 일**로 봤다.
- 로드맵상 커뮤니티는 MVP, 엽서는 3차 => **커뮤니티부터** 한다.
- 커뮤니티 글 CRUD 이슈를 만들고 계획 문서까지 작성했다. (아직 커밋 전)

> 헥사고날에서 말하는 포트, 어댑터, 유스케이스는?

- **포트** : 핵심 코드가 정한 인터페이스 (콘센트)
- **어댑터** : 그 인터페이스를 웹·DB로 구현한 클래스 (플러그)
- **유스케이스** : "사용자가 할 수 있는 일 하나"를 나타내는 입력 포트

> CRUD도 유스케이스마다 나눠야 할까?

- 우리 팀 규칙으로는 나눈다. => Create / Get / List / Edit / Delete **5개**
- 그런데 이건 헥사고날 원전(Cockburn)의 정석이 아니라, Tom Hombergs의 『만들면서 배우는 클린 아키텍처』 방식이었다.
- 원전은 포트를 얼마나 잘게 나눌지 정하지 않는다.

> 페이지 단위로 컨트롤러를 나누는 건 3계층이라서 생긴 방식일까?

- 아니다. 서버가 화면을 그리던 MVC나 SI 스타일에서 온 방식이다.
- REST API는 3계층에서도 보통 **도메인 단위**로 나눈다. => API는 화면을 몰라야 하기 때문

<br/>

## 공용 서버 설정

### 호스트 nginx 설정이 적용되지 않음

> `sites-available`에 설정 파일을 만들었는데 왜 적용이 안 됐을까?

- 응답이 "Welcome to nginx"(615바이트)라면 => **우리 설정이 아직 읽히지 않았다**는 신호
- `nginx.conf`의 `include`를 확인해 보니 `sites-enabled`를 읽고 있었다.
- `sites-enabled`에 링크를 걸어서 해결 → certbot으로 HTTPS 설정
- 최종 확인 : HTTP는 301로 https로 넘어가고, HTTPS는 502 => 앱이 아직 없어서 나는 것이고, **인증서는 정상**

<br/>

## compose 개편과 배포 방식

> 처음엔 `compose.override.yaml`을 서버용으로 썼는데, **Docker 관례와 반대**였다.

- 관례대로 3개로 다시 나눴다.
    - `compose.yaml` : 공통 설정
    - `compose.override.yaml` : 로컬용, 자동으로 합쳐짐
    - `compose.prod.yaml` : 서버용, GHCR 이미지 사용
- 로컬에서도 서버와 같은 구성을 띄울 수 있다. => 내 환경에서만 다르게 도는 **스노우플레이크 문제를 줄임**

> Spring Boot도 `compose.yaml`을 찾는데, 겹치지 않을까?

- 둘 다 **실행 폴더의 `compose.yaml`** 을 자동으로 찾는다.
- 두 표준이 충돌하는 게 아니라, **폴더를 나누면** 같이 쓸 수 있다. => backend 폴더는 DB만, 루트는 전체 구성

> 서버에는 파일을 어떻게 둘까?

- clone 대신 워크플로가 **필요한 파일만 복사** => 서버에서 직접 만드는 건 `.env`뿐
- 이미지와 설정이 **항상 같은 커밋에서** 온다.
- 정해진 표준은 아니지만, 이 방식을 경험해 보기로 했다.

<br/>

## Secrets와 .env

> 서버 접속 정보는 저장소가 아닌 **GitHub 환경 `develop`의 Secrets**에 넣었다.

- 환경 Secrets는 `environment: develop`을 지정한 작업만 읽을 수 있다. => **배포 작업만** 읽게 하기 위해

> 서버 `.env`에 비밀값을 넣을 때 주의할 점은?

- 키 값을 명령에 직접 쓰면 **셸 기록에 남는다.** => 편집기로 넣기
- `$(openssl rand -hex 32)`처럼 실행할 때 만드는 값은 기록에 남지 않는다.
- DB 비밀번호, `JWT_SECRET`은 한 번 정하면 바꾸지 않기

<br/>

## 오늘의 결정

> 모든 API에 `/api/v1` 접두사를 붙이기로 했다. 그럼 어떻게 붙일까?

| 방식 | 특징 |
| --- | --- |
| 컨트롤러마다 직접 쓰기 | 가장 흔하다 |
| `server.servlet.context-path` | 설정 한 줄로 끝나지만, `/error`와 Swagger까지 접두사 아래로 들어가고 MockMvc 테스트에는 적용되지 않는다 |
| `PathMatchConfigurer.addPathPrefix` | Spring 5.1부터 있는 공식 기능, 조건에 맞는 `@RestController`에만 붙인다 |
| Spring 7 API 버전 기능 | Boot 4에 새로 들어온 기능, 아직 사례가 적다 |

- **상황** : 컨트롤러마다 직접 쓰는 방식이 가장 흔하지만, 설정으로 한 번에 붙이는 방법을 찾았다.
- **무엇으로 바꿨나** : `addPathPrefix` => 컨트롤러는 `/auth`, `/members`처럼 접두사 없이 작성
- **왜** : context-path는 `/error`, Swagger까지 바뀌고 MockMvc 테스트에도 적용되지 않는다. => `addPathPrefix`는 **`@RestController`에만** 붙는다.
- 주의 : Spring Security 경로 검사에는 접두사가 붙지 않는다. => 인증 없이 여는 경로 목록에는 **전체 경로**를 써야 한다.

# 남은 작업

- 배포 PR : 지도 API 키를 넣고 머지 → 첫 배포 뒤 **GHCR 패키지를 공개로 바꾸고** 다시 실행
- 내일 PR들에 리뷰어 지정, 배포·DB 문서는 배포 PR 다음에 팀 의견 받기
- 커뮤니티 계획 문서 커밋, 인증 담당 팀원과 정리해 둔 내용 확인
