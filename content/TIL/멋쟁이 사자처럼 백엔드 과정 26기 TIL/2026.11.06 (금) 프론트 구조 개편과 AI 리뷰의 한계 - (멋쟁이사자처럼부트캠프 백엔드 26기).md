# 오늘의 상황

> 역할별 URL을 정리하고, 프론트 구조를 다시 점검해 개편했다.

인증·채팅과 팀원들의 백엔드 PR을 리뷰하고, 테스터와 개발자의 URL을 나누는 작업을 했다. 이후 프론트 전체 구조를 살펴보면서 코드 배치와 의존 방향까지 다시 정리하게 됐다.

# 오늘의 과정

## 프론트 구조를 다시 점검한 이유

프론트는 Next.js App Router를 사용하고 있었는데, 기존 React 프로젝트에서 쓰던 구조를 섞어 놓으면서 코드 배치와 책임 구분이 많이 흐트러져 있었다. 한 구역에서만 사용하는 컴포넌트가 최상위 공용 폴더나 `features`에 섞여 있기도 했다.

AI에게 구조를 점검하게 했지만, 우리 문서에 적힌 규칙을 따르는지만 확인했다. 그 규칙 자체가 적절한지, 실제 코드가 App Router에 맞게 구성되어 있는지는 충분히 확인하지 않았다.

그래서 Next.js 공식 문서와 웹 검색 결과를 함께 확인하게 했다. 이를 바탕으로 실제 구조의 문제를 찾아 개편을 진행했다.

그 과정에서도 AI가 사실과 다른 내용을 제시하는 일이 계속 있었다. 여러 세션을 오가며 리뷰를 시키고, 계획을 보완한 뒤 구현을 진행했다.

<br/>

## 역할별 URL부터 정리하기

테스터의 참여 테스트는 `/testers/recruitments`, 개발자의 프로젝트·모집은 `/developer/...`로 옮겼다. 페이지 이동에 맞춰 링크, 로그인 후 돌아갈 주소, 문서와 E2E도 수정했다.

- 모집 작성 시 프로젝트는 `?project=`로 받도록 정리했다.
- 모집 관리와 액션에서 소유권·상태 확인과 필요한 데이터 조회를 분리했다. 화면 전체를 조회해야만 처리할 수 있는 구조를 줄이기 위해서였다.
- URL 생성 규칙을 공통 함수로 모았다.

[PR #126](https://github.com/likelion-backendschool-9th/test-moa/pull/126)에서 타입 검사·lint·빌드와 E2E 298개 통과를 확인했다.

병합 후에는 [PR #132](https://github.com/likelion-backendschool-9th/test-moa/pull/132)로 테스터 참여 목록·상세 URL 생성도 공통화했다. 한글·공백·특수문자가 포함된 키의 인코딩을 확인하고, 역할별 URL 문서와 E2E를 보완했다. 이때는 E2E 300개가 통과했다.

<br/>

## 파일을 옮기기 전에 기준 만들기

목표 구조, 의존 방향, 파일 이동표와 검증 절차를 먼저 문서로 만들었다. 상위 이슈 #143과 하위 이슈 #144~#151로 작업도 나눴다.

계획을 리뷰하면서 실제 구현 시 문제가 될 부분을 찾아 보완했다.

- 액션에서 시연 데이터 저장 함수를 직접 호출하는 부분
- 서버 전용 의존성이 있는 화면 틀을 클라이언트 오류 화면에서 사용하는 부분
- 인증·회원·구독 사이의 의존 방향이 문서 안에서도 충돌하는 부분
- 검사 도구가 위반을 출력하고도 성공으로 종료하는 부분

문서에 규칙을 적어 두는 것과 그 규칙을 실제 코드에 적용할 수 있는지는 따로 확인해야 했다.

## 사용 범위와 책임에 맞춰 배치하기

별도 worktree에서 구조 개편을 진행했다.

- `src`를 없애고 `frontend/app`, `components/ui`, `features`, `demo`, `lib`로 정리했다.
- 한 구역에서만 사용하는 컴포넌트와 보조 코드는 해당 라우트의 `_components`, `_lib`로 옮겼다.
- 사이트 레이아웃과 채팅방 레이아웃을 분리했다. 404에서 본문과 푸터가 중복되는 경우도 찾아 수정했다.
- 시연 데이터와 쿠키 저장 코드는 `demo`로 모았다.
- 회원·구독·신고·크레딧·프로젝트·모집의 책임을 나누고, 데이터 접근은 도메인별 `api.ts`로 정리했다.

이번 프로젝트에서는 `src`를 제거하는 구조를 선택했다. `src`나 최상위 `components`가 있다는 이유만으로 잘못된 구조라고 판단한 것은 아니다. 실제 사용 범위와 책임에 맞게 배치하고 의존 경계를 정리하는 것이 기준이었다.

## 검사 도구도 다시 검증하기

import 경계 규칙 B1~B7과 배치 규칙 R0~R3을 검사 도구와 CI에 연결했다. 그런데 검사 도구에도 누락과 오탐이 있어서 반복해서 리뷰하고 수정했다.

- `.tsx` 파일과 중첩 폴더의 경계 검사가 빠지는 문제
- 백틱을 사용한 동적 import가 검사를 우회하는 문제
- 경로 그룹을 지우는 과정에서 배치 판정이 누락되는 문제
- 계정 화면과 채팅함 사이의 정상적인 공유까지 막는 문제

잘못된 의존을 놓치지 않는지뿐 아니라, 허용해야 하는 공유를 막고 있지는 않은지도 확인했다.

### 개편 후 검증 결과

| 항목 | 결과 |
| --- | --- |
| 타입 검사·lint·빌드·배치 검사 | 통과 |
| 전체 E2E | 311개 통과 |
| 구조 회귀 테스트 | 46개 통과 |
| 배치 규칙 위반 | 개편 전 R1 88건 → 개편 후 전체 규칙 0건 |
| 페이지·Route Handler 34개와 OG 이미지 경로 | 유지 |
| 도메인 순환 의존 | 없음 |

너무 크게 합쳤던 커밋 이력은 단계별 18개 커밋으로 다시 정리했다. 이후 [PR #152](https://github.com/likelion-backendschool-9th/test-moa/pull/152)를 올렸다. PR 생성 당시 CI는 실행 중이었다.

## PR 리뷰에서 확인한 문제들

### 인증 경쟁 상황과 채팅 테스트

채팅 API #104의 계층별 책임과 결합도, 과도한 추상화 여부를 검토했다. 인증 PR #102와 후속 PR #123에서는 토큰 갱신과 로그아웃이 겹치는 상황을 살펴봤다.

- 로그아웃 이후 늦게 도착한 갱신 응답이 사용자를 다시 로그인시키는지
- 여러 탭에서 같은 refresh 토큰으로 동시에 갱신해도 로그인이 유지되는지
- 여러 차례 갱신한 뒤에도 로그아웃이 제대로 적용되는지

전체 E2E에서는 채팅 테스트 S151이 간헐적으로 실패했다. 메시지가 표시되기 전에 개수를 읽고 있어서, 표시를 기다린 뒤 확인하도록 제안했다. 반영 후 20회 반복 실행과 전체 E2E 293개 통과를 확인했다.

### 날짜 경계와 동시 생성

AI 후속 질문 API #127은 실제 유료 분석 API를 호출하지 않고 구조와 테스트를 점검했다. 외부 HTTP 클라이언트가 JPA 엔티티와 조회 방식에 결합된 부분을 지적하고, 외부 통신 중 DB 트랜잭션을 유지하는지도 확인했다.

자정 전에 시작한 요청이 지연되어 다음 날 처리되면 하루 사용 한도를 초과할 수 있는 문제도 재현했다. 수정 후에도 날짜 집계 문제가 남아 있어서 후속 이슈 #136으로 남겼다.

프로젝트·모집 API #128에서는 `testItems: [null]`이 검증을 통과해 400 대신 500이 발생하는 문제를 발견했다. 최초 모집 작성 요청이 동시에 들어오면 유형 생성의 유일 제약 충돌로 실패할 가능성도 지적했다. 수정 후 관련 테스트 17개 통과를 확인했다.

### 그 밖에 확인한 내용

- 백엔드 패키지 개편 #140의 import·JPQL·스캔 범위와 OAuth 트랜잭션 범위, 공통 패키지에 섞인 출금 정책을 검토했다.
- 참여 목록 디자인 #141과 피드백 카드 #142를 리뷰했다.
- 채팅 메시지 길이 확장 계획에서는 테이블 삭제가 필요한지, 10,000자·10,001자 경계 검증이 충분한지 살펴봤다. 이 작업은 구현이 아닌 계획 리뷰까지 진행했다.
- 디자인 규칙과 버튼·검색창·정렬 등 UI 통일을 위한 후속 이슈를 등록했다.

## 배포 설정 점검

배포 실패 로그를 보고 필수 설정과 환경 변수 전달 경로를 확인했다.

Spring 설정의 `${환경변수:기본값}`과 Docker Compose의 필수 변수 검사가 서로 다른 단계라는 점을 정리했다. AI 설정이 없을 때도 애플리케이션이 기동할 수 있는지와 AI 기능을 사용할 수 있는지는 나눠서 확인했다.

설정 파일에는 환경 변수 참조를 두고, 실제 비밀값은 외부에서 주입하는 방식도 검토했다.

# 배운 점 & 느낀 점

AI에게 구조를 점검하게 했지만, 우리 문서에 적힌 규칙을 지켰는지만 확인하고 있었다. 문서 자체의 기준이나 실제 구조가 적절한지까지 확인한 것은 아니었다. 그래서 NextJS 공식 문서와 웹 검색 결과를 함께 확인하게 하고, 여러 세션을 오가며 계획과 구현을 반복해서 리뷰했다.

그 과정에서도 계속 잘못된 내용이 나왔다. 나도 아직 구조를 정확히 보는 데 미숙해서, 지금 개편한 결과를 100% 믿지는 못한다. 최대한 문서를 근거로 리뷰를 시키면서 문제를 찾아내는 식으로 진행했다.

결국 내가 확실하게 공부하고 알아야 한다는 걸 다시 한번 느꼈다. AI가 점검했다고 해도 내가 판단할 기준이 없으면 잘못된 부분을 놓칠 수 있다. AI는 완벽하지 않으니까, 결과를 확인하는 내 이해도도 같이 높여야 한다.
