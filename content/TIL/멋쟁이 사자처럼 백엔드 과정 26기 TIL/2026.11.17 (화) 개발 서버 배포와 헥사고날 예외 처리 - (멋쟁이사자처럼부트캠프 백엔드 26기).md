# 오늘의 상황

> 오늘은 개발 서버 배포를 마무리하고, 예외 처리 규칙을 정했다.

배포 PR에 달린 질문과 리뷰를 정리해서 머지하고, 첫 배포까지 확인해야 했다. 그리고 기존 예외 규칙 때문에 업무 규칙이 서비스로 밀려나고 있어서, 예외를 어디서 처리할지도 다시 정했다.

---

# 오늘의 과정

## 개발 서버 배포 마무리

> 머지 전에 팀원들이 궁금해한 것부터 정리했다.

- 서버에 compose 파일을 미리 옮길 필요는 없다. 배포 워크플로가 scp로 복사하니까. => 서버에 미리 있어야 하는 건 **`.env`뿐**이다.
- 복사할 경로는 Secret이 아니라 CI 워크플로 파일에 적혀 있다.
- 팀 계정 비밀번호도 필요 없다. Actions는 키로 접속하고, 계정이 docker 그룹이라 sudo 없이 실행된다.

> 리뷰 반영

- `docker image prune -a` : `-a`가 없으면 `sha-` 태그로 받은 이전 이미지가 계속 쌓인다. 저장소 라벨 필터를 같이 걸어서 다른 팀 이미지는 지우지 않는다.
- 배포가 성공했는지 판정할 수 있게, 배포 후 응답을 확인하는 단계를 추가했다.
- 호스트 키 검증용 `DEPLOY_HOST_FINGERPRINT` Secret을 추가했다. 값에 `SHA256:`까지 붙여야 한다. => 액션이 Go `x/crypto`로 만든 지문과 **글자 그대로** 비교하기 때문이다.

### 첫 배포가 실패했다

> 왜 `lookup *** ... no such host`가 났을까?

- 러너가 `DEPLOY_HOST`를 도메인으로 찾았는데 못 찾은 것이었다.
- Secret에 **내 PC의 SSH 별칭** 같은 값이 들어가 있었다. => 내 PC에서만 통하는 이름이었다.
- 러너가 인터넷에서 닿을 수 있는 주소(도메인이나 IP)로 바꿔서 해결
- 별칭 없이 `ssh <계정>@<도메인>`을 해서 비밀번호를 묻는 단계까지 가면, 연결은 된 것이다.

> 확인한 것

- HTTP는 301, `/`는 200(프론트엔드), `/api/v1/`은 401 => 백엔드까지 도달했다.
- 첫 Campfire 알림도 나갔다.
- GitHub 환경 `develop`은 develop 브랜치에서만 배포할 수 있게 막았다.

## 사진은 어디에 저장할까?

> 개발 서버와 운영 서버에서 사진을 저장하는 곳이 다르다.

- 파일 저장은 포트 뒤에 둔다. 개발 서버는 Docker 볼륨, 운영 서버는 S3 호환 스토리지를 쓴다. => 옮길 때 **어댑터만 바꾸면 된다.**
- 사진 한 장은 최대 15MB다. Spring `max-file-size`, `max-request-size`와 nginx `client_max_body_size`를 같이 맞춘다.
- 한 요청에 한 장씩 올린다. 업로드 API가 id를 돌려주고, 일기를 저장할 때는 id만 보낸다.
- external 볼륨이 아니라 일반 볼륨을 쓴다. 백업은 아직 없고, 외부 테스터를 받기 전에 만든다.

> 확인한 것

- Dockerfile에서 폴더를 app 소유로 만들어 두면, 새 볼륨이 그 소유권을 이어받는다. 컨테이너를 다시 만들어도 파일은 남는다.
- 미디어 PR 작성자에게 맞출 두 가지를 코멘트로 남겼는데, 3분 만에 반영됐다.
- 머지 후 배포 로그에서 볼륨이 만들어진 것까지 확인했다.

<br/>

## 헥사고날에서 예외는 어디서 바뀌어야 할까?

> 안쪽(도메인·애플리케이션)은 바깥 기술(HTTP 등)을 모른다. 그래서 예외는 계층 경계를 넘을 때 **그 계층의 말로** 바뀐다.

- 도메인 예외인지는 **도메인 객체 하나만 보고 판단할 수 있는가**로 가른다.
- ex) 이름 길이, 미래 생일, 작성자가 아닌 사람의 수정

> 기존 규칙의 문제

- "웹 어댑터는 도메인을 import하지 않는다"는 규칙이 예외 클래스까지 막고 있었다.
- 그래서 "작성자만 수정할 수 있다" 같은 업무 규칙이 서비스로 밀려났다. (반려동물 도메인의 소유권 확인)
- 그런데 바깥이 안쪽을 아는 의존은 헥사고날에서 원래 허용된다. => 기존 규칙이 표준보다 엄격했던 것이다.

<br/>

## 예외를 옮기는 작업은 이슈 하나로

> 도메인별 예외를 기본 예외로 옮기는 작업을 이슈 하나에 모았다.

- 도메인 담당자가 각자 자기 항목을 체크한다.
- PR에서는 `closes` 없이 참조만 하고, 마지막 항목을 체크한 사람이 이슈를 닫는다.
- global 담당은 아직 정하지 않았다. 기본 예외 코드가 아직 미디어 PR에만 있고 develop에는 없기 때문이다.
- 예외 규칙 이슈는 아직 열려 있다. 제목은 Docs인데 할 일에 코드 작업이 섞여 있어서다.

<br/>

## 커뮤니티 글 계획 문서

> 글 API 계획 문서를 올리고, 리뷰를 반영해서 머지했다.

- 경로는 `/api/v1/posts`, 카테고리 목록은 `/api/v1/posts/categories`로 정했다.
- 카테고리는 테이블로 관리하고, 목록을 조회할 때 카테고리는 필수다.

> 리뷰 반영

- 예외 처리를 새로 정한 규칙에 맞췄다. => 도메인별 핸들러를 만들지 않는다.
- 동시 수정, 목록 범위, 시나리오 번호 유지를 반영했다.
- `size`는 커서 기반 목록에서 한 번에 받아 올 글 개수다.
- 롬복은 따로 올라온 롬복 PR이 머지된 뒤에 적용한다.

> 계획 PR과 구현 PR은 나눴다.

- 계획용 브랜치를 `-plan`으로 따로 만들었다.
- 계획 PR에는 `closes`를 쓰지 않았다. => 이슈는 구현 PR이 머지될 때 닫힌다.

<br/>

## 그 밖에 한 일

- **CI 점검** : 필수 검사 이름과 경로 필터는 잘 되어 있었는데, 프론트엔드 테스트가 CI에서 돌지 않고 있었다. => `npm test` 단계를 추가하고 44개 통과를 확인했다.
- **라벨 자동화** : `backend/**`, `frontend/**` 경로를 바꾼 PR에 라벨을 붙인다. 계획 문서만 있을 때 연 PR에도 나중에 코드 커밋이 올라오면 라벨이 붙도록, 커밋이 추가될 때마다 다시 돈다.
- **계획 문서 양식** : scenario-plan 스킬 형식으로 양식을 샘플로만 추가했다. 원하는 사람만 쓰는 양식이라, 문서 안내에 넣었던 내용은 되돌렸다.

## 오늘의 결정

### 1. 예외는 공통 부모 예외로 처리

- **상황** : 헥사고날 구조에서 도메인 예외를 글로벌에서 응답으로 바꾸는 방법이 두 가지였다.
    - A : `GlobalExceptionHandler`가 도메인 예외를 하나씩 import한다.
    - B : 공통 부모 예외만 처리한다.
- **무엇으로 바꿨나** : B로 정했다. 글로벌 예외 패키지에 기본 예외 4개를 두고, 도메인 예외는 이걸 상속한다.
    - ex) 규칙 위반 → 400, 권한 없음 → 403
    - 예외 처리 문서를 새로 쓰고, 구조 문서의 의존 규칙 표와 리뷰 체크리스트도 고쳤다.
- **왜** : A는 global과 도메인 사이에 **순환 의존**이 생긴다.

### 2. 커뮤니티 카테고리는 테이블로

- **상황** : 글 카테고리를 enum으로 둘지, 테이블로 둘지 정해야 했다.
    - enum은 단순하고 컴파일할 때 검증된다.
    - 하지만 카테고리를 바꾸려면 배포해야 하고, 프론트엔드도 목록을 따로 가져야 한다.
- **무엇으로 바꿨나** : 테이블로 관리한다. (코드, 이름, 정렬 순서, 사용 여부)
- **왜** : 배포 없이 카테고리를 바꿀 수 있다.

# 배운 점 & 느낀 점

오늘은 구조와 팀과의 규칙에 대해 많은 논의가 있었다. 팀 규칙과 구조를 지키지 않은 코드가 너무 많이 PR에 올라온 것이다. 이걸 해결하고 규칙과 구조를 더 명확하게 하기 위해 서로의 코드를 많이 검토했다. 

이제 진짜 걱정은 팀원 모두가 이 규칙을 지킬 수 있는가이다. 실제로 오늘 규칙이 약한 부분이 있었다해도 전체적으로 규칙을 지키지 않은 코드도 많았다. ai가 정한 규칙을 따르는지 확인하고 검토해야하는데 아직 그 부분이 미숙했던 거 같다. 이것도 같이 프로젝트를 진행하면서 발전시켜야 할 거 같다.
