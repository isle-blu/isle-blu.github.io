# 논리 설계에서 생기는 쟁점

> 논리 설계에서 마주하게 되는 쟁점을 주문과 결제를 예시로 설명하고자 한다.

## 관계 테이블끼리도 연결이 가능한가?

> 가능하다. 상황에 따라 필요한 경우가 생긴다.

- 결제의 경우 반드시 주문하고자 하는 메뉴가 무엇인지 알아야한다. => 주문에 대한 데이터가 요구된다.
- 따라서 주문은 결제 테이블의 부모가 되고, 1:1 관계로 연결된다.
- 1:1 관계이므로, 결제 테이블은 외래키로 사용되는 주문 아이디가 PK가 된다.

![이미지](https://cdn.likelion.net/classroom/kdt-backendj-26th/til/3591f3bf-576b-4f94-b808-274102526a63.png)

> 테이블의 부모자식 관계

- 테이블이 이어진 경우 생성 순서에 따라 종속 관계가 생긴다.
- 따라서 먼저 만들어진 테이블이 **"부모"**가 되고, 나중에 만들어진 테이블이 **"자식"**이 된다.
- 다대다 관계의 경우 부모가 둘이 되므로 두 테이블에 종속되는 별도의 테이블을 만들게 된다.

## 속성 하나에 여러 값을 담을 수 있을까?

> 불가능하다.

- 따라서 해당 값을 저장할 별도의 공간이 필요하다. => 해당 속성의 값들을 저장하기 위한 별도의 테이블을 만든다.
- 하나의 주문의 경우, 여러 개의 메뉴가 들어갈 수 있다. 하지만 메뉴 아이디라는 하나의 속성에 여러 값을 담을 수 없다. => **"포함"**이라는 관계 테이블을 만들어, 주문과 메뉴 테이블을 연결한다.
- 포함 테이블에 주문과 메뉴를 연결하고 속성으로 주문 당시 가격과 수량을 넣으면 주문하고자 하는 메뉴에 대한 데이터를 저장할 수 있다.
- 테이블명으로 포함은 적절하지 않기에, 부모 테이블 둘의 이름을 가져와 "주문 메뉴" 테이블이라고 이름을 짓는다.

![이미지](https://cdn.likelion.net/classroom/kdt-backendj-26th/til/7f6cb4d9-2823-49f4-9011-6904839918d7.png)

> 대리키의 사용 여부

- 대리키는 PK로 사용할 키가 없는 경우 사용한다.
- PK의 조건 : 중복 불가, 민감정보 지양, 변경 가능성 없음
- 따라서 PK로 사용할 키가 있다면 대리키는 사용하지 않는다.
- 위에 `주문 메뉴` 테이블의 경우 부모 테이블을 참조하는 외래키 2개를 같이 묶을 경우 하나의 PK가 될 수 있기 때문에, 두 외래키가 하나의 PK가 된다.

> ERD에서 실선과 점선의 차이 실선 : 자식 테이블의 PK가 부모 테이블의 PK를 물려 받는 경우 사용 ex) 주문 메뉴 테이블, 1:1 관계에서 자식 테이블 점선 : 테이블끼리 오로지 참조만 하는 경우 사용
